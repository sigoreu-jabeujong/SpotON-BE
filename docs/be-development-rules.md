## 적용 기준과 원문 구분

분석 대상은 사용자 제공 `12_개발규칙_Git코드컨벤션_SpotON.pdf`(v1.1, 2026-11-06, 5쪽)다. 원문은 확정 사항, BE 피드백 반영 사항, 회의 합의 전 제안을 구분한다. PDF의 제안을 팀 전체의 확정 규칙으로 간주하지 않는다.

사용자 결정과 현재 작성 중인 BE 작업계획서·작업지시서를 우선하고, PDF는 누락된 실무 규칙을 보완하는 참고 자료로 사용한다. 같은 내용은 기존 문서를 기준으로 유지한다. API 계약 보완은 [be-contract-amendments.md](be-contract-amendments.md)에서 관리한다.

## 작업 브랜치·커밋·리뷰

`main`은 기본·시연·최종 반영 브랜치, `develop`은 개발 통합 브랜치다. 작업은 `feat/be-...`, `fix/be-...`, `docs/...`, `chore/...` 등으로 나누며 경로 접두사 뒤 이름은 영문 소문자와 하이픈을 사용한다. ETL·AI 작업은 영역을 구분해 이름을 짓는다.

1. 작업계획서와 현재 구현·CI·브랜치를 확인한다.
2. 미커밋 변경사항을 확인하고 최신 `develop`에서 새 작업 브랜치를 만든다. 기존 변경사항을 임의로 덮어쓰거나 버리지 않는다.
3. 한 작업 단위로 구현·검증하고 관련 문서·설정 예시를 갱신한다.
4. 커밋·푸시는 사용자 요청 범위에 맞춰 수행한다. PR 대상은 `develop`이며, `main` 최종 반영은 별도로 검토한다.
5. 기능 브랜치는 작게 유지한다. 병합 후 삭제는 병합·보존 상태와 사용자 요청을 확인한 뒤 수행한다.

커밋과 PR 제목은 기존 `타입(영역): 요약` 형식을 유지한다. 요약은 한국어 50자 이내, 끝 마침표 없이 쓴다. 타입은 `feat`, `fix`, `refactor`, `style`, `docs`, `test`, `chore`, `data`를 사용한다. 문서와 해당 설정 변경이 서로 독립적이면 커밋을 나눈다. 본문이 필요하면 빈 줄 뒤에 변경 내용·이유를 적고 실제 GitHub Issue는 `#번호`로 연결한다.

본문 작업 `BE-07`, 계획서 Issue 식별자 `BE-I05`, GitHub 실제 Issue `#번호`는 서로 다르므로 보고에서 구분한다. 작업 상태는 To Do → Doing → Review → Done으로 기록하고, 영역·종류·필수/선택 우선순위를 표시한다. 현재 GitHub에서 관리하며 GitLab 이관 전부터 GitLab Issue를 사용해야 한다고 해석하지 않는다.

PR에는 변경 내용, 확인 방법·결과, 관련 이슈, 화면 변경 시 스크린샷을 적는다. 문서만 변경했으면 코드 검사 미실행 사유와 실제 문서 검증 결과를 적는다. 실행하지 않은 검사를 통과로 표시하지 않는다.

리뷰에서는 다음을 확인한다.

- API 필드·enum·경로와 공식/참고 지표 구분이 계약에 맞는지
- 출처·기준일·공간 단위·분모와 결측·판단 보류가 정확한지
- API 실패·빈 데이터·시간 초과 처리와 원시 예외 비노출
- 비밀정보·대표자명·상담 원문과 불필요한 식별정보가 코드·샘플·이력에 없는지
- 코드 변경에 필요한 로컬 실행·ruff·mypy·pytest 및 충돌 해결 여부

최소 1인 리뷰, Squash merge, 24시간 내 리뷰 응답은 PDF의 협업 제안이다. 팀 운영 기준 확정 시 적용하며, 이 문서 작성이나 커밋·푸시 요청을 승인·병합 요청으로 확대하지 않는다. 제출용 main 병합·태그는 팀 확인 후 별도 진행한다.

## BE·ETL 코드와 의존성

- 모듈·함수·변수·JSON 필드는 `snake_case`, 클래스·스키마는 `PascalCase`, 상수는 `UPPER_SNAKE_CASE`를 사용한다. DB 테이블은 복수형 snake_case로 작성한다.
- API 경로는 기존 `/api/...` 계약을 따른다. 함수·요청·응답에 타입을 명시하고 계산은 `app/analysis/`, 라우팅·비즈니스 로직·외부 호출은 기존 폴더 역할에 맞춰 분리한다.
- 계산 함수 docstring에는 분석 로직 정의서의 실제 절 번호와 지표 의미를 기록한다. 원문을 확보하지 못하면 임의 절 번호를 만들지 않고 확인 대기로 표시한다.
- 반경 기본값·최소 표본 수·시간 제한 등 기준값은 설정이나 명명된 상수로 관리한다. 비밀값만 환경변수에 두고 설정 상수와 구분한다.
- Python 3.11, ruff·mypy·pytest와 실행 의존성은 `pyproject.toml`에서 관리한다. 실제 도입 시 호환성을 검증한 직접 의존성 버전을 고정하고 로컬·CI가 같은 선언을 설치한다. 간접 의존성까지 재현하는 잠금 방식은 BE-01에서 선정·기록한다.
- 인코딩은 UTF-8, 줄바꿈은 LF, Python 들여쓰기는 4칸으로 한다. 포맷 도구는 ruff 하나로 유지한다.

## 보안·원본 보존·운영 로그

원본 보존은 분석에 필요한 원천 필드의 보존을 뜻한다. 대표자명·연락처·실제 상담 원문은 적재하지 않는다. CSV·API 응답 전체를 그대로 보관하기 전에 허용 필드 목록을 적용하고, 원본 좌표·날짜·업태 등 필요한 필드만 접근을 제한한 보관 계층에 남긴다. 기존 주소·좌표·점포 식별정보의 AI 외부 전송·로그 금지는 계속 적용한다.

API 키·DB 비밀번호는 서버 환경변수·배포 시크릿으로 관리한다. 키를 노션·단체방·PR 본문·출력에 공유하지 않는다. 비밀값은 승인된 비밀 전달 수단을 이용하고 문서에는 변수명·발급 여부만 기록한다.

`.env.example`에는 비밀값을 비워 두고 변수 설명을 적는다. 새 환경변수는 해당 변경과 같은 PR에서 예시도 갱신한다. 현재 예시에 있는 `LLM_PROVIDER`, `LLM_MODEL`, `APP_ENV`, `CORS_ORIGINS` 등 비밀이 아닌 기본값은 기존 BE 문서 기준으로 유지한다. 복사한 실제 `.env`는 Git에 포함하지 않는다.

외부 API 오류는 공통 오류 코드와 사용자용 메시지로 바꾸고, 공급자 원시 예외·응답 본문·인증 정보를 반환하지 않는다. CORS는 개발·배포에 필요한 명시적인 origin만 허용하고, 무조건 `*`로 개방하지 않는다.

ETL에는 배치 ID, 단계명, 입력·정상·제외·보완·실패 건수와 소요 시간을 기록한다. 제외 사유별 건수를 남기되 로그에 원본 행·주소·좌표·사업자·점포 식별정보를 출력하지 않는다. 중복 집계되는 검토 플래그 건수와 최종 제외 건수는 구분해 보고한다.

## API 표현과 데이터 출처

일자 필드는 `YYYY-MM-DD`, 월 필드는 기존 `YYYY-MM`, 시각 필드는 시간대가 포함된 ISO 8601을 사용한다. 분기는 확정할 API 계약 표현을 따른다. 거리 m, 면적 ㎡, 비율 %로 의미를 통일하고 각 필드 단위를 명세에 적는다. 비율을 0~1 값과 0~100 값 사이에서 임의로 바꾸지 않는다.

응답은 `{data, meta, error}`를 유지하고 지표 출처·적용 기준일/분기·공간 단위·분모를 명세의 해당 필드에 담는다. 실제 필드 구조가 미확정이면 보완 문서에 남기고 임의 이름을 배포하지 않는다. FastAPI 앱 구현 후 개발 서버 `/docs`에서 계약을 확인한다.

샘플은 `data/sample/`에 소량만 두고 실제·가상 여부, 원천 이름·링크, 추출/생성 기준, 기준일, 라이선스·이용 조건과 정제 제한을 함께 기록한다. 가상 점포·시연 숫자는 예시임을 명시한다. 데이터 출처·라이선스를 확인하지 못한 항목은 확인 대기로 남기고 출처 확보 완료로 표시하지 않는다.

## README·제출 준비

README에는 서비스 소개, 팀·역할, Python 환경, pyproject 설치·실행 명령, 환경변수 설명, 데이터 준비·ETL 순서, 샘플 재현 방법, 검증 명령을 작성한다. 사용 데이터·API의 출처표와 이용 조건, 테스트 목록, PDF/이미지 예시를 함께 준비한다.

유의사항에는 참고용 정보라는 점, 창업 성공·실패를 판정하지 않는다는 점, 사업주 역량 미반영과 시연 데이터 여부를 명시한다. 실제 제공하지 않은 데이터·검증을 완료한 것처럼 적지 않는다.

공공 GitLab 제출은 현재 FE·BE 별도 저장소 구조를 기준으로 준비한다. 대상 프로젝트·권한과 main 보호 등 운영 설정은 이관 시 별도 확인한다. 저장소 미러링과 Issue·PR·문서 이관을 구분하고, 기존 대상 이력을 덮어쓰지 않으며 제출 환경에서 재현 검증을 수행한다. 모노레포 전환은 이 작업의 범위에 포함하지 않는다.
