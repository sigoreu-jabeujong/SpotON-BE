# FE 연동 피드백 BE 재검증·조치 판단 보고서

- 작성일: 2026-11-13 (KST)
- 기준 코드: BE `develop`의 `3ed3f2f` / FE 로컬 `be01370`
- 범위: 사용자 전달 FE 연동 결과의 BE 측 재현·원천 대조·원인 분석·수정 방향 검토
- 상태: **Claude Code 2회 검수·Codex 최종 보완 완료(분석 보고서 범위). 런타임 코드 수정·DB 보정·클라우드 이전은 수행하지 않음. 전체 프로젝트 완료 판정이 아님.**
- 검토 대상: 한식 업종 혼입 의심, geocode 층 정보, 첫 조회 지연, 프랜차이즈 미확인, AI 문맥 PR 반영 상태

이 보고서는 수정 전 `3ed3f2f`에서 확인한 분석 기록이다. 이후 [#102 상세 위치 파서 수정 설계·검증](designs/feat102-address-place-floor-parser.md)에서 공통 파서와 새 ETL 변환 경로를 수정한다. 아래의 코드 미수정·회귀 검사 미추가 설명은 분석 당시 상태이며, 기존 DB의 NULL 상세 위치 보정은 후속 작업으로 남는다.

후속 진행: [#104 기존 상세 위치 복구](designs/feat104-floor-location-backfill.md)에서 원본 전체 대조·실제 Claude 검토·최종 코드 복제 리허설 후 현재 PC 개발 DB의 24,738행을 보정하고 이력·AI 문맥과 비위치 값 보존을 검증했다. 아래의 DB 미보정 설명은 분석 당시 상태다. 업종 품질·성능·브랜드 후속이나 다른 팀원의 독립 DB 적용까지 완료한 것은 아니다.

## 2. 확인 범위와 근거 수준

### 직접 확인한 것

- 로컬 Uvicorn `127.0.0.1:8000` + 실제 Kakao 주소 검색 + 실제 PostGIS 개발 DB를 사용했다.
- `양화로 45`, `세종대로 110`, `명동길 14`의 카페·한식 6개 조회 조합을 대조했다. 한식에는 `category=restaurant&sub_category=korean`, 반경에는 500m를 명시했다.
- geocode 결과의 `building_key`·좌표를 사용해 이력·주변·Risk·활동·조회 가능 기간·2025-11 시점 조회를 확인했다. geocode의 층 값을 그대로 전달한 이력 요청도 별도로 6건 확인했다.
- 최초 검증 집합은 실서버 geocode 15건·데이터 API 48건·geocode 층 값 그대로 전달한 이력 6건·지원 링크 2건으로 **71건 모두 200**이었다. 층/호 구분을 추가한 진단 재실행에서 geocode 3건·지원 링크 2건을 더 호출해 **실서버 총76건 모두 200**이다. 같은 조건의 반복 조회를 포함하며, 200은 의미까지 정확하다는 뜻이 아니다.
- 별도 앱을 조합별로 새로 만들어 Risk·활동 각 3회, 총 36건을 확인했다. 이 경우는 HTTP 네트워크가 없는 TestClient이며 DB는 실제 개발 DB다. 전부 200이었다.
- 카카오 후보를 1개/2개로 바꾼 합성 응답 6개로 파서 문제를 분리했다. 이는 실제 카카오 응답 검증과 구분한다.
- 원천 업태·층 정보·브랜드 근거는 `READ ONLY` 트랜잭션으로 조회했다. 조회 전후 stores 689,440·생활인구 관측 531,922·브랜드 매칭 6,839·migration0011은 같았다. 전체 행 hash 비교를 수행한 것은 아니다.
- 관련 기존 단위 검사 132개와 AI 해석 계약 검사 39개, 합계 **171개 통과**. 기존 Starlette TestClient deprecation 경고가 있다. 이 검사에는 지명 `중구`로 발생하는 새 결함의 회귀 사례가 없었다. 통합 테스트 묶음은 이번에 실행하지 않았다.

### 이번에 완료로 주장하지 않는 것

- FE 브라우저에서 입력→화면→PDF/이미지 저장 전체 흐름은 FE 담당자의 전달 결과다. 이번 BE 재검증에서 브라우저·인쇄·다운로드를 다시 실행하지 않았다.
- SpotON의 실제 AI 해석 모델 요청과 실서버 AI 엔드포인트 호출은 모두 0건이다. 사용자 PC의 키 미설정 503은 전달받은 결과이며, 이번에는 모의 공급자를 사용하는 기존 AI 계약 검사로 오류 처리 경로를 확인했다. 보고서 검수를 위한 Claude Code 2회 실행은 이 앱 검증 호출 수와 구분한다.
- 최초 OS/DB 페이지 캐시까지 비운 부하 시험, 운영 SLA, 다른 PC의 실행 계획, 최신 원천 API 재수집, 데이터 분류의 현장 사실 확인은 하지 않았다.
- `.env`·키·원천 비허용 개인정보는 보고서나 Claude 입력에 넣지 않는다. FE 파일은 수정하지 않는다.

이하 실제 HTTP·DB 조회는 직접 측정, 후보 수를 바꾼 응답은 합성 진단, 구 토큰 제거는 가정 실험이다. FE 브라우저 성공·사용자 PC의 AI503과 지연 수치는 전달 결과로 구분한다. 새 테스트나 수정안을 이미 구현한 것처럼 표시하지 않는다.

## 3. 한식 목록에 제외 업종처럼 보이는 상호가 나타나는 이유

### 재현과 DB 보존 원천 필드 대조

현재 DB의 `bzstat_nm`과 변환 코드를 대조했다. 외부 원천 API나 최초 CSV를 이번에 재수집·재대조한 것은 아니다.

| 위치·조건 | 현재 주변 점포 수 | 반환된 원천 업태 | 이름 키워드 검토 후보 수 |
|---|---:|---|---:|
| 양화로45·카페 | 77 | 커피숍 77 | 미집계 |
| 양화로45·한식 | 261 | 한식 261 | 10 |
| 세종대로110·카페 | 152 | 커피숍 152 | 미집계 |
| 세종대로110·한식 | 376 | 한식 376 | 9 |
| 명동길14·카페 | 187 | 커피숍 187 | 미집계 |
| 명동길14·한식 | 454 | 한식 454 | 17 |

키워드는 `치킨|통닭|주점|호프|분식|커피|카페|비비큐|bbq`의 대소문자 무관 검색이다. **17건은 이 진단식에 걸린 행 수이며 제보의 약18곳과 동일한 목록을 확정한 수가 아니다. 실제 제외 업종 수·순수 점포 수·지표 보정량도 아니다.** 같은 상호라도 원천 관리번호가 다르면 별도 행이다.

명동길14의 제보 표본은 다음과 같다. 거리 값은 현재 API가 표시한 값이다.

| 상호 | 원천 업태 `bzstat_nm` | 현재 분류 | 거리 |
|---|---|---|---:|
| 비비큐치킨 명동스타점 | 한식 | restaurant / korean | 46.6m |
| 인생주점 | 한식 | restaurant / korean | 216.0m |
| 틈새 커피점 | 한식 | restaurant / korean | 231.2m |

DB의 `category=restaurant, sub_category=korean`인 223,363행도 보존 원천 업태가 모두 `한식`이다. 이 집계에는 삭제·검토·날짜·반경 필터를 추가하지 않았으며, 서울 범위는 수집 당시 서울 관할 필터에 따른다. 현재 확인한 범위에서는 `통닭(치킨)`·`분식` 등 명시 제외 업태가 ETL에서 한식으로 잘못 변환된 근거는 발견하지 못했다.

### 코드와 정책 판단

- [normalize.py](../etl/localdata/normalize.py)의 `normalize_category()`는 명시 업태 `한식/중국식/일식/경양식`을 지원 업종에 매핑한다. 분식·호프/통닭·통닭(치킨)·감성주점 등은 제외한다.
- [pipeline.py](../etl/localdata/pipeline.py)는 원천 업태를 `stores.bzstat_nm`에 보존한다.
- 조회는 [store_cohort.py](../app/services/store_cohort.py)의 공통 업종 조건을 사용한다. 지금 보이는 사례는 **원천 업태 기준의 현행 정책과 실제 업종에 대한 사용자 기대 사이의 차이**다. 저장 매핑 오류와 구분하고, 제외 업종 정책이 실제 데이터에서 충족되는지는 별도로 검토한다.
- 치킨·주점 등 제외 범위는 유지하되, 상호 키워드만으로 실제 업종을 확정하거나 과거의 영업 형태까지 바꿔서는 안 된다. 예를 들어 카페처럼 보이는 상호를 곧바로 카페로 이동하지 않는다.

### 권장 수정 방향

1. `source+license_no`로 충돌 후보를 만들고 원천 업태·검토 근거·적용 규칙 버전·판정 상태를 **현재 집계에 즉시 영향을 주지 않는 별도 검토 레이어**에 보존한다. 기존 `category_review_flag`를 후보 표시용으로 바로 켜면 SUPPORTED_STORES와 브랜드 자동 판정에서 즉시 빠지므로 재사용하지 않는다.
2. 키워드는 검토 후보 생성에 사용한다. 검증된 원천·공식 자료·수동 확인 근거를 확보한 판정만 반영한다. 같은 이름의 모든 지점을 한꺼번에 바꾸지 않는다.
3. 원천 `bzstat_nm`을 덮어쓰지 않고, 확인된 제외/재분류 근거를 분리하는 방식을 설계한다. 인정 가능한 근거의 종류·기준 시점·충돌 해결·오탐 취소·판정 주체와 검증 절차를 먼저 확정한다. 현행 매핑을 변경해 후보/확인 판정을 실제 집계에 적용하는 것은 별도 설계·정책 확정 후의 단계다.
4. 실제 적용 시 이력·주변·시점·활동·Risk·서울 평균·AI 문맥·캐시·브랜드 근거가 같은 분류 판정을 사용하는지 함께 검증한다. 이력의 건물 내 지원 업종 전체와 주변의 업종·반경·시점 등 API별 모집단 계약은 유지하며 모든 count를 같게 만들지 않는다. 월별 모집단과 개업/폐업 분자·분모·서울 평균의 전후 차이를 산출한다. 명동길14 진단식에 걸린 주변 응답 17행을 빼는 것만으로 과거 개폐업률의 보정값을 만들지 않는다.
5. 현재 인허가별 상호는 최신 저장값이며 매월의 과거 업종을 보증하지 않는다. 현재 상호에 대한 판정을 개업 이후 전 기간에 자동 소급하지 않는다. 과거 적용 근거가 없으면 그 한계와 적용 범위를 명시한다.

아직 검토 후보를 DB에서 제거하거나 분류·지표를 변경하지 않았다. 기존 정책을 위반해 분류를 느슨하게 만드는 수정도 권하지 않는다.

## 4. 층 정보 누락: 공통 파서의 지명 오인

### 실제 주소 입력별 결과

| 요청 query | 결과 형태 | floor_unit |
|---|---|---|
| 양화로 45 2층 | 다중 후보 2개 | 2층 |
| 명동길 14 2층 | 단일 대표 응답, candidates=[] | 2층 |
| 세종대로 110 2층 | 단일 대표 응답, candidates=[] | 2층 |
| 서울 마포구 양화로 45 2층 | 다중 후보 2개 | 2층 |
| 서울 중구 명동길 14 2층 | 단일 대표 응답, candidates=[] | null |
| 서울 중구 세종대로 110 2층 | 단일 대표 응답, candidates=[] | null |

`candidates=[]`는 주소 0건이 아니라 최상위 data에 단일 주소가 있다는 뜻이다.

따라서 **이번 축약 주소는 후보 수와 무관하게 정상이고, `중구`를 포함한 전체 주소는 후보 수와 무관하게 null이었다.** FE 담당자의 원래 네트워크 요청 전문은 확보하지 않았으므로 모든 제보가 같은 입력 형태였다고 단정하지 않는다. 다만 동일한 표면 현상과 명확한 BE 원인을 실제 주소·독립 합성 응답으로 재현했다. 후속 재현 자료는 공개 예시 주소의 query·응답 필드·버전만 최소한으로 받고 인증 헤더·키·개인 주소를 포함한 전체 HAR는 받지 않는다.

### 원인

[floor_unit.py](../etl/address/floor_unit.py)의 `_candidate_failure()`에는 다음 조건이 있다.

```python
if token in _COMPLEX_FLOOR_TOKENS or token.startswith(("반지하", "옥탑", "중")):
    return FloorUnitFailure.AMBIGUOUS
```

`중`으로 시작하는 모든 토큰을 애매한 층 표현으로 처리하므로 `중구`, `중랑구`, `중앙로`도 거절된다. [kakao_local.py](../app/services/kakao_local.py)는 입력 query에서 먼저 층을 파싱한 뒤 같은 값을 각 주소 후보와 대표 응답에 전달한다. 후보 개수 분기에는 층 값을 지우는 코드가 없다.

합성 카카오 응답을 1개/2개로 바꿔도 마포 주소는 항상 2층, 중구 전체 주소는 항상 null이었다. 즉 후보 수는 원인이 아니다.

### 기존 적재값 영향

ETL도 같은 파서와 `reconcile_floor_units()`를 사용하므로 geocode만 고쳐도 기존 DB의 null은 복구되지 않는다. 아래는 **구 이름 토큰 제거 가정 실험이며 전체 영향 범위가 아니다.** 지원 업종·검토/삭제 제외 조건(`SUPPORTED_STORES`)의 행이고 날짜·반경 필터 적용 전이다.

| 범위 | 지원 행 | 현재 floor_unit null | 구 이름 토큰만 제거하면 상세 위치를 얻는 행 | 그중 건물 키 존재 |
|---|---:|---:|---:|---:|
| 중구 | 16,865 | 16,864 | 5,805 | 5,668 |
| 중랑구 | 9,367 | 9,367 | 2,289 | 2,263 |

진단은 보존 주소에서 정확한 `중구`/`중랑구` 공백 토큰만 제거하고 기존 파서를 다시 실행한 **가정 실험**이다. 중구의 5,805행은 층만4,750·층과호828·호만227, 중랑구의 2,289행은 층만1,733·층과호254·호만302다. 따라서 8,094행 전부가 층 정보를 얻은 것도 아니다.

8,094행은 전체 영향의 상한/하한·확정 보정 수·영업 점포 수·같은 자리 수가 아니다. 중계동·중곡동·중림동·중화동·중앙로처럼 다른 지명도 원인이 될 수 있고, 구 이름만 제거해도 동 이름 때문에 여전히 실패할 수 있다. **서울 전체의 관련 지명 토큰과 실제 수정 파서 기준 영향 집합은 아직 산출하지 않았다.** 이 변형을 정식 파싱 규칙으로 채택하거나 DB에 쓰지 않았다.

### 수정·완료 기준

- 지명 전체를 예외 처리하는 임시 삭제가 아니라, 실제 중간층 표현의 문법과 주소 영역을 구분하도록 좁힌다. 중구·중랑구·중앙로·중계동 등의 정상 주소 회귀 사례를 추가한다.
- 반지하·옥탑·단독 중·중 2층·중2층·중층·M층·메자닌의 모호성, 복수 층·호수·범위, 불법 상세 위치는 계속 거절한다. 정상 지명 뒤의 2층 및 2층 201호, 후보 1개/2개, 한쪽 주소만 실제로 모호한 도로명/지번 조합도 각각 검사한다. 기존 reconcile의 실제 모호성 우선 규칙을 완화하지 않는다.
- API 파서 수정과 기존 ETL 재처리를 별도 단계로 수행한다. 재처리의 출처·날짜·hash 보존 조건은 아래 절을 따른다. 현재는 실제 수정 파서와 백필을 구현하지 않았다.
- 이력·AI 문맥은 geocode의 floor_unit을 그대로 받는 경로와 null 생략 경로를 모두 확인한다.

### 재처리의 출처·날짜·규칙 보존 조건

- [runner.py](../etl/localdata/runner.py)는 `today=collection.collected_at.date()`로 변환하고, [provenance.py](../etl/localdata/provenance.py)는 원천 갱신일·수집 기준·원문 행 hash를 배치에 기록한다. **검증된 원래 스냅샷과 원래 collection.collected_at을 재사용**하고 재처리 날짜를 원천 기준일/수집일로 쓰지 않는다. 원본과 원래 변환 기준을 확인할 수 없으면 쓰기 단계는 중단한다.
- `update_reason`은 작업 사유 칸이 아니라 원천 날짜 오류 사유다. 현재 정상값 None과 실제 원천 갱신일을 보존한다. 보정 설명을 이 필드에 넣으면 current_provenance가 전체 조회를 500으로 막을 수 있다. 보정 사유는 별도 검증 기록으로 남긴다.
- 층 파서 자체에는 버전 상수가 없다. 별도 설계에서 `ETL_RULE_VERSION`의 정규화 규칙 버전 증가 등 실제 기록 위치를 확정한다. 업종 매핑이 그대로면 MAP_VERSION을 업종 변경처럼 사용하지 않는다. 원문이 같으면 `input_sha256`·`rows_sha256`은 보존하며, 이를 정제 결과 hash로 혼동하지 않는다.
- 우선 원천 단위 전체 staging/dry-run 대조를 설계한다. 구별 부분 재적재로 배치가 혼재하는 상태를 기본안으로 삼지 않는다. 정상화된 업무 열의 허용 차이는 `floor_unit`·`location_level`로 제한하고, 그 외 업무 열과 geometry의 hash·건수는 같아야 한다. 새 배치 ID·updated_at 등 예상 관리 열 변경은 별도 허용 목록으로 검증한다.
- 전체 재정제를 사용하는 경우 pyproj·PROJ·좌표 변환 grid 등 실행 환경도 고정해 기록한다. 원본 스냅샷과 현재 저장값의 비위치 업무 열·geometry가 일치하지 않으면 예전 값으로 덮지 말고 쓰기를 중단한다.
- `data_updated_at`·전역 reference·날짜 플래그·개폐업 날짜/상태·업종·비위치 지표와 서울 평균은 보존해야 한다. 동일 위치 판정과 그에 따른 이력/AI 문장은 의도한 변경 범위를 명시해 대조한다. 모든 지표가 무조건 같아야 한다고 요구하지 않는다.
- [assignment.py](../etl/brands/assignment.py)의 브랜드 입력 hash 대상은 source·license_no·name·category·sub_category·is_franchise·brand_id이며 floor와 batch는 포함하지 않는다. 위치 열만 고칠 때 활성 브랜드 근거 6,839건과 판정값이 유지되는지 확인한다. 소스 기반 규칙의 영향과 실제 쓰기 후 검증은 구분한다.
- 새 배치 ID·규칙은 data_version·캐시·AI 문맥을 바꿀 수 있다. 기존 배치 덮어쓰기나 캐시 강제 재사용 대신 새 버전으로 무효화되고 출처 조회가 정상인 것을 확인한다. 모든 전후 조건·rollback·유지보수 및 읽기 재개 검증을 통과한 뒤에만 명시적으로 적재한다.

### `unverified`가 정상인 경우

[store_history.py](../app/services/store_history.py)의 계약상 **요청과 저장 값이 모두 2층이어도 호실이 없으면 same_spot이 아니다.** 이 경우는 unverified다. 2층과 3층이 same_building이 되려면 요청 대상의 건물에 속한 저장 행이고 저장 location_level도 유효해야 한다. 층·호가 모두 일치하고 저장 신뢰 수준까지 충족하면 same_spot이다. 호만 있는 값 역시 위치를 확정하지 않는다.

따라서 층 파서와 재적재를 고친 뒤에도 호수 미상·원자료 결측 점포를 상세 위치 미확인으로 표시하는 것은 유지해야 한다.

## 6. 유명 브랜드의 프랜차이즈 정보 없음

- 현재 활성 브랜드 원천은 2025년 11,167행이다. 보유 brands의 `name ILIKE '%스타벅스%' OR normalized_name ILIKE '%starbucks%'` 검색 결과는 0행, 활성 자동 매칭 근거의 `name LIKE '%스타벅스%'`도 0행이었다.
- `SUPPORTED_STORES AND Store.name.contains('스타벅스')`의 부분 일치 점포는 762행이다. 날짜·상태·반경 필터 전이며 현재 영업 중 수나 서울 전체 최신 브랜드 지점 수를 뜻하지 않는다.
- 실제 양화로 주변의 `스타벅스합정메세나몰` 등은 원천 분류값과 자동 근거가 없어 franchise=unknown이었다.
- [catalog.py](../etl/brands/catalog.py)의 정규화는 NFKC·casefold·연속 공백 정리다. [matching.py](../etl/brands/matching.py)는 정규화 후 정확 이름·단일 후보·외식 업종만 허용한다. 지점명을 제거하거나 부분 일치시키지 않는다.
- [franchise.py](../app/services/franchise.py)는 외부 분류값을 우선하고, 현행 원문·업종과 유효한 근거가 일치할 때만 catalog_exact_name 추정을 반환한다. 목록 미일치는 개인 매장 확정으로 바꾸지 않는다.

**판단:** 현행 계약을 어긴 API 오류 근거는 없다. 이 사례는 목록에 기준 브랜드가 없는 상태와 보수적인 상호 일치 규칙의 적용 범위를 구분해야 한다. 목록에 없는 브랜드는 접미사 제거만으로 해결되지 않는다. DB에 적재된 2025 카탈로그 버전(11,167행)을 확인한 것이며, 원천 API 재수집이나 해당 기업의 계약 형태·전체 연도 등재 여부를 확인한 것은 아니다.

### 후속 방향

- 유명 브랜드 여부와 가맹 여부는 다른 의미로 유지한다. 알려진 체인이라는 이유로 franchise=true나 independent를 만들지 않는다.
- 지점명 제거·영문/한글 별칭은 근거가 있는 별도 alias 규칙과 오탐/충돌 회귀 검증 후 도입한다. 과거 실제 계약으로 소급하지 않는다.
- 직영 체인 표시가 제품에 필요하면 가맹 추정 필드와 구분되는 새 계약을 설계하고 FE 요청서로 전달한다. 현재 unknown의 의미와 원천 기준년도 안내는 유지한다.

## 8. 실행 순서와 완료 조건

1. **층 파서 결함:** 짧은/전체 주소·중구/중랑구·실제 모호 층·카카오 후보 수 회귀 검사를 만든 뒤 공통 파서를 수정한다. 기존 위치 보수성은 유지한다.
2. **기적재 층 값:** 검증 원본과 새 파서 규칙으로 읽기 전용 차이를 먼저 산출한다. 새 배치·내용 검증·명시적 쓰기 단계에서만 재적재하고 이력·AI 문맥을 다시 확인한다.
3. **업종 품질:** 의심 목록과 근거 있는 판정 레이어를 설계·검토한다. 실제 제외 판단과 지표 변화량을 제시한 뒤 공통 모집단으로 반영한다.
4. **성능:** 제보 PC 또는 실제 배포 대상의 동일 조건에서 SQL과 HTTP를 나눠 측정한다. 필요한 인덱스·통계·중복 집계를 근거로 개선한다.
5. **브랜드:** 현재 unknown을 유지하고 alias·체인 표시 확장이 필요한지 별도 범위로 결정한다.

후속 구현은 각각 이슈→브랜치→설계→Claude 검토→구현·테스트 순서로 진행한다. API 계약에 영향이 있으면 BE 측 FE 변경 요청서로 전달하며 FE 저장소는 직접 수정하지 않는다. 운영 DB 선택·이전은 이 검토와 분리해 보류한다.

## 9. 검수 기록

### Codex 초안

- 실제 HTTP·읽기 전용 DB·단위 검사·현재 소스·GitHub 병합 상태를 대조해 작성했다.
- 추정 키워드 수와 확정 제외 업종 수, 대표 단일 응답과 candidates 배열 길이, 앱 캐시와 DB 캐시, FE 전달 결과와 이번 BE 직접 검증을 구분했다.
- 실제 요청·측정 상세는 저장소 밖 임시 검증 파일에만 보관했다. 키·접속 URL·브랜드 원문 body는 포함하지 않는다.

### Claude Code 검토

Claude Code 2.1.322를 실제 CLI로 실행했다. 1차는 제공 보고서와 원인 코드 발췌에 대한 읽기 전용 검토로, 별도 DB·네트워크·파일 수정 도구를 사용하지 않았다. 1차 결과는 **수정 후 재검토**이며 다음을 반영했다.

1. 기존 재처리 계획에 원래 수집/변환 기준일·전역 reference·원문 hash·날짜 플래그·비위치 지표 보존을 추가했다. update_reason 오용·배치 혼재·캐시/AI 버전 변화를 명시했다.
2. 8,094행을 전체 영향 범위나 층 복구 확정 수로 표현하지 않고 상세 위치 가정 실험으로 좁혔다. 추가 측정에서 층만/호만/층·호를 분리하고 서울 전체 영향이 미측정임을 명시했다.
3. 업종 항목을 확정 ETL 결함에서 정책·품질 검토로 분리하고, 기존 category_review_flag로 후보를 즉시 집계에서 빼는 우회를 금지했다. 과거 모집단 소급과 월별 분자·분모 영향 검증을 추가했다.
4. 새 앱과 새 프로세스·캐시 계층·호출 순서·브라우저 경합의 차이를 명시하고, 모호한 층과 정상 지명의 인수 검사를 구체화했다.
5. Codex 재확인으로 runner가 원래 collection.collected_at을 today로 쓰고, 브랜드 입력 hash는 floor/batch를 포함하지 않는 점을 보강했다. 모든 지표 불변 요구 대신 비위치 지표 보존과 위치 지표의 의도한 변경을 분리했다.
6. FE #28~35의 병합은 실제 gh 출력에서 확인됐으므로 단순 미확인으로 바꾸지 않았다. 대신 요청서 전항목 반영과 브라우저 성공은 사용자 전달이며 이번 직접 검증과 다름을 명시했다.

### Claude Code 2차 검수·Codex 최종 점검

- 같은 Claude Code CLI를 별도로 다시 실행해 보완 보고서·1차 의견·추가 원인 코드와 검증 사실을 전달했다. 두 실행 모두 정상 종료했으며, 별도 DB/파일 수정 도구는 사용하지 않았다.
- 최종 판정은 **PASS FOR ANALYSIS**다. 이는 분석 보고서의 근거와 범위가 적합하다는 의견이며, 파서 수정·데이터 보정·성능 개선·운영 배포의 완료 승인이 아니다.
- Claude는 1차의 높은 지적사항인 재처리 provenance, 8,094행 범위, 업종 정책/결함 구분이 해소됐다고 판단했다.
- 경미한 추가 의견을 반영해 축약 주소의 정상 동작은 후보 수와 무관하다고 정리하고, 17건을 현재 영업 점포가 아닌 주변 응답 17행으로 고쳤다. 브랜드 카탈로그 확인 범위·캐시/SQL 제한 근거 링크·변환 환경 고정 조건도 보강했다.
- Codex는 분류 판정의 공유와 API별 모집단 계약을 구분하고, 앱 AI 호출 0건과 검수용 Claude 2회를 구분했다. 문서 상대 링크·수치 합계·공백·Git 변경 범위를 마지막으로 확인한다.
