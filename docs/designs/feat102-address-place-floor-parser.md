## 1. 문제와 목표

`etl/address/floor_unit.py::_candidate_failure()`의 `token.startswith("중")` 때문에 `중구`·`중랑구`·`중계동`·`중곡동`·`중림동`·`중화동`·`중앙로` 등 정상 지명이 AMBIGUOUS가 된다. `서울 중구 명동길 14 2층`은 null, 지명 없는 `명동길 14 2층`은 2층이다.

KakaoLocalService는 query에서 floor_unit을 한 번 파싱하고 같은 값을 대표 응답과 각 후보에 넘긴다. 후보 수는 원인이 아니다. 같은 파서가 ETL과 HistoryQuery/AI history의 정규화에도 쓰인다.

목표는 실제로 모호한 상세 위치의 거절을 유지하면서 지명 때문에 명시 층·호가 사라지지 않게 하는 것이다. 일반 입력의 정규화·부정확 상세 위치 보호·모든 날짜/좌표/업종 계약은 유지한다.

## 2. 변경 범위

### 2.1 공통 파서

- 지명을 삭제하거나 행정구역 사전을 하드코딩하지 않는다.
- `중` 전체 접두사 검사를 실제 상세 위치 문법으로 좁힌다.
- 독립 `중`·`중간`·`중층`·`중간층`은 모호한 표현으로 유지한다.
- `중층...`·`중간층...` 및 `중2층`, `중2F`, `중201호`, `중간2층`처럼 `중[간] + 숫자 + 층/F/호`로 시작하는 상세 위치 토큰은 계속 모호하게 처리한다. 기존보다 잘못된 중간층을 일반층으로 받아들이지 않는다.
- (Claude 검토 반영) `중[간]` 바로 뒤가 상세 위치 문법의 시작인 토큰도 모두 모호로 유지한다: 숫자, `B/b`, `F/f`, `층`, `제`, `지하`, `지상`, 구분자(`,` `/` `-` `·` `~`). 예: `중B1`, `중지하1층`, `중제2층`, `중2-3층`, `중,2층`, 그리고 `중2 층`처럼 공백으로 층 표지가 분리돼 `_combine_tokens`가 합치지 못하는 `중2`. 이들은 현재 `중` 접두사 규칙으로 AMBIGUOUS인데, `숫자+층/F/호`만 보는 초안 정규식으로는 무시(NO_DETAIL 기여)되어 `중B1 101호`·`중2 층 201호`·`중,2층 201호`가 `101호`/`201호` 단독 값으로 **새로 수용**된다. 이는 의도하지 않은 수용 확대이므로 금지한다.
- 최종 구현안(구현 재검토 보강, 8.3절): `_MIDDLE_DETAIL_RE = re.compile(r"중(?:간)?(?:[^가-힣]|층|제|지하|지상|지층|반지하|옥탑|옥상|메자닌)")`를 두고 `match`(접두 일치)로 인식한다. 1차 설계의 열거된 구분자 외에도 `.`, `:`, `_`와 알려진 복합 층 표현을 보수적으로 거절한다. `_COMPLEX_FLOOR_TOKENS`에 `중`/`중간`/`중간층`을 명시 추가하고(`중층`은 기존 유지), `startswith` 접두사 목록은 `반지하`/`옥탑`만 남긴다. 정규식 검사는 NFKC 정규화 이후 토큰에 적용되므로 전각 숫자·문자도 동일하게 걸린다.
- 이 규칙으로 `중구`·`중랑구`·`중계동`·`중곡동`·`중림동`·`중화동`·`중앙로`·`중앙로2길`·`중랑천로14길`·`중계1동`은 더 이상 모호가 아니다. 반면 `중2로`처럼 `중` 직후가 숫자인 토큰은 기존과 동일하게 모호로 남는다(현재 동작 유지이며 회귀가 아님, 실제 서울 지명 사례도 확인되지 않음).
- 지명이 상세 위치에 붙어 쓰인 `중앙상가2층` 같은 토큰은 수정 후 다른 일반 지명(`대한상가2층`)과 동일하게 무시된다. 이는 `중` 지명에만 있던 우연한 거절이 사라지는 것이며 별도 신규 정책을 이 PR에서 만들지 않는다(기존 공통 한계로 기록).
- 이미 존재하는 NFKC·최대 길이·금지 문자·괄호·범위·건물 동·유닛 불법 문법·중복/충돌 검사와 도로명/지번 reconcile 순서는 유지한다.

### 2.2 ETL 규칙 버전

파싱 결과가 달라질 수 있으므로 `etl/localdata/provenance.py`의 `ETL_RULE_VERSION`을 `localdata-normalization-v1`에서 `localdata-normalization-v2`로 증가시킨다. 업종 매핑을 바꾸지 않으므로 MAP_VERSION은 유지한다.

새로 적재하는 배치에만 새 정규화 버전이 기록된다. 과거 배치 metadata를 UPDATE하지 않으며 이 PR은 ETL 쓰기·과거 재처리를 실행하지 않는다. 원문 해시(input_sha256/rows_sha256)는 입력이 같다면 그대로다. 원천 갱신일·collection.collected_at·runner의 today 선택은 바꾸지 않는다.

(Claude 검토 반영) 버전 증가의 부수 효과 점검 항목:

- 구현 전 저장소 전체에서 `ETL_RULE_VERSION`과 문자열 `localdata-normalization-v1`의 사용처(테스트 기대값, fixture, 스냅샷, 재적재 skip/동일 배치 판정, 캐시 키, AI history 버전)를 검색해 목록을 PR에 기록한다. 버전 비교로 재적재를 건너뛰거나 v1 일치를 요구하는 로직이 있으면 이 PR 범위에서 동작을 바꾸지 말고 보고한다. migration·DB CHECK 제약에 버전 문자열이 박혀 있다면 범위 밖이므로 버전 증가 자체를 보류하고 판단을 요청한다.
- 버전 증가는 파서 변경과 같은 커밋에 둔다(파서만 바뀐 상태의 v1 배치가 생길 수 있는 중간 커밋 금지).
- 버전 증가 후 DB에는 v1 배치 행과 v2 배치 행이 섞인다. 행 단위 출처는 batch_id로 추적되므로 이는 정상이며, v1 행의 NULL 상세 위치는 별도 보정 작업의 대상이다(이 PR에서 backfill 요구하지 않음).
- geocode 응답은 버전 필드가 없어 같은 질의의 `floor_unit`이 null→값으로 바뀐다. 공개 schema·nullable은 동일하므로 계약 변경은 아니나, PR 설명에 "값 변화(동일 schema)"로 명시한다.

### 2.3 회귀 검사

1. 순수 파서: 정상 지명 + 층만/층·호/호만, 상세 위치 없는 지명, 중간층/반지하/옥탑/불법/충돌 표현, 혼합 문자열의 fail-closed. (Claude 검토 반영) 최소 포함 사례:
   - 수용: `서울 중구 명동길 14 2층`→`2층`(same_building), `서울 중랑구 테스트로 1 2층 201호`→`2층 201호`(same_spot), `서울 중구 명동2가 1-1 B1`→`B1`, `서울 노원구 중계1동 1 201호`→`201호`(same_building), `서울 중구 중앙로2길 3 3F`→`3층`.
   - 상세 없음: `서울 중구 명동길 14`, `서울 중랑구 중랑천로14길 5` → NO_DETAIL (기존 AMBIGUOUS에서 바뀌는 실패 유형임을 테스트 이름/주석에 명시).
   - 모호 유지: `중`, `중간`, `중층`, `중간층`, `중 2층`, `중간 2층`, `중2층`, `중2F`, `중201호`, `중간2층`, `중B1`, `중지하1층`, `중제2층`, `중2-3층`, `중2 층 201호`, `중,2층 201호`, `중B1 101호`, `서울 중구 명동길 14 중2층`(지명은 정상이어도 중간층은 거절), 기존 `반지하 1층`·`옥탑`.
   - 불변식(결정적 차등 테스트): 대표 상세 문자열 집합 X에 대해 `parse_floor_unit("서울 중구 테스트로 1 " + X) == parse_floor_unit("서울 마포구 테스트로 1 " + X)`. 지명 접두가 결과를 바꾸지 않음을 직접 고정한다.
   - 도로명/지번 reconcile: 도로명 `서울특별시 중구 … 2층`, 지번 `서울특별시 중구 명동2가 … 2층 201호` → AMBIGUOUS(기존 충돌 규칙 유지), 지번에 상세가 없으면 도로명 값 수용.
2. 서비스·라우터: 실제 문제 주소의 1개/2개 카카오 합성 응답에서 대표와 후보의 floor_unit이 동일함을 확인. 실제 외부 호출은 별도 읽기 검증으로 구분한다.
3. ETL 변환: 중구/중랑구 등 도로명·지번 주소를 변환해 building_key·층·호·location_level을 확인. 날짜·업종·좌표·원문 보존과 명확한 모호 표현의 reconcile 거절을 확인.
4. 출처: 동일 원본으로 만든 배치의 normalization-v2·기존 map version·원천 기준일·raw row hash 보존을 검사한다.
5. 격리 PostGIS: 새 변환 결과를 일회용 테스트 DB에 upsert해 공간/업종/출처와 상세 위치 저장을 확인하고, 같은 층만으로 same_spot을 만들지 않는 이력 규칙도 연결 검증한다. 개발 DB를 통합 테스트 대상으로 사용하지 않는다.
6. (Claude 검토 반영) 질의·저장 비대칭 구간: 이 PR 이후 기존 DB 보정 전까지 `중`구 등 주소는 **질의 측**(geocode/HistoryQuery)에서는 floor_unit이 생기지만 **저장 측** 기존 행은 `floor_unit=NULL`, `location_level=unverified`로 남는다. 질의 `2층 201호` + 저장 NULL/unverified 조합이 same_spot은 물론 "층이 다름(same_building)"으로도 판정되지 않고 기존 unverified/건물 단위 판정에 머무는지 테스트로 고정한다. 저장 수준이 same_building인 행과 질의 층·호 일치 시에도 same_spot으로 승격되지 않음을 함께 확인한다.
7. ETL 품질 집계: 영향 주소의 `floor_unit_ambiguous` 카운트가 `floor_unit_ok`/`floor_unit_no_detail`로 이동하는 것은 의도된 변화다. 집계 수치를 고정한 기존 테스트가 있으면 기대값 변경 사유를 테스트에 남긴다.

## 3. 변경하지 않는 계약

- 공개 API 요청/응답 schema, 오류 envelope/status, `floor_unit` 필드명·nullable·기존 canonical 값.
- building_key·category·좌표·후보 정렬/최대5개·원문 주소/키 비노출.
- 같은 층만 확인되면 unverified, 층이 다르고 저장 신뢰 수준이 유효하면 same_building, 층과 호가 모두 일치하고 저장 수준이 same_spot일 때만 same_spot.
- actual same_spot/위치 판정의 신뢰 수준을 parser의 추출 성공만으로 끌어올리지 않는다.
- DB 모델·migration0011·SQL 및 3초 제한, 실제 .env·Docker 설정, FE 저장소.
- 업종 정책·브랜드 alias/가맹 추정·성능 구조·생활인구/매출 pending·AI prompt.

기존 API 구조가 같으므로 FE 타입·FE CLAUDE.md 변경은 필요하지 않다. BE CLAUDE.md와 작업계획에는 파서 및 기존 DB 보정 미완료 경계를 기록한다.

## 4. 기존 데이터와 배포 경계

이 수정은 geocode의 새 요청과 새 ETL 변환에 적용된다. 이미 저장된 null 값은 자동으로 바뀌지 않는다.

이전 보고서의 8,094행은 중구/중랑구 토큰 제거 가정 실험의 상세 위치 후보이며 실제 수정 파서의 전체 영향 수나 보정 확정 수가 아니다. 실제 기존 데이터 보정은 원래 검증 원본·원래 기준일을 확보한 별도 작업에서 수행한다.

해당 후속은 원천 전체 dry-run, 변경 열 허용 목록(floor_unit/location_level 및 새 batch 관리 열), 나머지 업무/geometry hash·기준일·날짜 플래그·비위치 지표·브랜드 근거 보존, 출처/캐시/AI 버전 변경 검증과 통제된 유지보수 절차를 요구한다. 이 PR을 기존 데이터 복구 완료로 표시하지 않는다.

## 5. 실행·검증 계획

- 수정 전 새 회귀 검사의 실패를 확인하고, 최소 파서 변경 후 통과시킨다.
- `ruff check .`, `ruff format --check .`, `mypy app etl migrations`, 일반 pytest 전체를 실행한다.
- CI와 같은 PostGIS17-3.7 이미지의 별도 로컬 테스트 컨테이너로 통합 묶음을 실행한다. 테스트 fixture가 만든 spoton_it_ 임시 DB/role만 사용한다.
- 실제 Kakao 읽기 검증은 축약/전체 주소 3곳의 층 전달을 확인한다. 키는 Settings에서 로컬로 사용하고 출력·커밋·Claude 입력에 넣지 않는다. 실제 LLM은 호출하지 않는다.
- 개발 DB에 DML/DDL/ANALYZE/VACUUM은 하지 않는다. DB 읽기 확인을 수행하면 변경 전후 head·행 수·검증 범위를 명시한다.
- staged diff·비밀값·범위·문서 링크를 확인하고 지정 PR 양식으로 develop에 제출한다. CI/저장소 조건 통과 후 기존 사용자 지시대로 정상 Squash 병합한다. main·보호 규칙 우회·수동 브랜치 삭제는 하지 않는다.

- 검토 방식: 이 설계 문서를 Read로 직접 읽고, 사용자가 제공한 소스 발췌(`etl/address/floor_unit.py`, `etl/localdata/provenance.py`, `app/services/kakao_local.py`, ETL pipeline 발췌, 관련 테스트 3종)와 대조했다. 명령 실행·테스트 실행·DB/브라우저 접근·.env/키 열람은 하지 않았다. 아래 동작 분석은 코드 읽기에 기반한 추론이며 실행 검증이 아니다.
- 이 문서 외 파일은 수정하지 않았다.

### 7.1 확인된 사항 (동의)

1. 원인 진단이 정확하다. `_candidate_failure()`는 층·호로 정규화되지 않은 모든 토큰에 대해 `token.startswith(("반지하", "옥탑", "중"))`를 검사하므로 `중구`·`중랑구` 등 정상 지명 토큰 하나가 주소 전체를 AMBIGUOUS로 만든다. 지번 주소도 같은 지명을 포함하므로 `reconcile_floor_units`에서 양쪽 모두 모호가 되어 ETL에서도 같은 손실이 난다.
2. `KakaoLocalService.geocode()`는 `_floor_unit(query)`를 한 번 계산해 모든 후보에 같은 값을 넘기므로 후보 수는 원인이 아니라는 판단에 동의한다.
3. `FloorUnitValue.location_level`(층과 호가 모두 있어야 same_spot), pipeline의 `building_key` 부재 시 unverified 강등, 이력 비교의 저장 신뢰 수준 요구는 이 설계에서 바뀌지 않는다. 파서 수정이 신뢰 수준을 끌어올리는 경로는 없다.
4. 지명 사전 하드코딩 금지, 결정적 정규식 기반 수정, API schema/모델/migration/FE/클라우드 설정 무변경, 기존 DB backfill을 이 PR 범위에서 제외한 경계가 적절하다.

### 7.2 발견 사항과 문서 수정 내역

1. **[중대] 초안 정규식의 의도하지 않은 수용 확대.** 초안 `중(?:간)?[0-9]+(?:층|[Ff]|호)`는 `중B1`, `중지하1층`, `중제2층`, `중2-3층`, `중,2층`, 공백 분리된 `중2 층`의 `중2`를 잡지 못한다. 이 토큰들은 현재 AMBIGUOUS인데, 수정 후에는 아무 실패도 기여하지 않아 함께 쓰인 `101호`/`201호`가 단독 값으로 수용된다(`_split_chunks`는 `중,2층`을 분리하지 않고, `_combine_tokens`는 숫자만인 토큰만 결합하며, `_INVALID_SUFFIX_RE`는 한글 접두 토큰에 fullmatch되지 않기 때문). → 2.1절에서 `중[간]` 직후가 숫자/`B`/`F`/`층`/`제`/`지하`/`지상`/구분자이면 모호로 유지하는 정규식으로 교체했다. 정상 지명(`중앙로2길`, `중계1동`, `중랑천로14길`)은 `중` 직후가 한글이므로 영향받지 않는다.
2. **[보통] 회귀 사례 부족.** 위 우회 사례, 지명+중간층 혼합(`서울 중구 … 중2층`), 지명 접두가 결과를 바꾸지 않는다는 차등 불변식, reconcile 충돌 사례를 2.3절 1항에 추가했다.
3. **[보통] 질의·저장 비대칭 구간.** backfill 전까지 질의 측은 층·호를 얻고 저장 측 기존 행은 NULL/unverified다. 이 조합이 same_spot이나 "층 다름" 판정으로 이어지지 않음을 테스트로 고정하도록 2.3절 6항을 추가했다.
4. **[보통] 버전 증가의 부수 효과.** `ETL_RULE_VERSION` v2 증가에 동의하되, 사용처 전수 확인·재적재 skip 로직/DB 제약 존재 시 보류·같은 커밋 원칙·v1/v2 혼재 명시를 2.2절에 추가했다. `MAP_VERSION` 유지에 동의한다.
5. **[경미] 실패 유형 이동.** 상세 없는 `중구` 주소는 AMBIGUOUS→NO_DETAIL로 바뀌어 ETL 품질 집계가 이동한다. 의도된 변화로 2.3절 7항에 기록했다.
6. **[경미] 기술 정정.** 초안의 "`중2로`에는 규칙이 적용되지 않는다"는 수정 정규식 기준으로 틀리다. `중2로`는 기존처럼 모호로 남으며 이는 회귀가 아니라 현행 유지임을 2.1절에 명시했다. `중앙상가2층`처럼 붙어 쓴 토큰은 다른 지명과 같은 공통 한계로 기록했다(이 PR에서 새 정책 없음).

### 7.3 남은 우려 (구현 시 확인)

- `ETL_RULE_VERSION` 사용처는 제공 발췌만으로 전부 확인할 수 없었다. 구현 시 검색 결과를 PR에 남긴다.
- HistoryQuery/AI history의 비교 코드는 이번 검토 입력에 없어 7.2-3의 비대칭 판정은 설계 문구(3절)에 근거한 요구사항이다. 실제 코드가 저장 NULL을 "층 다름"으로 취급한다면 이 PR에서 비교 로직을 바꾸지 말고 보고 후 판단한다.
- 5절의 실제 Kakao 읽기 검증은 병합 조건이 아닌 보조 확인으로 두고, 질의 주소·응답 body를 로그/커밋에 남기지 않는다.
- 기존 DB 보정은 이 PR 범위 밖이며 PR 설명·작업계획에 "미완료"로 명시해야 한다(4절 유지).

### 7.4 설계 판정

**조건부 승인.** 7.2의 수정(특히 1번 정규식 교체와 우회 사례 회귀 테스트)을 반영한 현재 문서 기준으로 Codex 구현을 진행해도 된다. 구현이 초안 정규식(`숫자+층/F/호`만 검사)으로 돌아가거나, `ETL_RULE_VERSION` 사용처에서 migration/DB 제약·재적재 skip 의존이 발견되면 구현을 멈추고 재검토한다.

## 8. Codex 최종 판단·구현·검증

### 8.1 검토 반영과 변경 범위

- Claude가 수정한 정규식을 채택했다. 정상 `중` 지명은 통과시키되 `중B1`, `중2 층 201호`, `중,2층 201호` 등 모호한 상세 표현은 계속 거절한다. 잘못된 입력 뒤의 호수만 수용하는 우회를 막는다.
- `ETL_RULE_VERSION`은 파서 수정과 같은 커밋에서 v2로 변경했다. app/etl/migrations/tests 전체 검색 결과, production 사용처는 `etl/localdata/provenance.py`의 상수 선언과 `import_batch()` 대입뿐이다. v1 문자열에 의존하는 DB 제약·재적재 skip·AI 캐시 키는 발견하지 않았다. 신규 검사는 v2를 기대한다. MAP_VERSION은 유지했다.
- 기존 `location_match()`를 읽고 검사했다. 저장 NULL/unverified 또는 same_building만 있는 행은 질의 층·호가 명확해져도 same_spot으로 승격하지 않는다. 비교 로직은 수정하지 않았다.
- API의 값 변화는 같은 schema 안의 null→명시 상세 위치다. 기존 DB 재처리·실데이터 쓰기·FE 변경·모델/migration 변경은 하지 않았다.

### 8.3 잔여 작업과 후속 경계

- 실제 Claude Code CLI의 읽기 전용 구현 재검토는 PASS였다. 소스 기반 판단이며 Claude가 테스트·DB를 직접 실행한 것은 아니다. Codex는 다음 경미한 지적도 반영하기로 했다.
  - 1차 검토 정규식에서 빠진 `중.2층`·`중:2층`·`중_2층`·`중M층`·`중지층`·`중반지하`·`중옥탑` 등도 모호하게 유지한다. Claude의 제안대로 `중[간]` 뒤가 한글 음절이 아닌 경우와 알려진 복합 층 표현을 포괄한다. 최종 정규식은 `중(?:간)?(?:[^가-힣]|층|제|지하|지상|지층|반지하|옥탑|옥상|메자닌)`이며 NFKC 후 match한다. 정상 지명의 통과와 기존 fail-closed 의도를 유지하기 위한 보강이다.
  - `3F`→`3층`, 정상 ETL의 ambiguous 집계 0, 지명+실제 모호 표현의 ETL reconcile 거절, 실제 DB 저장 규칙 v2를 추가 검사한다.
  - 공통 파서를 쓰는 HistoryQuery에서 `floor_unit="중구 2층"`은 기존 422 대신 `2층`으로 정규화될 수 있다. 다른 정상 지명을 포함한 상세 입력과 일관되는 의도된 변화다. 요청 schema와 일반 오류 코드/형식은 같지만, 이 수정 대상 입력의 수용 결과까지 불변이라는 뜻은 아니다.
- 위 보강 후 Codex의 전체 단위/통합·실제 Kakao·정적 검사·최종 diff·변경 범위·비밀값·문서 링크 확인을 통과했다. 최종 파서와 테스트를 다시 읽고 같은 장소의 신뢰 수준·출처 불변 경계를 확인했다. 테스트용 컨테이너만 정리하며 PR/CI·병합 기록은 #102에 연결된 PR을 따른다.
- 기존 DB 상세 위치 보정은 별도 이슈·원본 검증·유지보수 절차가 필요하다. 현재 PR 병합만으로 기존 NULL 행을 복구했다고 안내하지 않는다.
- 한식 원천 분류/상호 불일치, 첫 조회 지연, 공정위 미등록 브랜드는 선행 보고서의 판단과 보류 경계를 유지한다. 상호만으로 업종을 제외하거나 브랜드 미일치를 개인 매장으로 확정하지 않는다.
