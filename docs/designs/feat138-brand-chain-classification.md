- 요청/이슈: [BE #138](https://github.com/sigoreu-jabeujong/SpotON-BE/issues/138)
- 작성일: 2026-11-15 KST. BE 코드 기준: `origin/develop`의 `43878f7`. FE 계약 읽기 대조: FE `origin/develop`의 `4bf012f` (`diagnosis.ts`, `api/params.ts`, `utils/storeDisplay.ts`).
- 범위: 현행 진단, 데이터 요구사항, BE/FE/API/ETL 개편 설계, Claude Code 두 차례 검수 및 최종 재검토. 이번 작업은 문서만 변경한다.
- 상태: **설계 작성·Claude Code 1/2차 검수·Codex 최종 재검토 완료**. 검수 기록은 15절. 사용자 정책·점포 근거·서비스 승인 확인과 실제 구현/검증/운영 적용은 후속이다.

## 1. 제안과 사용자 목표

스타벅스·파스쿠찌·코코이찌방야·본죽 같은 기업 브랜드의 점포를 찾거나 제외하려면 현행 `is_franchise` 하나로 판정하는 구조를 **브랜드·체인 소속 판별**로 확장해야 한다. 공정위 목록과 정확한 상호 비교는 보조 근거로 유지하고, 공식 브랜드 매장 목록·검증된 별칭·점포 주소와 시간 근거를 결합한다.

권장 화면 명칭은 **브랜드·체인점**이다. 가맹점과 직영점을 모두 포함하는 브랜드 소속과 개별 점포의 운영 형태를 분리한다. `법인이 운영한다`는 이유만으로 단독 식당을 체인점으로 분류하지 않는다. 개인사업자가 운영하는 가맹점도 브랜드·체인점에 포함될 수 있다. 카드 결제의 ‘가맹점’과 프랜차이즈 계약의 ‘가맹점’도 구별한다.

이번 요청의 기본 해석은 **기업이 조직적으로 운영·관리하는 외식 브랜드 네트워크 소속 점포를 가맹/직영에 관계없이 선별**하는 것이다. 기업 규모·법인 여부로 단독 매장을 제외하거나 지역 소규모 체인을 제외하는 정책은 아직 결정하지 않았다. 체인의 점포 수를 임의로 2개/5개 이상으로 정해 자동 판정하지 않는다. 브랜드 운영 주체와 네트워크 근거를 확인해 등록하며, 경계 사례는 사용자 답변 후 정책 버전을 확정한다.

사용자에게 필요한 정보는 문서와 검수를 마친 뒤 14절의 최소 질문으로 요청한다. 답변 전에도 데이터 모델·읽기 전용 진단·충돌 검토 기반 설계는 진행할 수 있다.

### 1.1 반드시 분리할 세 축

| 축 | 의미 | 허용 값/처리 |
|---|---|---|
| 브랜드 소속 | 해당 인허가 기록과 특정 브랜드 네트워크의 관계 | `confirmed`, `estimated`, `non_chain_confirmed`, `unknown`, `conflict` |
| 점포 운영 형태 | 해당 점포를 본사가 직접 운영하는지 계약 사업자가 운영하는지 | `direct`, `franchised`, `licensed`, `unknown`, `conflict` |
| 사업자 성격 | 실제 점포 운영자의 법인/개인 여부 | 필요 시 별도 근거로만 관리. MVP 필터에서 제외 |

`licensed`는 명시된 라이선스 운영 근거가 있는 별도 형태이며 국내 가맹 법적 관계로 자동 변환하지 않는다. 브랜드의 가맹사업 등록 여부는 별도 `franchise_registry_status`이고 점포 운영 형태와 다르다. 네트워크 자체의 직영/가맹 혼합 운영은 브랜드 속성으로 기록할 수 있으나, 어느 매장이 어느 형태인지 모르면 점포 값은 `unknown`이다.

### 1.2 목표와 완료의 한계

- 네 브랜드를 우선 등록 대상으로 삼고, 동일 구조로 다른 기업 외식 브랜드를 확장한다.
- 지도·주변 점포·과거 조회·활동·Risk·AI가 같은 판정 버전과 명시한 시간 의미를 쓴다.
- 미매칭을 개인 매장으로 치환하지 않고, 실제 브랜드 소속/운영 형태 확인과 상호 기반 추정을 구별한다.
- ‘모든 프랜차이즈 100% 검출’은 보장하지 않는다. 원천에 없는 점포·과거 소속·브랜드 전환·미지원 업종은 별도 결측으로 공개한다.
- API로 실제 가맹 계약 여부를 전수 확인하는 시스템은 별도 점포 단위 자료 없이는 구현할 수 없다.

## 2. 실제 코드·DB 진단

### 2.1 확인 방법과 모집단

2026-11-15 로컬 개발 DB에서 SQLAlchemy 연결의 `REPEATABLE READ, READ ONLY`와 SQL 제한 45초를 사용했다. `transaction_read_only=on`을 확인하고 종료 시 rollback했다. 원천 API 재수집·DB 쓰기·서비스 재시작·운영 DB 접근은 하지 않았다. 재현 자료는 저장소 밖 `SpotON-private-backups/brand-chain-design-20261115/audit.py`, `audit.json`이다. 키·인허가번호·사업자번호·대표자·전화번호는 결과에 포함하지 않았다.

| 항목 | 읽기 전용 확인값 |
|---|---:|
| stores 전체 인허가 기록 | 689,440행 |
| `SOURCE_SUPPORTED_STORES` | 355,835행 |
| 상호 제외 정책까지 적용한 `SUPPORTED_STORES` | 338,905행 |
| 활성 공정위 카탈로그 | 2025년, 11,167행 |
| 해당 카탈로그 수집 관측 시각 | 2026-11-12 15:51:54 KST |
| 활성 매핑 실행의 저장된 정확 일치 후보 | 6,839행 |
| 활성 실행의 기존 외부 분류 보유 | 0행 |

6,839는 매핑 실행에 저장된 인허가 행 수이며 현재 영업 중 실제 매장 수·정답 수·전국 체인점 수가 아니다. 카탈로그 11,167도 복합 식별자로 보존한 원천 행 수이며 독립된 실브랜드 수가 아니다. 현재 DB가 2026년 전체 최신 원천을 수집했다는 뜻도 아니다.

상호 검색어는 스타벅스=`스타벅스|starbucks`, 파스쿠찌=`파스쿠|pascucci`, 코코이찌방야=`코코이찌|코코이치|cocoichibanya|coco ichibanya`, 본죽=`본죽`이다. 대소문자 무시 부분 문자열로 **감사 후보**를 뽑았다. 이름이 비슷한 타 점포가 섞일 수 있고 다른 표기는 놓칠 수 있다. 이 검색 자체는 신규 분류 규칙도 정답셋도 아니다. 삭제 표시 없는 행을 대상으로 하고, 지원 업종 열은 source·category·sub_category·category_review_flag 조건을 다시 적용했다. 영업/폐업 전체 이력을 포함하고, 반경·시점·면적·좌표 필터는 적용하지 않았다.

### 2.2 요청한 네 브랜드의 누락 근거

| 대상 | 상호 후보 전체 | 지원 업종 후보 | 활성 목록에서 해당 검색어 행 | 현재 자동 추정 true | 지원 후보의 탈락 사유 |
|---|---:|---:|---|---:|---|
| 스타벅스 | 925 | 762 | 0 | 0 | 762 `no_exact_candidate` |
| 파스쿠찌 | 238 | 152 | 0 | 0 | 152 `no_exact_candidate` |
| 코코이찌방야 | 45 | 37 | 1 | 2 | 35 `no_exact_candidate` |
| 본죽 계열 | 498 | 368 | 본죽/본죽&비빔밥 2행 | 4 | 319 `no_exact_candidate`, 45 `weak_name` |

표의 숫자는 인허가 기록 수다. ‘지원 업종 후보’는 `SOURCE_SUPPORTED_STORES` 기준이며 이름 제외 정책 적용 전이다(본죽 43행 포함, 2.3절). 나머지 상호 후보(스타벅스 163·파스쿠찌 86·코코이찌방야 8·본죽 130행)는 업종 미매핑(`None/None`) 또는 삭제·검토 대상이라 현행 분석 모집단 밖이다. ‘현재 자동 추정 true’는 활성 실행의 `exact_name_candidate` 행이며, 본죽 계열 4행은 정규화 상호가 `본죽&비빔밥`과 정확히 같은 행이다(`본죽` 자체는 `weak_name`). 모든 후보가 공식 브랜드 점포인지 아직 심사하지 않았으므로 이를 재현율·누락 매장 확정 수로 사용하지 않는다. 목록 검색 0은 **이 활성 2025년 스냅샷에서 해당 표기를 찾지 못했다**는 사실이다. 파스쿠찌에 가맹사업이 없거나 공정위의 모든 연도 자료에 없다는 결론이 아니다. 향후 다른 연도·브랜드 변경 이력·공식 운영 주체 자료와 대조해야 한다.

- **스타벅스**: 현행 카탈로그 밖 브랜드를 추가하는 별도 등록 경로가 필요하다. 공식 매장 검색은 브랜드·점포 연결 근거의 출처 후보이며, 자동 수집 여부는 9.3절 이용 조건 확인 후 정한다(확인 전에는 수동 확인/제공 파일). 이 설계는 국내 체인 포함을 목표로 하며, 해외 운영 방식이나 모든 시대의 점포 형태를 일괄 확정하지 않는다.
- **파스쿠찌**: `파스쿠찌`, `카페파스쿠찌 서울시청점`, `(주)파리크라상 파스쿠찌 광화문점` 같은 표기가 있다. 카탈로그 보강과 검증된 별칭·법인 접두사 처리가 모두 필요하다. 공식 사이트의 가맹 안내는 브랜드 차원의 가맹사업 근거이며 특정 점포의 가맹 계약 증빙은 아니다. [파스쿠찌 공식 사이트](https://www.pascucci.co.kr/index.asp)
- **코코이찌방야**: 목록에는 `BRD_20100100189 / JNG_000555`, 외식/서양식으로 존재한다. `(주)농심 코코이찌방야 광화문LX빌딩점` 등 법인명·지점명이 붙으면 정확 일치하지 않는다. 브랜드 업종 ‘서양식’만 보고 모든 인허가 기록을 양식으로 바꾸면 안 된다. 후보의 현행 DB 세부 업종은 일식 20/한식 8/양식 7/중식 2행으로 분산된다. 업종 정정은 점포별 원천 근거를 갖춘 별도 과제다.
- **본죽**: `BRD_20080100243`, 본죽&비빔밥=`BRD_20141221`로 다른 브랜드 행이다. 본죽은 영숫자 두 글자라 기존 `weak_name`(정규화 후 영숫자 3자 미만) 규칙에 걸려 정규화 상호가 사실상 `본죽` 단독인 후보 45행이 탈락한다(`weak_name`은 정확 비교 이전 단계라 카탈로그에 `본죽`이 있어도 후보가 되지 않는다). 전체 짧은 이름 방어를 없애지 않고 **승인된 짧은 별칭**으로 해결한다. 활성 카탈로그에서 두 행은 같은 가맹본부 관리번호 `JNG_018965`를 갖는다. 이는 카탈로그상 같은 본부라는 사실이며 두 브랜드를 하나로 합치거나 법적 관계를 추론할 근거가 아니다. canonical 관계(같은 본부)는 기록하되 개별 brand identity를 유지한다. 공식 사이트도 구별해 안내한다. [본아이에프 브랜드·매장 안내](https://www.bonif.co.kr/)

### 2.3 브랜드 로직 외의 누락: 상호 제외와 업종 범위

`app/services/store_scope.py`의 `store-name-keywords-v1`은 음식점 상호에 `cafe`, 카페, 커피 등 제외 키워드가 들어가면 분석에서 제외한다. 위 본죽 지원 후보 368행 중 **43행**이 이 조건에 걸린다. 예: `본죽&비빔밥 cafe 종로1가점`. 이 43행이 모두 유효 분석 업종인지는 아직 검수하지 않았다.

`SOURCE_SUPPORTED_STORES`를 쓰는 브랜드 후보 배치는 이 행들을 조사할 수 있지만 API `SUPPORTED_STORES`는 제외할 수 있다. 그러므로 ‘브랜드를 찾았는데 화면에 없다’를 전부 브랜드 미매칭으로 설명하면 안 된다. 카테고리 미지원/검토 대상, 이름 제외, 시간/영업일 결측, 좌표 없음, 면적 조건, 브랜드 결측을 서로 다른 사유로 측정해야 한다.

이번 설계의 기본은 기존 업종 범위를 유지하는 것이다. 브랜드 등록으로 분식·치킨·주점 등 기존 제외 업종을 우회하지 않는다. 본죽 43행도 자동 복구하지 않는다. 별도 점포별 업종 검토 후 예외가 필요하면 `store-scope` 정책 버전을 증가시키고 모든 분모·캐시·과거 비교를 같이 검증한다. 브랜드명 전체 화이트리스트로 이름 제외를 무조건 해제하지 않는다.

### 2.4 기존 구조에서 유지할 장점과 교체할 제약

| 코드 | 현재 동작 | 개편 방향 |
|---|---|---|
| `etl/brands/catalog.py` | NFKC·casefold·공백 정규화, 연도/브랜드번호/본부번호 원천 보존 | 수집·무결성 검증 유지, canonical brand를 별도로 둠 |
| `etl/brands/matching.py` | 정확한 전체 상호만 비교, 3글자 미만 차단, 반복 번호/동명이인 격리 | 승인 별칭과 점포 연결을 추가, 충돌 방어 유지 |
| `etl/brands/assignment.py` | 원천 stores를 덮어쓰지 않고 증거 실행 세대 저장 | 증거 불변·원자적 공개 전환을 재사용 |
| `app/models/brand.py` | 현재 `brands`는 카탈로그 행, 재수집 세대마다 다른 내부 ID 가능 | 영속 canonical identity와 혼용 금지 |
| `app/services/franchise.py` | 기존 외부 `is_franchise/brand_id` 우선, 이후 활성 exact-name 증거 파생 | legacy는 보존, 새 소속/운영 증거를 별도 해석 |
| 같은 파일 `automatic_match()` | 현재 source/license/name/category/subcategory 튜플이 일치해야 증거 유효 | 새 주소·시간·공간 근거도 사용 시 입력 지문에 추가 |
| FE 필터 | 프랜차이즈(추정)/개인 매장, 선택 시 unknown 제외 | 브랜드·체인/비체인 확인/미확인과 추정 여부 명시 |

현행 `franchise=franchise`는 `include_unknown_franchise=true`이면 미확인도 포함한다. `independent`와 unknown 제외는 명시적 `is_franchise=false`만 포함하므로 현재 자료에서는 거의 비어 보일 수 있다. 미매칭 전부를 false로 채워 해결하면 안 된다. 기존 외부 `brand_id`만 있고 bool이 null이면 유효 bool도 null일 수 있으므로 이 ID의 존재만으로 새 소속·운영 형태를 확정하지 않는다.

### 3.2 최소 자료 형식

브랜드 등록용 CSV/JSON은 `brand_key, display_name, country, operator_name, network_basis_url, observed_at, valid_from, valid_to, temporal_precision, source_record_id, franchise_registry_refs[]`를 가진다. 미확인 효력일은 null로 두며 관측일을 개점/계약 시작일로 쓰지 않는다. 원천 ID가 없으면 내부 생성 ID라는 것을 명시한다.

별칭 파일은 `brand_key, alias, language, alias_kind, match_mode, scope, evidence_url, observed_at, valid_from, valid_to, reviewer, decision`을 가진다. `alias_kind=official|approved_variant|legal_prefix|former_name`, `match_mode=whole_name|approved_branch_pattern|review_only`. 전역 단어 삭제·전역 부분 문자열은 허용하지 않는다.

점포 근거 파일은 `provider, provider_outlet_id, brand_key, outlet_name, branch_name, address_road, address_jibun, floor_unit, lat, lng, source_status, source_reference_date, observed_at, valid_from, valid_to, temporal_precision, operation_type, operation_basis_url`을 가진다. 없는 컬럼은 null, 좌표계/주소 기준은 manifest에 기록한다. `operation_type`은 근거가 없으면 unknown이다. 원천의 대표자·회원·연락처·사업자번호는 판별에 필수로 요구하지 않는다.

## 4. 판정·필터의 의미

### 4.1 소속 판정

| 값 | 공개 의미 | 필요한 근거 |
|---|---|---|
| `confirmed` | 특정 브랜드 소속 확인 | 신뢰 가능한 점포 단위 공식 근거와 인허가 기록의 동일 점포 연결, 시간 적용 가능성 확인 |
| `estimated` | 브랜드 소속 추정 | 승인된 브랜드/별칭 규칙과 일관된 점포 후보, 실제 소속 확인에는 부족. 기존 exact-name 증거도 여기에 해당 |
| `non_chain_confirmed` | 해당 시점 비체인 확인 | 점포 단위의 명시적인 비체인 근거와 검수. 자료 부재/브랜드 미검색은 근거가 아님 |
| `unknown` | 판별 자료 부족/만료 | 미매칭·적용 기간 모름·기록 변경·연결 불가 |
| `conflict` | 유효한 증거가 상충 | 복수 브랜드 연결·기관/수동 근거 충돌. 후보 보존, 확정 필터에서 제외 |

숫자 confidence를 임의로 0.9/0.95로 부여하지 않는다. 규칙 ID·근거 등급·판정 사유로 설명하고, 점수가 필요하면 별도 정답셋으로 보정한다. 매칭률이 높아지는 것만으로 품질이 좋아졌다고 판단하지 않는다.

### 4.2 브랜드 선별 계약 제안

새 계약에서 다음 조건을 정규화한 하나의 서버 predicate로 사용한다.

- `brand_scope=all|chain|non_chain` (기본 all)
- `brand_unknown=include|exclude` (기본 include. FE에서 chain/non_chain을 선택할 때 명시적으로 exclude 전송)
- `brand_evidence=confirmed_only|include_estimates` (권장 초기값 include_estimates, 화면에 ‘추정 포함’ 표시)
- `operation_type=any|direct|franchised|licensed|unknown` (기본 any, 2단계 기능)

`C`=confirmed, `E`=estimated, `N`=non_chain_confirmed, `U`=unknown 또는 conflict. `brand_evidence=confirmed_only`에서는 E를 필터상 U로 취급하되 반환된 원래 status를 unknown으로 덮어쓰지 않는다. conflict는 UI에서 구별하고 unknown 그룹 포함 시에만 조회한다.

| brand_scope | unknown=exclude | unknown=include |
|---|---|---|
| all | C+N+(허용된 E) | C+N+E+U 전체 |
| chain | C+(허용된 E) | C+(허용된 E)+U 및 미허용 E |
| non_chain | N | N+U 및 미허용 E |

‘브랜드·체인만 보기’의 권장 조합은 `chain/exclude/include_estimates`이며 추정이 섞임을 표시한다. ‘확인된 체인만’은 `chain/exclude/confirmed_only`다. 체인을 제외하면서 많은 미확인 점포를 보려면 `non_chain/include/include_estimates`를 사용하고 화면에는 **체인 제외 · 미확인 포함**이라고 표시한다. 이를 전부 ‘개인 매장’으로 부르지 않는다. 미확인 포함을 켜면 chain 선택에도 미확인이 나타나므로 상태별 수와 안내를 반드시 제공한다.

운영 형태는 브랜드 소속 조건과 **AND**다. unknown은 자동 포함하지 않고 `operation_type=unknown` 선택 시 근거 없음/충돌을 표시한다. 예를 들어 `chain+franchised`는 실제 가맹점 운영 근거가 있는 브랜드 소속 점포만 포함하고, 브랜드의 가맹 등록이나 지역 집계만으로 운영 형태를 채우지 않는다. `non_chain+direct|franchised|licensed`는 상충하는 요청으로 422를 제안한다. `non_chain_confirmed`에는 위 운영 형태 확정을 저장하지 못하도록 무결성 검사한다.

위 enum은 전체 목표 계약이다. 초기 v2는 `operation_type=any`, `brand_time_basis=observed_record`만 지원하며 나머지는 기능 미지원 사유를 붙인 422로 거절한다. 미지원 모드를 빈 결과로 대신하지 않는다. 운영 형태와 as_of를 각각 활성화할 때 계약 버전/capabilities를 갱신하고 FE에서 그때만 선택지를 연다.

**기존 증거가 새 상태로 들어오는 규칙(진리표 입력 정의)**. v2 상태는 아래처럼만 만든다. 빈칸 해석으로 legacy 값을 새 상태로 승격하지 않는다.

| 입력 | v2 소속 상태 | 사유 코드 |
|---|---|---|
| 현행 활성 실행의 exact-name 일치(`automatic_match()`와 같은 튜플 유효성) | E | `legacy_exact_name_estimate` |
| 승인 별칭/지점 패턴만 일치 | E | `approved_alias_name_estimate` |
| 공식 점포 근거 + 동일 기록·시간 연결 검수 | C | `official_outlet_link` |
| legacy `is_franchise`/`brand_id`만 있음(새 증거 없음) | U | `legacy_external_unverified` |
| legacy true(해석 가능한 브랜드 ID 없음) + 새 C/E | 새 증거의 상태 그대로(C 또는 E) | 새 증거의 사유. legacy는 보조 기록만 하며 E를 C로 승격하지 않음 |
| legacy `brand_id`만 있고 namespace를 해석할 수 없음 + 새 C/E | 새 증거의 상태 그대로 | 새 증거의 사유 + `legacy_external_unverified` 보조 기록. 해석 불가 ID를 충돌 근거로 쓰지 않음 |
| legacy false + 새 C/E | conflict | `source_conflict` (6.3절) |
| 새 증거와 legacy true가 다른 브랜드를 가리킴 | conflict | `source_conflict` |
| 위 어느 것도 없음 또는 지문 불일치 | U | `no_brand_candidate`/`stale_store_input` |

현행 `Matcher.classify()`는 외부 분류가 있는 행을 `existing_classification`으로 먼저 빼므로 legacy exact-name 증거와 legacy 외부 분류는 같은 run에서 공존하지 않는다. 공존은 run 이후 stores 변경이나 새 별칭/점포 증거에서만 생긴다. 첫 행은 해당 catalog 행에서 canonical brand로의 승인된 source link가 존재할 때만 E다. 이 연결은 세대마다 바뀌는 catalog 내부 bigint `brands.brand_id`가 아니라 `(reference_year, management_no, headquarter_no)` 원천 복합키로 한다. 연결되지 않은 원천 identity나 brand ID namespace는 추정 브랜드를 임의 생성하지 않고 U/검수로 보낸다. 표는 상충 증거 확인이 우선인 논리 규칙이며 SQL CASE의 첫 일치 순서로 그대로 구현하지 않는다. legacy bool=true 자체에는 브랜드 identity가 없으므로 ‘다른 브랜드’ 충돌은 별도 해석 가능한 ID/근거가 있을 때만 성립한다.

**N의 현실적 공백**. 2.1절 기준 legacy 외부 분류는 0행이고, 점포 단위 비체인 근거를 만드는 자료 경로는 MVP에 없다. 따라서 MVP의 `non_chain/exclude` 결과는 0건이 정상이며, 이는 ‘비체인 점포 없음’이 아니라 ‘비체인 확인 자료 없음’이다. v2 meta는 상태별 카운터로 N=0을 공개하고, FE는 N 생성 경로가 생기기 전까지 `non_chain/exclude`를 기본 선택지로 노출하지 않는 것을 권장한다(‘체인 제외 · 미확인 포함’만 노출).

같은 공백이 C에도 있다. 1단계(11절)는 C를 만들지 않으므로 그 기간의 `brand_evidence=confirmed_only` + `chain/exclude` 결과도 0건이 정상이다. meta는 C=0과 ‘확정 근거 경로 미활성’을 공개하고, FE는 C 생성 경로가 생기기 전까지 ‘확인된 체인만’을 기본 선택지로 노출하지 않는다.

이는 초기 보유 자료 기준이다. 승인 파일에 명시적인 비체인 근거가 들어오면 N 생성 경로를 검수해 활성화할 수 있다. 그런 입력을 금지하거나 N이 영구히 0이라고 가정하지 않는다.

### 4.3 시간 의미

브랜드 자료의 기준연도, 관측 시각, 소속 효력 기간, stores 인허가 개폐업 기간을 별도 보존한다. 기간은 `[valid_from, valid_to)`로 통일하고 정밀도를 `day|month|year|observed_only|unknown`으로 기록한다. 월/연도만 있는 근거를 임의 일자로 확정하지 않는다.

권장 MVP는 기존 시간 의미와의 호환성을 위해 `brand_time_basis=observed_record`를 사용한다. 현재 확보한 증거가 **해당 인허가 기록의 브랜드 소속을 어떻게 설명하는지**를 뜻하며 과거 T의 소속을 보장하지 않는다. UI는 ‘확보된 브랜드 정보 기준, 과거 소속 미확인’을 표시한다. 현재 점포 명부와 폐업 기록은 상호/주소가 같아도 시간 연결 불가 시 confirmed로 연결하지 않는다.

진정한 과거 소속 필터 `brand_time_basis=as_of`는 2단계다. 점포별 유효 기간 근거가 있을 때만 사용하고 T 시점 증거가 없으면 unknown이다. 연간 브랜드 등록으로 1월~12월 모든 점포 소속을 채우지 않는다. 같은 인허가번호로 상호·브랜드가 변경되면 과거 이름을 완전 복원할 수 없다는 한계를 유지한다.

활동 분석의 12개월/연도별 지표는 MVP에서 하나의 관측 기록 분류를 전체 코호트에 적용하고 이 한계를 설명한다. 기간별 소속으로 멤버십을 움직이는 방식은 분모·생존율 정의까지 바뀌므로 별도 설계/정책 버전으로 진행한다. 과거 분석에 현재 체인만 적용하면 생존 편향이 생길 수 있다.

## 5. 매칭 파이프라인

### 5.1 처리 순서

```text
공식 원천/승인 파일 → 불변 스냅샷·범위 검증
  → 원천 브랜드와 canonical brand 연결 → 승인 별칭/충돌 사전
  → 인허가 기록 후보 생성 → 공식 점포 후보와 주소·시간 대조
  → confirmed / estimated / unknown / conflict 및 사유 산출
  → dry-run 차이표 → 검수 승인 → 불변 공개 세대 생성
  → active generation 원자적 전환 → 공통 조회 predicate → FE/AI
```

1. 브랜드 identity를 먼저 확인한다. 공정위 `브랜드번호+본부번호+연도`는 원천 식별자이며 canonical brand와 별도 매핑한다. 반복 번호의 이유를 추론해 합치지 않는다. 운영자 변경은 유효 기간이 있는 관계로 관리한다.
2. 원상호는 그대로 보존한다. NFKC/casefold/공백 정리는 정규화 필드에서만 수행한다. 기호·괄호 제거·한영 변환·법인 접두사 제거는 브랜드별 승인 규칙에서만 사용하고 원문과 변환 내역을 함께 저장한다.
3. 전체 상호가 승인 별칭과 같거나 승인된 지점명 패턴을 충족하면 후보를 만든다. 본죽처럼 짧은 별칭은 승인 목록에서만 후보 생성하고 이름 단독으로 confirmed 승격하지 않는다. `본죽&비빔밥`처럼 더 구체적인 별칭을 먼저 시도하되 복수 유효 후보는 검수한다.
   - `approved_branch_pattern`은 정규화 상호 **전체**가 `[승인된 법인 접두사]? 별칭 [구분자]? 지점표지`에 고정(anchored) 일치할 때만 성립한다. 지점표지는 `…점`/`…지점`/괄호 안 지점명처럼 브랜드별로 승인한 형태이며, 별칭 뒤에 다른 한글 음절이 바로 붙는 승인 외 결합(`본죽이네`, `스타벅스커피숍` 등)은 `review_only`다. 짧은 별칭(영숫자 3자 미만)에 지점명을 붙이는 패턴은 공백·괄호 등 명시 구분자가 있는 경우만 허용하고 구분자 없는 결합은 검수로 보낸다. 승인된 짧은 별칭과 전체 이름이 정확히 같은 `본죽`은 별도 `whole_name` 규칙으로 후보가 될 수 있다. `&` 뒤 복합 브랜드명은 일반 지점 구분자가 아니라 본죽&비빔밥의 더 구체적인 별칭으로 먼저 처리한다.
   - `…점`으로 끝난다는 것만으로 지점표지가 되지 않는다. 지점명 본문은 다음 중 하나라도 해당하면 `review_only`다. (1) 일반 업종·형태 접미(`전문점`, `분식점`, `음식점`, `커피숍` 등), (2) 위치 설명어(`옆`, `앞`, `맞은편`, `근처`), (3) 다른 승인 별칭이나 활성 카탈로그 브랜드명, (4) 메뉴·식품명. 예를 들어 `파스쿠찌옆분식점`, `스타벅스커피전문점`, `본죽 비빔밥 강남점`은 E가 아니라 검수 대상이다. `본죽 비빔밥 강남점`은 본죽&비빔밥과의 혼동 때문이다. 감사 예시 `코코이찌방야홍대와이즈파크점`, `(주)파리크라상 파스쿠찌을지로입구점`, `본죽&비빔밥용산후암점`처럼 3자 이상 별칭 뒤에 구분자 없이 지점명이 붙는 형태는 위 제외에 걸리지 않을 때만 패턴 후보가 된다. 이 형태의 채택/검수 비율은 dry-run 차이표에 별도 열로 둔다.
   - 브랜드별 거부 목록(denylist)을 별칭과 같은 승인 버전으로 관리한다. 위 일반 제외어 목록도 같은 버전에 포함한다. 거부 목록 변경도 정책 버전 증가 대상이다.
   - 이 규칙의 결과는 최대 `estimated`다. 감사 후보(2.2절)의 키워드는 이 문법이 아니며, 별칭 문법 승인 전 dry-run에서 후보 대비 채택/거부/검수 수를 비교해 오탐 사례를 정답셋(10.1절)에 넣는다.
4. `브랜드+지점명+도로명/지번 건물+가능한 상세 위치+시간`으로 공식 점포와 대조한다. 주소 변환은 기존 주소 파서와 좌표계 검증을 재사용한다. 좌표 거리 하나, 같은 건물 하나, 업종명 하나만으로 확정하지 않는다.
5. 법인 접두사는 본사 관계가 확인된 형태만 해당 브랜드 범위에서 처리한다. `(주)` 제거로 검색 후보가 늘어나도 법인 여부·직영 형태를 추론하지 않는다.
6. 영문·띄어쓰기·기호·과거 이름 변형은 승인된 별칭으로 해결한다. 오타/유사도/fuzzy는 검수 후보 생성만 허용한다. LLM·임베딩으로 최종 분류나 자동 음성 판정을 하지 않는다. 외부 모델 없이 MVP 구현 가능하다.
7. 공식 점포 단위 근거와 인허가 기록의 동일성·시간이 확인되면 confirmed. 승인 상호 패턴만 충분하고 점포 근거가 없으면 estimated. 다중 후보/상충은 conflict. 목록에 없으면 unknown이다.

### 5.2 충돌·예외

- ‘본죽’이 포함된 독립 상호, 유사 이름, ‘스타벅스 옆’ 설명, 식품명/메뉴명을 상호로 오인하는 경우는 검수한다. 전역 `contains()`를 최종 판정으로 쓰지 않는다.
- 백화점·푸드코트·같은 건물의 복수 지점은 층/호/지점명과 실제 운영 기간을 추가 대조한다. 현재 원천이 부족하면 동일 주소라도 확정하지 않는다.
- 인허가 갱신으로 하나의 물리 점포에 여러 license 기록이 있을 수 있다. 원본 기록을 합치거나 경쟁업체 수를 새로 중복 제거하지 않는다. 기존 지표 단위는 인허가 기록이며, 물리 점포 entity는 별도 참조다.
- 공식 매장 하나와 인허가 여러 기록의 연결은 관계와 유효 기간을 저장한다. 같은 시점 활성 중복은 자동 1:1 선택 금지. 샵인샵/복합 브랜드는 다중 관계를 보존하고 MVP 단일 주브랜드가 확정되지 않으면 conflict 처리한다.
- 단종/폐점으로 현재 명부에서 사라졌다고 예전 소속을 부정하지 않는다. 원천 누락·일시 실패·범위 축소를 삭제로 해석하지 않는다.
- 상가정보와 Kakao가 동일 상위 원천을 공유할 수 있다. 두 검색 결과라는 이유만으로 독립 증거 2개로 점수를 올리지 않는다. 증거 계보를 남긴다.

### 5.3 사유 코드 제안

`official_outlet_link`, `approved_alias_name_estimate`, `legacy_exact_name_estimate`, `no_brand_candidate`, `short_alias_not_approved`, `ambiguous_alias`, `multiple_outlets`, `source_conflict`, `address_mismatch`, `temporal_unverified`, `stale_store_input`, `expired_evidence`, `explicit_non_chain_evidence`, `legacy_external_unverified`.

상태와 사유는 분리한다. 판정 대상 아님은 `out_of_scope` 진단 카운터로 관리하고 비체인으로 저장하지 않는다. 운영자 도구에는 검토 이유와 후보 비교를, 일반 사용자에게는 상태·브랜드명·기준일·간단한 근거 유형을 제공한다.

| `brand_operators` / `brand_operator_relations` | 운영 조직과 브랜드 관계, 국가·기간·출처. 사업자 성격은 점포 운영자와 구별 | 후속, 초기에는 증거 메타데이터로 보존 |
| `brand_outlets` / `outlet_source_links` / `outlet_license_links` | 물리 점포 entity, provider namespace별 ID, 인허가 기록 연결과 유효 기간 | 후속, 초기 공식 점포 ID는 evidence 원천 ref로 보존 |

**projection 모집단과 크기**. projection은 이름 제외 전 `SOURCE_SUPPORTED_STORES`(355,835행)를 판정 모집단으로 생성하고, 조회 시 기존 `SUPPORTED_STORES`/코호트 조건과 AND한다. 이름 제외 정책만 바뀌고 매칭에 쓰인 필드가 같다면 브랜드 결과를 재사용할 수 있지만, publication에 조회 정책 버전을 기록하고 API/캐시 버전은 갱신한다. 이름 제외 사유와 브랜드 미확인 사유를 분리 계측한다. 모든 행에 U를 저장하면 세대당 약 36만 행이 되므로 작은 DB에서는 C/E/N/conflict만 저장하는 희소 방식을 기본으로 한다. 행 수만으로 저장 불가능이라고 단정하지 않고 9.3절에서 실제 크기를 측정한다. publication 상태가 없을 때의 `pending`과 행 부재의 U는 반드시 구별한다(7.1절). 새로 적재된 stores 행은 다음 세대 전까지 행 부재=U다.

MVP부터 점포 단위 증거의 주소/지점/시간은 있어야 한다. 후속 entity 테이블을 만들지 않았다는 이유로 이름만 보고 confirmed로 승격하지 않는다. Projection은 원본 증거와 결정으로 재생성할 수 있어야 한다.

### 6.2 제약과 버전

- `brand_key`는 canonical UUID다. 기존 bigint `stores.brand_id`와 신규 canonical ID를 같은 필드나 FK로 재사용하지 않는다. 공정위 catalog의 내부 brand_id도 영속 브랜드 ID가 아니다.
- source record key에 provider·스냅샷/기준연도를 포함한다. 별칭은 전역 unique name 하나로 묶지 않는다. 동일 범위/기간의 중복 별칭은 review conflict다.
- `confirmed|estimated`는 brand_key 필수, non_chain_confirmed는 brand_key 없음+명시적인 음성 근거 필수. unknown/conflict는 단일 확정 brand_key를 공개하지 않고 후보는 별도 evidence에 보존한다.
- 점포 운영 형태 `direct|franchised|licensed`는 자체 근거·기간이 필수다. 소속 근거에서 자동 복사하지 않는다. 유효한 운영 형태가 특정 브랜드 소속을 필연적으로 입증하는 자료라면 두 축의 근거 연결을 검수해 기록한다.
- 같은 publication/record/time basis에서 조회 결과는 하나여야 한다. 과거 구간형 판정은 겹침 방지 제약과 시간 경계 검사를 추가한다. canonical brand 합병/분리는 기존 ID 삭제 대신 관계/승계와 새 projection 세대로 처리한다.
- 읽기 최적화는 `(generation, source, license_no)` unique 및 상태/brand_key 인덱스, evidence source ref 인덱스를 후보로 둔다. 모든 원문 JSON에 GIN을 먼저 만들지 않는다. EXPLAIN·실제 저장 크기로 선정한다.
- 입력 지문에는 실제 판정에 쓴 상호·주소·층호·좌표·업종·삭제/검토 상태·개폐업/상태·원천 배치와 관련 외부 분류를 포함한다. 사용하지 않은 칼럼으로 과도한 재계산을 유발하지 않되, 매칭에 사용한 필드 누락은 허용하지 않는다.
- ETL 세대 전환 후 API는 현재 stores의 지문/검증된 관련 필드를 대조한다. 불일치면 새 판정은 unknown/stale로 취급한다. 요청마다 모든 주소를 비싼 문자열 hash로 계산하지 않도록 ETL이 별도 지문 projection을 관리하거나 비교 열을 저장한다. 정확한 방식은 병합·갱신 경합 테스트와 계획 분석 후 확정한다.

### 6.3 기존 외부 분류 충돌

기존 외부 bool/brand_id는 데이터 소유권을 보존한다. true도 점포 가맹 운영 형태 확정의 증거인지 확인 전에는 신규 `franchised`로 복사하지 않는다. false도 실제 ‘비체인’ 근거인지 확인해야 한다. 새 소속 confirmed와 legacy false가 충돌하면 legacy API는 기존 규칙을 유지하고 새 계약은 `conflict` 또는 검수된 명시적 결정으로 처리한다. 조용히 우선순위를 뒤집거나 원본을 덮어쓰지 않는다.

## 7. API·공통 조회 설계

### 7.1 호환 경계

기존 `/api`의 `franchise=all|franchise|independent`, `include_unknown_franchise` 의미는 유지한다. 새 기능은 **별도 계약 `/api/v2`**로 제안한다. 실제 FE와 계약 확정 전 v1 파라미터를 v2 의미로 바꾸거나 같은 응답 필드에 direct/chain 값을 넣지 않는다.

v2 요청은 다음처럼 표현한다. URL은 아직 구현되지 않은 제안이다.

```text
GET /api/v2/stores/nearby?lat=37.57&lng=126.98&radius=500
    &category=restaurant&sub_category=korean
    &brand_scope=chain&brand_unknown=exclude&brand_evidence=include_estimates
    &brand_time_basis=observed_record&operation_type=any
```

v2에서는 legacy `franchise`, `include_unknown_franchise`, legacy `include_unknown`을 받지 않고 422로 명시 거절한다. 면적 결측은 기존 별도 `include_unknown_area`로 유지한다. v1에서 v2 필드를 보내도 조용히 무시하지 않도록 명시적으로 검증한다. 이는 현재 무시될 수 있는 미지의 query 인자를 422로 바꾸는 v1 동작 변경이므로, 구현 전 현행 v1 파서의 unknown 인자 처리를 확인하고 FE 요청서에 명시한다.

**v1 고정과 사용자 체감 시점**. v1은 현행 exact-name run(`brand_mapping_state`)만 계속 읽고 새 publication을 읽지 않는다. 따라서 스타벅스·파스쿠찌 등의 개선은 FE가 v2로 전환하기 전까지 현재 화면에 나타나지 않는다. 이 지연은 직영 체인을 v1 ‘프랜차이즈’로 오표시하지 않기 위한 의도된 비용이다. 기존 브랜드 ETL(`etl.brands.apply`)이 v1 run을 갱신하는 경로는 그대로 두되, v2 publication은 legacy run을 입력 증거(`legacy_exact_name_estimate`)로 참조만 한다. v2 publication이 어떤 legacy run을 참조했는지 `data_version`에 기록해 두 계약의 차이를 재현할 수 있게 한다. 참조 방식은 **publication 생성 시점에 legacy 증거를 projection 행으로 고정(materialize)**하는 것이다. v2 조회는 `brand_mapping_state`나 `automatic_match()`를 실시간으로 읽지 않는다. 실시간으로 읽으면 같은 generation인데도 v1 ETL의 run 전환에 따라 v2 결과가 바뀐다. 그러면 불변 세대, 캐시 key, rollback 의미가 깨진다. 따라서 v1 run이 바뀌어도 v2는 다음 publication 전까지 이전 run 기준을 유지한다. 이 시차는 meta의 참조 run과 운영 차이 보고로 드러낸다. 공개 enum·기본값·오류 규칙은 OpenAPI/FE 계약/서버 파서에서 일치시킨다.

v2 결과의 새 필드 예시(가상의 schema 예시이며 실제 점포 판정이 아님):

```json
{
  "brand": {
    "status": "estimated",
    "brand_key": "01900000-0000-7000-8000-000000000001",
    "name": "본죽",
    "basis": "approved_alias_name_estimate",
    "reference_date": null,
    "reference_year": 2025,
    "observed_at": "2026-11-15T00:00:00Z",
    "time_basis": "observed_record"
  },
  "operation": {"type": "unknown", "basis": null}
}
```

meta에는 `brand_classification={availability, time_basis, reference_sources, observed_at, limitations}`, 정규화 query, `data_version.brand_classification={generation, rule_version, alias_version, policy_version}`를 둔다. 원문 URL의 키·관리자 이름·내부 로그 경로는 공개하지 않는다. 기존 내부 전체 hash나 캐시 지문을 AI 문장으로 노출하지 않는다.

자료 미설치 상태는 `availability=pending`으로 구별한다. all+unknown 포함은 기본 코호트를 유지할 수 있지만 chain 엄격 필터는 0건이어도 ‘브랜드 데이터 준비 안 됨’을 명시한다. 확인된 점포가 0이라는 의미로 안내하지 않는다. 상태 포인터 손상/DB 실패는 오류로 응답하며 pending/미확인으로 숨기지 않는다.

### 7.2 엔드포인트별 적용 범위

| 경로/영역 | 변경 원칙 |
|---|---|
| v2 nearby, snapshot | 동일한 공통 코호트 SQL에 소속/운영/시간 조건. map/table/count 같은 결과집합 |
| v2 activity, risk | 지역·서울 비교 코호트·좌표 미확보 집계에도 같은 비공간 브랜드 조건. 분모·생존율 대상 정의 보존 |
| v2 risk interpret | FE 집계 신뢰 금지, 같은 서버 세션에서 Risk/활동 재계산, query 및 classification 세대 일치 검증 |
| history | **현행 history는 요청 category·브랜드로 이력을 자르지 않음**. 단, `SUPPORTED_STORES`(지원 업종 + `store-name-keywords-v1` 이름 제외)는 이미 적용되므로 이름 제외된 본죽 43행 같은 기록은 이력에도 나오지 않는다. v2도 이 범위를 그대로 두고 브랜드 파라미터를 받지 않으며(422), 각 행에 새 소속/시간 근거만 표시. 필터링 이력 UX는 별도 제안 전 추가하지 않음 |
| meta/data-range | **현행 category/sub_category만 받음**. v2도 브랜드와 무관한 원천 조회 월 범위를 유지하고 FE에 그 의미 표시. 브랜드 조건을 거절. 브랜드별 조회 가능 월은 별도 계약이 필요 |
| 공식 상권 지표/인구·매출 | 원천이 브랜드별로 분해되지 않으면 필터된 숫자로 재표시하지 않음. 해당 공식 통계의 모집단/공간/기간을 계속 안내 |

여러 HTTP 요청 사이 동일 DB snapshot은 보장되지 않는다. FE는 결과 generation이 다르면 결과 묶음을 새로 조회하거나 혼합 표시를 중단한다. generation은 snapshot pinning을 뜻하지 않는다. 서버 내 단일 요청의 Risk/활동/AI 준비는 기존 READ ONLY 세션의 일관성 기준을 지킨다. 요청 중 외부 매장 검색·LLM 판별·ETL을 실행하지 않는다.

분류 meta의 상태별 카운터는 필터 적용 전의 **동일 장소/반경/업종/시점/면적 조건 코호트**에서 산출하고 분모를 명시한다. 서울 좌표 미확보 카운터는 기존 비공간 코호트 설명을 유지하며 주변 미확보 숫자로 오인시키지 않는다. 별도 상태 counts를 N에 더하지 않는다. 다중 근거 join으로 인허가 행이 늘지 않도록 classification projection 단일 행/EXISTS를 사용한다.

## 8. FE·AI 설계 변경

### 8.1 화면

- ‘프랜차이즈(추정)/개인 매장’을 ‘전체/브랜드·체인/비체인 확인’으로 개편하고, ‘추정 포함’과 ‘브랜드 정보 미확인 포함’을 별도 제어한다. ‘체인 제외’ 조합은 4.2절 계약으로 명확히 표시한다.
- 초기 화면은 기존 전체 조회를 유지한다. chain 선택 시 unknown 제외를 명시 전송한다. 면적 결측 토글과 혼용하지 않는다.
- 배지 예: `브랜드 소속 확인`, `브랜드 소속 추정`, `비체인 확인`, `미확인`, `근거 충돌`. 가맹/직영 배지는 실제 운영 근거가 있을 때만 별도로 표시한다.
- 기준연도/관측일/과거 소속 한계를 툴팁·상세에서 제공한다. unknown을 개인 매장 아이콘·독립점 비율로 표시하지 않는다.
- ‘결과 없음’, ‘브랜드 자료 준비 중’, ‘미확인 제외로 결과 감소’, ‘지원 업종/이름 제외’의 사유를 구별한다. 전국 전체 매장 수나 브랜드 공식 총매장 수로 부르지 않는다.
- FE 자체 부분 문자열 재분류·하드코딩 브랜드 예외를 제거한다. 모든 표/지도/다운로드·보고서에서 서버 필드를 사용한다. 브랜드 전체 목록 화면은 별도 운영용 과제다.

현재 FE 파일은 수정하지 않는다. 구현 단계에서 FE 수정 요청 문서와 계약 예시를 전달하고 담당자 반영·실브라우저 검증을 별도로 기록한다. 기존 내부 프롬프트·원천 hash·검수자 정보를 제품 화면에 노출하지 않는다.

### 8.2 AI 해석

LLM 키 추가는 브랜드 판별의 선행 조건이 아니다. 소속은 서버 증거와 규칙으로 결정한다. AI에는 허용된 상태별 집계·필터/시간 기준·기준년도·한계만 전달한다. 점포명·주소·인허가번호·검수자·원문 명부를 보내지 않는다.

`브랜드 소속 추정`을 `실제 가맹 계약 확인`으로 바꾸거나 unknown을 독립점으로 해석하는 문장은 서버 후보/검증 단계에서 차단한다. 현재 연결 문단·근거 ID 검증 구조를 유지하고 v2의 allowed context/schema/prompt 버전을 증가시킨다. 추정 포함 여부·운영 형태·시간 기준·공개 세대·원천 배치·규칙 버전을 Risk/AI 캐시 key에 포함해 기존 결과와 섞지 않는다. 자료 pending이면 그 기능의 한계만 설명하며 다른 확보된 지표까지 임의로 생성하지 않는다.

## 9. 적재·검수·운영

### 9.1 안전한 수집과 공개

1. 공급자별 승인/이용 조건, 기준일·지역·업종·페이지 수/전체 건수·중복키·행 hash·용량 상한·쿼터를 manifest로 기록한다. 스키마 변경/응답 오류/빈 응답은 정상 0건과 구별한다.
2. 불변 snapshot 저장 후 canonical/별칭 변경안과 점포 판정을 dry-run으로 만든다. `기존→신규 status`, brand 전환, 운영 형태, 업종/이름 제외, 미확인/충돌, 변경 사유를 집계한다.
3. 승인된 브랜드와 별칭만 사용한다. 새로운 짧은 별칭/운영 형태 확정/충돌 해결은 검토 큐에서 결정한다. 일괄 승인도 결정 버전과 대상을 기록한다.
4. 입력 hash·stores 관련 필드·별칭/규칙 버전이 계획과 같을 때만 새 publication을 완성한다. 변경되면 재계획한다. 검증되지 않은 부분 수집은 기존 완전 세대를 대체하지 않는다.
5. 한 트랜잭션으로 classification projection의 무결성 확인과 active 포인터 전환을 수행한다. 공개 준비 중인 세대는 API가 읽지 않는다. 실패하면 이전 세대 유지, 실패/범위 부족을 운영 상태로 기록한다.
6. 변경된 generation이 즉시 새 캐시 namespace가 되도록 연결한다. 포인터 전환은 DB 쓰기이므로 기존 #74 MVCC snapshot 지문만으로도 보수적 miss가 나지만, 그것은 의미 기반 무효화가 아니다. publication generation·alias/policy 버전·v2 필터 정규화값을 Risk/AI key에 명시적으로 넣고, v1과 v2 결과가 같은 key를 공유하지 않도록 계약 버전도 key에 포함한다. old snapshot이 새 세대 결과를 덮지 않는 기존 규칙을 유지한다. 논리적 보존 기간 내 이전 publication으로 포인터 rollback 가능해야 한다. stores 원본/인허가키·기존 외부 분류는 변경하지 않는다.
7. 원천별 부분 성공 정책은 사전에 정한다. 한 브랜드의 자료 수집 실패로 기존 모든 브랜드를 unknown/비체인으로 초기화하지 않는다. 만료된 근거는 상태·시간 기준에 따라 unknown으로 내리며 과거 관측 증거 자체는 삭제하지 않는다.

### 9.2 신선도·관측 이력

인허가 최신화·브랜드 카탈로그 연도·공식 매장 명부 관측일은 독립 지표다. 월 1회 갱신이라는 기존 운영 방향을 기본으로 삼되, 공급자 승인 조건/실제 배포 주기를 확인한 후 세부 TTL을 정한다. 일률적인 30일 경과 즉시 비체인 전환은 금지한다. 유효 기간/철회/갱신 상태에 따라 현재 판정은 보류할 수 있다.

수집 실패·응답 부분 누락·별칭 충돌 증가·브랜드 변경 급증·unknown 비율 급증을 알리고 운영자가 이전 세대와 비교한다. 자동 경보 임계치는 초기 검증 분포를 보고 정하며 임의 정확도 숫자를 사실처럼 문서화하지 않는다. 검토 책임자는 서비스 운영자, 원천/API 승인은 계정 소유자, BE/ETL 구현·측정은 BE 담당, 화면/계약 적용은 FE 담당으로 제안한다. 실명·담당 확정은 사용자 답변 대상이다.

### 9.3 보관·보안·비용

공공 API와 브랜드 사이트/지도 제공자의 재사용 조건은 각각 다르다. 공식 안내·개별 계약에서 허용된 최소 항목만 저장하고 보관 기간/재배포/출처 표시/철회 절차를 기록한다. 로봇 배제 준수만으로 수집 허락이 충족됐다고 보지 않는다. 허용이 불명확하면 수집 대신 제공 파일·개별 확인 증거를 사용한다.

기존 data.go.kr/Kakao 키는 환경에 존재한다. 공정위 브랜드 서비스의 기존 승인은 확인되어 있지만 다른 서비스의 같은 키 활용 권한은 별개다. 원문 키를 MD·git·로그·대화에 넣지 않는다. URL에서 serviceKey를 제거하고 오류도 비밀값 없이 기록한다. 별도 관리자 인증/감사 없이 공개 API에서 별칭·판정을 수정할 수 없게 한다. MVP 검토 큐는 비공개 CLI/승인 파일로 충분하다.

수집은 API 프로세스 밖에서 실행하고 호출 빈도·재시도/백오프·동시성·일일 한도를 설정한다. 서울/지원 업종·변경분 중심으로 수집한다. 호출량은 `ceil(예상행수/허용page_size)×원천·연도·분할범위+검증/재시도`로 산정하며 실제 쿼터와 비용은 승인 화면/이용약관에서 확인한다. API가 무료여도 서버/DB/작업자 비용은 별도다. 유료 결제·대규모 크롤링을 이번 문서 작업에서 실행하지 않는다.

Render Free의 현재 연결·시간 예산과 작은 DB에서 대형 원문·모든 과거 snapshot을 무제한 보관하지 않는다. 전체 원문은 허용된 저장소 밖 파일/별도 보관소, DB는 검증된 최소 증거와 조회 projection을 권장한다. 실제 용량 여유·index 포함 크기·배치 peak를 측정해 수용하지 못하면 데이터 축소/외부 보관/환경 확장을 먼저 결정한다. migration/ETL은 서버 시작 시 실행하지 않는다.

**용량 gate(Render Free DB 저장 한도 1GB 전제)**. 현재 Free DB 사용량은 이 문서에서 측정하지 않았다. 구현 전 `pg_database_size`와 신규 테이블·인덱스의 `pg_total_relation_size`를 측정한다. 활성+직전 1개 세대를 유지한 채 새 세대를 작성하면 순간적으로 **최대 3개 projection 세대**가 공존한다. 이 상태의 실제 테이블/인덱스·증거 누적·정리/VACUUM·migration 여유를 계산한다. WAL/임시 공간은 `pg_database_size`에 모두 포함되지 않으므로 공급자의 디스크/쿼터 산정 방식에 맞춰 별도로 측정하고 중복 합산하지 않는다. 실제 한도 내에서 수집/rollback이 가능한 여유가 있어야 배포 후보가 된다. 80% 이하 사용은 초기 엔지니어링 목표 예시이며 측정 사실이나 별도 사용자 승인 요건이 아니다.

활성+직전 1개는 온라인 rollback 대상으로 보존한다. 그보다 오래된 projection은 접근/보존 정책에 따라 정리하며 원천·증거·검토 결정은 재생성 가능하도록 허용된 보관소에 보존한다. 즉시 포인터 rollback과 오래된 세대의 재구축/검증을 구별한다. projection 삭제 직후 물리 디스크 공간이 즉시 반환된다고 가정하지 않는다. 원천 원문 JSON/HTML은 DB에 넣지 않는다. 세대 정리는 진행 중 독자가 참조하는 세대를 삭제하지 않도록 버전 사용/트랜잭션과 조율한다. 2026-12-13 Free DB 만료와 복원 절차도 신규 테이블을 포함하도록 갱신 대상이다.

## 10. 검증 기준과 관측 지표

### 10.1 정답셋

네 브랜드의 단순 이름/지점 접미사/법인 접두사/영문·별칭/짧은 이름/다른 브랜드 변형을 포함한다. 카탈로그에 있는 다른 브랜드·카탈로그 밖 직영 체인·지역 체인·비슷한 이름의 독립점·다중 입점·폐업/상호 변경·좌표 결측·업종 제외·기존 외부 분류 충돌도 포함한다.

정답은 브랜드 소속, 운영 형태, 적용 기간, 동일 인허가 연결을 각각 라벨링한다. 원천 URL·기준일/관측일·검수 판단을 함께 보존한다. 단순 키워드 검색으로 라벨을 자동 작성하지 않는다. 조정용 집합과 최종 평가 집합을 분리하고, 중요한 confirmed/음성/충돌 사례는 다른 검토자가 재검토한다. 표본 수·브랜드/기간/표기별 분포는 실제 확보 자료를 보고 정하되 네 브랜드와 음성/충돌/시간 사례가 빠진 평가로 출시하지 않는다.

| 지표 | 산식/의미 | 출시 판단 |
|---|---|---|
| confirmed 정밀도 | 정답인 확정 소속 / 확정으로 예측한 라벨 사례 | 시범 검수셋의 확인된 오확정 0건. 모집단 100% 정확도 주장이 아님 |
| 추정 정밀도·재현율 | 추정 포함 양성의 precision/recall, 정답 소속 행 기준 | 브랜드별·표기별 공개, 기준선 exact-only와 비교 |
| 운영 형태 정밀도/coverage | 운영 근거 있는 라벨에서 별도 측정 | 브랜드 소속 지표와 합치지 않음. 근거 없음 unknown |
| 분류 coverage | 상태별 기록 수 / 같은 필터 전 모집단 | 전체 영업/폐업·현재 범위·업종/원천 구분, unknown 감소만 목표로 삼지 않음 |
| 충돌/노후화/범위 제외 | 이유별 건수와 이전 공개 세대 차이 | 급격한 변화 원인 미확인 시 공개 보류 |
| 수집 완전성 | 페이지/범위/기준일 검증, source별 관측 갱신 상태 | 일부 수집 성공을 전체 완료로 표시하지 않음 |

**재현율과 연결 커버리지의 분모**. 2.2절 키워드 감사 후보는 키워드에 걸린 것만 담으므로 모집단 재현율 분모로 쓸 수 없다. (a) 공식/허용 서울 매장 명부 중 인허가 기록과 연결된 비율은 **점포 연결 커버리지**다. 이를 곧바로 분류 재현율로 부르지 않는다. 명부의 현재성·지역·지원 업종과 연결 불가 사유를 공개한다. (b) 분류 재현율은 키워드와 독립적으로 뽑아 검수한 인허가 표본의 정답 브랜드 소속 양성 중 C/E로 검출한 비율로 측정한다. (c) 명부에서 독립적으로 연결·검수한 인허가 양성 집합에서도 분류 재현율을 별도로 측정하되 연결 가능한 점포로 한정된 지표임을 명시한다. 원천 물리 점포와 인허가 기록 단위는 혼합하지 않는다. 표본 수·불명 라벨 수·95% 신뢰구간을 공개하고 층화 표본은 층별 결과와 모집단 가중 방식을 명시한다. 현재 명부로 평가할 수 없는 폐업 기록은 미측정으로 표시한다.

**출시 gate 설계**. 아래 지표는 구현 검증 시 측정한다. 정밀도 0.95 같은 수치는 초기 목표 예시이며 검증된 정확도나 지금 사용자가 승인해야 하는 정책이 아니다. 실제 정답셋/오탐 비용·표본 오차로 수용 기준을 정해 최종 평가 전에 고정하고, 통과를 위해 평가 후 기준을 바꾸지 않는다.

| gate | 측정 | 제안 기준 |
|---|---|---|
| 확정 오탐 | 네 브랜드의 모든 C 판정 전수 검수 | 오확정 0건 |
| 추정 정밀도 | 네 브랜드 E의 패턴별 오탐 점검과 별도의 행 확률표본 검수. 패턴 대표 사례를 확률표본에 임의 합산하지 않음 | 초기 목표 예시: 브랜드별 점추정 ≥ 0.95, 적절한 신뢰구간/표본 수 함께 공개. 단순 이항 표본은 Wilson 하한, 층화/가중 시 해당 표본설계에 맞는 구간 사용 |
| 기준선 대비 | 같은 정답셋에서 exact-only(현행) 대비 | 재현율 증가, 정밀도 비열위 |
| 짧은 별칭 확산 | 승인 짧은 별칭 외 영숫자 3자 미만 상호의 E 생성 | 0건 |
| v1 호환 | 같은 stores/legacy run·동일 요청으로 migration/publication 전후 nearby/snapshot/activity/risk/history/data-range 비교 | 동적 시각 등 비교 제외 필드 목록을 사전 고정한 정상 응답의 data/meta 의미 값 동일. AI는 고정 mock으로 비교. v2 인자를 보낸 요청의 422는 의도된 차이 |
| 원본 무변경 | stores 전체 행/EWKB hash, legacy 브랜드 5테이블 hash | 동일 |
| 집합 일관성 | 10.2절 count 등식, 상태 카운터 합 = 필터 전 코호트 | 전 조합 일치 |
| 성능 | 같은 코드/DB·연결 설정·쿼리/동시성·캐시 조건에서 기존 v1와 새 v2 반복 측정. 중앙값/상위 지연·SQL 수 공개 | 기존 요청 시간/연결 예산 준수, timeout·500 0건. 새 계약별 예산은 구현 전 정하며 과거 #122의 다른 환경 숫자에 임의 10% 기준을 적용하지 않음. Render Free의 모델 밖 운영 인덱스(`ops_free_risk_cover`/`ops_free_risk_name_v1`)와 실제 계획을 고려한다. 신규 DDL은 용량·잠금·rollback 검증을 별도 배포 계획에 포함 |
| 용량 | 9.3절 용량 gate | 통과 |

**단계별 gate 적용**. 위 gate가 모든 단계에서 측정 가능한 것은 아니다. C가 없는 단계에서는 ‘확정 오탐 0건’이 내용 없이 통과하므로 C 경로를 열기 전에는 통과로 보고하지 않고 ‘해당 없음(C=0)’으로 표시한다. 재현율에는 (b) 키워드 독립 표본이나 (c) 명부 연결 집합이 필요하다. 브랜드별 양성이 희소할 수 있어 단순 무작위 표본만으로 충분한 표본을 확보하기 어려울 수 있다. 감사 후보 762/355,835를 실제 스타벅스 소속 발생률로 사용하지 않는다. 필요하면 지역·건물 등 키워드와 독립된 층화와 설계 가중을 사용한다. 명부와 독립 표본이 모두 없는 E 전용 단계(1단계 → 3단계)에서 측정·공개하는 항목은 다음으로 한정한다.
- 같은 검수 라벨셋에서 exact-only 대비 **추가 정답 검출 수와 추가 오탐 수(절대값)**
- 추정 정밀도
- 짧은 별칭 확산
- v1 호환, 원본 무변경, 집합 일관성, 성능, 용량

이때 ‘재현율 증가’는 ‘재현율 미측정’으로 명시한다. 이 상태로 v2 E 전용 공개를 할지는 사용자/FE 결정이다. 2단계(점포 근거)는 C 경로와 재현율 측정의 선행조건이지만, 위 gate를 통과한 E 전용 v2(3단계)의 선행조건은 아니다.

### 10.2 회귀·일관성·운영 검사

- 네 브랜드를 찾는 테스트와 동일 부분 문자열의 비소속 점포를 배제하는 테스트를 함께 둔다. 본죽 짧은 별칭 예외가 다른 두 글자 상호의 자동 true로 번지면 실패다.
- 본죽/본죽&비빔밥 각각 identity 보존, 파스쿠찌 카탈로그 미존재 경로, 코코이찌방야 법인/지점 접미사, 스타벅스 공식 명부 연결·운영 미확인 처리를 확인한다.
- 범위 유지 시 이름 제외 본죽 후보 43행이 자동 복구되지 않는지 확인한다. 복구를 별도 승인했다면 정책 버전과 원천/업종 정답 근거를 테스트한다.
- 필터 진리표, E를 U로 취급하는 엄격 모드, conflict·운영 unknown, 422 혼합 파라미터, pending와 실제 0건을 검증한다.
- 동일 조건/세대에서 nearby count = snapshot N = 해당 T의 Risk 경쟁 점포 수 = 활동 open_count를 대조한다. 활동 개폐업·과거 코호트는 각 원래 기간 정의를 유지한다. history 전체 건수는 브랜드 필터와 무관하므로 위 등식에 넣지 않는다.
- 지역·서울 비교/좌표 미확보 집계에 같은 브랜드 조건 적용, 다중 증거 join의 중복 부풀림, AI query/meta 교차 검증과 캐시 교차 오염을 검사한다.
- 인허가 상호/주소/좌표/기간 변경, 원천 누락/회수, 동일 batch 내 데이터 수정, 삭제/복구, ETL 중 API 조회, 부분 실패, rollback, 재실행 no-op/idempotence를 검증한다.
- 과거 월 경계·브랜드 전환·현재 명부만 있는 폐업 기록을 확인한다. `as_of` 미지원 단계에서는 요청을 명시 거절하고 observed_record를 역사적 소속으로 표시하지 않는다.
- 실제 PostGIS에서 `EXPLAIN (ANALYZE, BUFFERS)`는 읽기 전용 격리 검증 환경에서 수행하고 로컬 전체 코호트/서울 집계·동시 조회·SQL 수·응답시간·메모리·DB/index 용량을 측정한다. cold/warm 조건과 환경을 명시한다. 현재 문서는 성능 측정을 수행한 결과가 아니다.

문서 작성 검증과 향후 구현 테스트를 구별한다. 이번에 신규 앱 테스트를 만든 것처럼 기록하지 않는다. 구현 단계에서는 기존 unit/integration·타입/정적 검사와 새 계약 회귀 검사를 통과해야 한다.

| 단계 | 산출물 | 선행조건/완료 기준 |
|---|---|---|
| 0. 설계 검수 | 이 문서, 실제 누락 진단, 2차 Claude 검수, 사용자 최소 질문 | 이번 요청 범위 |

구현은 별도 이슈/작업 브랜치와 설계 검수 후 작은 커밋으로 진행한다. DDL/매칭 ETL → 조회 계약/공통 집계 → AI/캐시 → FE 요청/검증으로 분리하고 CI 통과·develop 반영과 실제 배포를 구별한다. 데이터 없이 UI 선택지만 늘리는 것으로 기능 완료 처리하지 않는다.

구버전 API는 새 canonical 증거를 무조건 ‘프랜차이즈’로 투영하지 않는다. 특히 직영 체인을 v1 가맹 계약 확인으로 바꾸지 않는다. v2 관찰 기간에 두 결과의 차이와 원인을 운영 보고로 기록한 뒤 FE의 명시적 전환을 진행한다. v1 폐기일은 사용자/FE와 정하며 현재는 미정이다.

## 14. 문서 검수 완료 후 사용자에게 요청할 정보

다음 세 묶음만 먼저 요청한다. 비밀 키 원문은 대화로 받지 않고 기존 비밀 설정 또는 별도 승인된 설정 경로를 사용한다.

1. **포함 기준**: 권장안인 ‘가맹점+직영점을 포함한 브랜드·체인’을 사용할지, 지역 소규모 체인도 포함할지. 기업 법인 단독 매장까지 별도 필터가 필요한지. 후자는 체인과 별개 기능이다.
2. **서비스 활용 승인 상태**: [소진공 상가정보 15012005](https://www.data.go.kr/data/15012005/openapi.do) 승인 여부. 선택으로 [공정위 가맹/직영 집계 15125490](https://www.data.go.kr/data/15125490/openapi.do) 승인 여부. 기존 공정위 브랜드 API 키를 새로 요청하지 않는다. 없으면 신청 가능한 계정/담당만 확인한다.
3. **브랜드 점포 근거와 운영 범위**: 네 브랜드 공식 매장 자료/CSV 또는 이용이 허용된 제공처·조건·기준일, 더 포함할 우선 브랜드 목록, 검수 담당자. 현재 소속 선별부터 시작할지, 과거 시점의 실제 소속·개별 직영/가맹 확인도 당장 필수인지. 관련 자료가 없으면 그 값은 unknown으로 둔다.

업종 이름 제외 예외는 별도 정답 검수 후 제안한다. 이번 질문에서 43행 전체 복구를 일괄 승인받는 것으로 대체하지 않는다. 자료가 없어도 진행 가능한 기반 작업과 해당 자료가 반드시 필요한 확정/운영/역사 기능을 분리한다.

## 15. 실제 검수와 최종 재검토 기록

Claude Code 1차 검수 → 지적 반영 → 2차 검수 → Codex 최종 재검토를 실제 수행했다. 아래는 각 시점의 지적·조치와 후속 확인을 구별해 기록한다.

### 15.1 Claude Code 1차 검수 (2026-11-15, Round 1)

- 방식: 대상 MD Read/Edit만 사용. 제공된 읽기 전용 감사 JSON과 `matching.py`·`catalog.py`·`franchise.py`·`store_scope.py`·`brand.py`·`store_history.py`·`data_range.py`·`nearby.py`·`ai/context.py` 발췌를 대조했다. 셸·DB·네트워크·다른 파일 접근 없음. 외부 출처 URL은 재확인하지 않았다(Codex 2026-11-15 확인을 전제).
- 사실 대조: 689,440/355,835/338,905, 카탈로그 11,167, 6,839, 네 브랜드 후보·사유·업종 분포(코코이찌방야 일식20/한식8/양식7/중식2, 본죽 이름 제외 43)는 JSON과 일치했다. 파스쿠찌·스타벅스 부재를 ‘이 2025 스냅샷 한정’으로 서술한 점도 맞다.

차단 결함과 조치:

1. **history 범위 서술 오류** — 원문은 “history는 업종 필터로 자르지 않음”이었으나 코드상 `SUPPORTED_STORES`(지원 업종+이름 제외)를 적용한다. 7.2절을 정정하고 v2 history의 브랜드 인자 422를 명시했다.
2. **진리표 입력 정의 누락** — legacy exact-name, legacy 외부 분류만 있는 행, legacy false와 새 증거 충돌이 어느 상태가 되는지 없어 구현마다 해석이 갈릴 수 있었다. 4.2절에 입력→상태 표를 추가했다.
3. **N(비체인 확인) 공백 미반영** — MVP에 N 생성 경로가 없어 `non_chain/exclude`가 항상 0건이 되는데 이를 정상으로 정의하지 않았다. 의미·meta·FE 노출 권고를 추가했다.
4. **projection 크기/모집단 미정 + 1GB DB 충돌** — 행마다 U를 저장하면 세대당 약 36만 행이고 세대 보존과 충돌한다. 희소 projection(행 부재=U), 판정 모집단=`SOURCE_SUPPORTED_STORES`·조회 시 `SUPPORTED_STORES` AND, 용량 gate와 세대 보존 한도를 추가했다.
5. **측정 불가능한 출시 기준** — 키워드 후보로는 재현율을 낼 수 없다. 명부 기반·키워드 독립 무작위 표본 분모와 제안 gate(오확정0, 정밀도·Wilson 하한, v1 hash 무변경, 원본 hash, 성능·용량)를 추가했다. 수치는 제안값으로 표기했다.
6. **별칭 패턴 오탐 경계 불명확** — `approved_branch_pattern`의 고정 일치 문법, 짧은 별칭 구분자 요건, 브랜드별 거부 목록을 5.1절에 추가했다.

비차단 개선과 조치: 2.2절 열 정의(이름 제외 전 기준·범위 밖 행 수)와 본죽 exact 4행·`weak_name` 의미 정밀화, 스타벅스 공식 매장 검색의 수집 전제 정정, v1 고정에 따른 사용자 체감 지연·legacy run 참조 기록, v1 unknown 인자 422가 동작 변경임을 명시, 캐시 key에 generation·계약 버전 명시(MVCC 지문 의존 금지), 1단계 산출 상태를 E/U/conflict로 한정한 완료 기준.

남은 데이터/정책 의존성: 포함 기준, 상가정보 등 서비스 승인, 네 브랜드 점포 명부와 이용 조건, 검수 담당이다. 이름 제외 43행의 처리는 별도 점포 검수 과제다. 점포·운영·역사 근거가 필요한 기능의 확정/출시는 해당 자료 확보까지 제한한다. 자료와 무관한 schema/검수 도구·pending/unknown 경로 구현을 모두 중단할 필요는 없다. 1차에 제안한 정밀도·용량·성능 수치는 Codex가 아래 재검토에서 조정했다.

Round 1 판정: 차단 결함 6건을 이 문서에 직접 반영했다. 설계 문서로서 **PASS FOR DESIGN**(구현 준비 완료 아님). 2차 검수에서 반영 내용의 일관성을 다시 확인해야 한다.

### 15.2 Codex의 1차 반영 재검토

1차 직접 수정 결과를 읽고 기존 소속 ID에서 canonical identity로의 승인 연결·충돌 우선순위, 짧은 전체 이름과 지점 패턴 구분, 운영/as_of 초기 미지원 422를 보완했다. 명부 연결 커버리지와 분류 재현율을 분리하고 비교 환경이 다른 과거 지연에 임의 10% 기준을 적용하는 안을 제외했다. v1 응답 비교는 동적 필드를 사전 구별해 의미 값을 비교한다. 용량 계획의 최대 3세대 공존·WAL/임시 공간 별도 산정·삭제 후 공간 회수·진행 중 독자를 보완했다. 제안 수치를 사용자 승인 요건으로 확대하지 않았고 자료 비의존 구현을 일괄 중단하는 표현을 정리했다. 수정본으로 실제 Claude Code 2차 검수를 진행한다.

### 15.3 Claude Code 2차 검수 (2026-11-15, Round 2)

- 방식: 1차와 같다. 대상 MD Read/Edit만 사용했고, 같은 감사 JSON과 코드 발췌로 현재 수정본 전체를 다시 대조했다. 셸·DB·네트워크·외부 URL 재확인은 하지 않았다. 1차에서 해결된 항목은 반복하지 않았다.
- 사실 재대조: 수치, 본죽 `weak_name` 45행·exact 4행, 이름 제외 43행, 코코이찌방야 업종 분포, 스타벅스·파스쿠찌의 ‘이 2025 스냅샷 한정’ 부재 서술은 정확했다. history의 `SUPPORTED_STORES` 적용과 비필터 이력, data-range의 category 전용 범위, 기존 업종·이름 제외 보존, 외부 stores 필드 비변경도 일관된다.

차단 결함과 조치:

1. **v2의 legacy run 참조 방식 미정** — v2가 `brand_mapping_state`를 실시간으로 읽으면 같은 generation에서도 v1 ETL에 따라 결과가 바뀐다. 그러면 불변 세대·캐시·rollback이 성립하지 않는다. publication 시점에 고정(materialize)하고 시차를 meta로 공개하도록 7.1절에 명시했다.
2. **지점표지 오탐 잔여** — 1차 문법은 `…점`으로 끝나기만 하면 지점표지로 인정할 수 있었다. 그래서 `파스쿠찌옆분식점`, `스타벅스커피전문점` 같은 오탐이 E가 될 수 있었다. 일반 업종 접미·위치어·타 브랜드명·메뉴명 제외 규칙과 구분자 없는 결합의 별도 계측을 5.1절에 추가했다.
3. **진리표 미정 조합** — legacy true(브랜드 ID 없음)나 해석 불가 legacy `brand_id`에 새 C/E가 겹치는 경우의 상태가 정의되지 않았다. 4.2절에 행을 추가했다. 현행 Matcher상 같은 run에서는 legacy 외부 분류와 exact-name 증거가 공존하지 않는다는 점과, 원천 복합키(내부 bigint 아님)로 연결한다는 점도 명시했다.
4. **단계별 출시 기준의 측정 불가능성** — C=0 단계에서 ‘확정 오탐 0건’은 내용 없이 통과한다. 재현율 gate도 명부나 독립 표본 없이는 측정할 수 없다. 그런데 3단계의 선행조건이 불명확했다. 10.1절에 단계별 gate를 추가했다(E 전용 단계는 절대 추가 TP/FP·정밀도 등으로 한정, ‘재현율 미측정’ 명시, 희소 양성의 층화 필요). 11절 3단계의 진입 조건도 정리했다.

비차단 개선: 본죽 두 행의 관계를 카탈로그 사실(같은 본부 관리번호 `JNG_018965`)로 한정하고 법적 관계 추론을 배제했다. C 경로 미활성 시 `confirmed_only` 0건도 N과 같은 방식으로 정의했다. Render Free 운영 인덱스 의존을 성능 gate에 추가했다.

선택 사항(반영하지 않음): 이름 제외 정책은 `cafe`만 잡고 `cofe` 변형(`본죽&비빔밥 cofe(종각점)`)은 잡지 못하는 불일치가 감사 예시에서 보인다. 이는 브랜드 설계 범위 밖의 `store-scope` 정책 과제이므로 기록만 한다.

남은 데이터/정책 gate(설계 결함 아님): 포함 기준, 상가정보 등 서비스 승인, 네 브랜드 점포 명부와 이용 조건, 검수 담당, 일반 제외어/별칭 초기 목록의 승인, E 전용 v2 공개 여부, Free DB 실사용량 측정이다.

Round 2 판정: 차단 결함 4건을 이 문서에 직접 반영했다. 설계 문서로서 **PASS FOR DESIGN**이다. 구현/출시 완료는 아니며 해당 기능별로 16절의 검증과 입력이 필요하다. 이후 Codex 최종 재검토는 다음 절에 기록한다.

### 15.4 실행 증빙 및 Codex 최종 재검토 (2026-11-15)

실제 `Claude Code 2.1.322`의 비대화형 CLI를 두 번 별도로 실행했다. `Read,Edit`만 허용했고 MCP는 비워 두었으며 세션 지속 저장을 비활성화했다. 외부 사이트 검증은 Codex가 공식 원문으로 수행했고 Claude는 제공 코드/감사 결과/문서를 대조했다.

| 실행 | KST 시작~종료 | 실제 결과 | 대상 MD 입력 SHA-256 |
|---|---|---|---|
| 1차 | 00:35:07~00:38:28 | exit 0, success, 18 turns, permission_denials 0, PASS FOR DESIGN. MD 직접 수정 | `5151f623c2f4389c7322c96ab303c62791fb49c898ab869eb5a94fecb1c3592f` |
| 2차 | 00:41:20~00:44:22 | exit 0, success, 14 turns, permission_denials 0, PASS FOR DESIGN. 수정본 MD 직접 재검수/수정 | `1cde454d4423d4aad7d609b75f5a4044775565c59cf7ba1b487a5ebfda97f4f4` |

2차 출력 MD SHA-256은 `d85bc74d1cf4cd334df5950f3b43493a330d610167f4bafcd2122953c0a5aece`다. 이후 이 기록과 최종 정리 문구를 덧붙였으므로 최종 파일 지문과는 다르다. 저장소 밖 `SpotON-private-backups/brand-chain-design-20261115/`에 `review-1.json`, `review-2.json`, `metadata-1.json`, `metadata-2.json`, 각 입력/오류 출력과 감사·최종 정적 검증 결과를 보관했다. 원문 키/대표자/연락처/인허가번호는 검수 입력에 포함하지 않았다.

Codex는 2차 반영본을 원 코드·감사 결과와 대조해 수치/원인 한정, legacy source link와 고정 publication, 4.2절 모든 필터 조합, 짧은 별칭 전체 이름, C/N 미활성 상태, 업종/이름 제외, history/data-range, AI/캐시·rollback을 다시 확인했다. 후보 비율을 실제 브랜드 발생률로 쓰지 않도록 표본 문구를 정리하고 패턴 대표 사례와 확률표본의 분모를 분리했다. 임의의 추가 사용자 승인 요건을 제외하고 구현의 실제 DDL·용량 검증 대상으로 정리했다. UTF-8·16개 절·JSON 예시·문서 링크·git 공백/변경 파일 범위 검사도 확인한다.

최종 판정은 **설계문서 완료**다. 이번 변경은 이 MD와 공통 안내 두 파일뿐이며 앱/FE/DB/운영 배포를 변경하지 않았다. 정답셋 기반 정확도·성능·실제 API 연동 검증을 완료한 것으로 주장하지 않는다. 미확보 입력은 14절의 사용자 요청과 16절의 기능별 후속 검증에 남긴다.
