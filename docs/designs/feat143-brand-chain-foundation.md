# 브랜드·체인 판별 및 소진공 점포 대조 기반

상태: 기반 구현·실제 API 수집/로컬 인허가 비교·최종 실제 Claude Code 재검수 **PASS FOR FOUNDATION IMPLEMENTATION**. 저장소 CI는 PR에서 확인한다. 공개 필터/v2 publication/FE·운영 배포 완료가 아니다.

4차 검수용 보완: 본죽/본죽&비빔밥 혼동을 막기 위해 이름과 소진공 별도 지점 경로 양쪽에 같은 거절어 검증을 적용했다. 단독 `죽`은 제외하지 않아 `죽전점` 같은 지명은 보존한다. 관측 기준월과 seed 검수일은 UTC 호스트에서도 한국 달력으로 비교한다. 상세는7.5절.

현재 단계는 별도 ETL/읽기 전용 비교 기반 구현이다. 새 공개 API/FE 필터 연결은 후속이다. 기존 공개 화면의 동작 변경 완료를 뜻하지 않는다.

## 1. 실제 소량 호출

두 API에 GET 1회씩, 1행 요청, redirect/retry 없음, 20초·응답 1MiB 제한으로 확인했다. 공정위와 소진공 모두 HTTP200/resultCode00이다. 공정위 2025 목록은 11,167행이다. 소진공 `storeListInDong`, `divId=ctprvnCd,key=11,indsLclsCd=I2`는 137,173행을 보고했다. 이 숫자는 호출 당시 서울 I2 상가목록 행 수이며 지원 업종·현재 인허가 수/전국 체인점 수가 아니다.

소진공 JSON은 최상위 `header/body`다. 기준년월 `stdrYm`은 **header**, totalCount/pageNo/numOfRows/items는 **body**에 있다. 지점명 `brchNm`, 상호 `bizesNm`, 도로명 `rdnmAdr`, 지번 `lnoAdr`, 건물관리번호 `bldMngNo`, `lon/lat`, 업종/지역 코드가 실제 응답에 있었다. 제공 `lon`은 실제 서울 경도 범위로 검증하고 문서의 항목 설명 오기를 그대로 좌표 뒤바꿈에 쓰지 않는다.

공식 명세: [소진공](https://www.data.go.kr/data/15012005/openapi.do), [공정위 목록](https://www.data.go.kr/data/15125467/openapi.do). 인증 소량 결과/기준년월은 저장소 밖 private 진단 자료에 보존하며 원문 인증 URL·대표자·사업자번호·연락처는 수집 산출물에서 제외한다.

## 2. 이번 구현 경계와 후속 연결

이번 단계는 API 요청 처리 밖의 독립 ETL/판정 기반이다. 명시적으로 신규 패키지 `etl.chains`를 두고 기존 `etl.brands`/가맹 bool/원본 stores/공개 API 동작을 보존한다. 아직 새 판정을 공개 필터에 연결하거나 migration/배포하지 않는다. 다음 v2 publication/공통 코호트 구현이 이 산출물을 사용하며, 기반 구현만으로 현재 FE 누락이 해결됐다고 표시하지 않는다.

산출물은 (1) 근거 있는 브랜드/별칭 registry, (2) 정확 이름·승인 지점 패턴 판별, (3) 소진공 최소 필드 불변 snapshot, (4) 인허가 읽기 전용 dry-run 집계/증거 계획, (5) 공식 점포 확인 자료와 후속 API 계약이다. 이름만으로 확정 가맹/직영/비체인 판정을 만들지 않는다. 공식 점포 명부의 자동 수집 허용이 불명확하면 공식 브랜드 등록 근거와 공공 상가 자료를 사용하고 결과는 추정으로 한정한다.

## 3. Registry와 판별 규칙

- 공정위 catalog의 유일한 외식 브랜드·3글자 이상 정확 이름 경로를 보조 후보로 재사용한다. 이 catalog 경로는 **전체 이름 정확 일치만** 허용하고 아래 지점 패턴을 적용하지 않는다(8,873개 외식 브랜드명 전체에 접미 패턴을 열면 일반명사형 브랜드명의 전역 오탐이 생긴다). 반복 브랜드 관리번호/동일 정규화명 다중 행은 자동 합치지 않고 격리한다. `(브랜드관리번호,본부관리번호)` 원천 namespace와 canonical key를 구별한다.
- 스타벅스/파스쿠찌/코코이찌방야/본죽/본죽&비빔밥을 검수 seed로 둔다. 각 seed는 공식 출처 URL·관측일·승인 별칭/법인 접두사·namespace와 함께, 수집 snapshot 기준 공정위 catalog 대응 복합키가 **있는지/없는지/복수인지**를 사실대로 기록한다. 공정위 등록 여부를 사전에 가정하지 않으며, 대응 행이 있으면 승인 복합키 매핑으로 같은 canonical identity에 연결해 catalog 경로와 seed 경로가 같은 브랜드를 conflict로 만들지 않게 한다. 본죽과 본죽&비빔밥은 별도 identity이고, 같은 본부의 다른 브랜드라는 사실만으로 합치지 않는다. 소규모 체인 추가에도 최소 지점 수나 기업 규모 조건을 두지 않는다. 다만 이번 단계의 비가맹 소규모 직영 체인 커버리지는 seed 등록분에 한정되며, 소진공 반복 상호를 자동으로 체인 양성으로 승격하지 않는다(필요 시 외부 파일의 검수 후보 목록까지만).
- 기본 정규화는 NFKC/casefold와 공백 **연속 축약·양끝 제거**다. 지점 구분자 판정은 공백·괄호를 보존한 이 형태에서 수행하고, 공백 전체 제거형은 정확 일치 비교 키로만 쓴다(공백을 먼저 지우면 `본죽 강남점`과 `본죽강남점`의 구분자 규칙이 사라진다). 원상호 변경 금지. 기호/법인명/한영 표기는 seed에서 승인한 것만 허용한다. 지점 패턴은 전체 이름 고정 일치이며 임의 contains/LLM/fuzzy 최종 판정을 금지한다.
- 짧은 별칭(영숫자 3자 미만, 예: `본죽`)은 seed에서 명시 승인한 경우에만 쓰며 catalog 경로의 3글자 하한을 일반적으로 완화하지 않는다. 전체 이름이 승인된 짧은 별칭과 같으면 estimated 후보가 될 수 있다. 지점명이 붙은 짧은 별칭은 명시 구분자(공백·괄호·`-`)가 필요하고 무구분자 결합(`본죽강남점`)은 이름 단독 판별에서 `short_alias_no_separator`로 보류한다. 별칭이 이름 중간/끝에 있는 경우(`원조본죽집` 등)는 후보가 아니다.
- 지점 패턴(seed 별칭 전용) 문법: `별칭 + 구분자? + 지점토큰 + (점|지점)` 또는 `별칭 + (지점토큰점)` 괄호형. 지점토큰은 한글/영문/숫자로 시작하고 내부에 공백·`.`·`_`·`-`만 허용하며, 길이 상한(구현값 40자, 6절)·정책 버전으로 관리한다. `점/지점` 표지만으로 충분하지 않다. 지점토큰에 일반 업종 접미(식당·집·분식 등)·옆/앞 등 위치 설명·다른 승인 별칭·메뉴명·허용 외 문자·상한 초과 꼬리가 있으면 보류한다. 등록되지 않은 꼬리(예: 별칭 뒤에 `&`·추가 브랜드어가 붙은 형태)는 더 짧은 별칭으로 내려 매칭하지 않고 unknown이다. 복수 브랜드 후보는 conflict다. 복합 브랜드는 **승인된** 더 긴 별칭(`본죽&비빔밥`)을 우선하되 실제 다른 브랜드 충돌을 숨기지 않는다.
- 반환 상태는 `estimated|unknown|conflict`이며 이것은 **브랜드 소속(chain membership)** 축이다. 가맹/직영 운영 형태와 법인/개인 사업자 성격은 별도 축으로 레코드 단위 `unknown`을 유지한다. 브랜드 수준의 공식 운영 방침(예: 전 매장 직영 공시)은 seed 출처 메모로만 기록하고 이번 단계에서 개별 점포 운영 형태로 내리지 않는다. 법인명 접두사·법인 상호만으로는 소속 후보를 만들지 않는다.
- legacy 비교: 외부 `is_franchise`는 가맹 축 값이므로 `false`가 직영 체인 소속과 반드시 모순되지 않는다. 따라서 legacy false + 새 소속 추정은 소속 conflict로 덮지 않고 `legacy_false_with_chain_estimate` 비교 구간으로 따로 집계한다. 이번 기반은 legacy의 **양성 포함 여부**만 비교하며 같은 브랜드 identity인지는 검증하지 않는다. 겹치는 양성은 `legacy_positive_brand_unchecked`, 신규 후보는 `additional_estimate`, 기존 양성의 새 unknown/conflict는 `legacy_positive_now_unknown|conflict`로 공개한다. 브랜드 identity 단위 이행 비교/충돌 판정은 v2 publication 전 후속이며 현재 집계로 같은 브랜드 확인을 주장하지 않는다. legacy true나 해석 불가 brand_id만으로 확정/브랜드 identity를 생성하지 않고 기존 외부 값은 덮어쓰지 않는다. 출력에는 운영 형태 unknown과 observed_record 한계를 명시한다.
- 업종·이름 제외 정책과의 관계: 판별은 SOURCE_SUPPORTED_STORES 전체에 대해 계산하되, `store-name-keywords-v1`로 제외되는 기록은 별도 집계(`name_excluded`)로 보고하고 소속 추정이 제외 기록을 분석 모집단으로 되돌리지 않는다.

## 4. 소진공 수집 계약

호출은 고정 HTTPS 호스트/경로 `.../sdsc2/storeListInDong`, 서울 `11`, 대분류 `I2`로 제한한다. 쓰기 기능 `reqStoreModify`·임의 endpoint·전국 수집·외부 URL 입력은 지원하지 않는다. HTTPX 스트리밍, timeout20초, redirect/retry0, 로그 URL 억제, 에러는 고정 코드만 출력한다. httpx timeout20초는 연결/읽기 단위 제한이며 요청 전체 시간 상한이 아님을 기록한다. Decoding 키는 한 번 정규화 후 HTTPX params로 전송한다(기존 `etl.brands.client`와 같은 규칙을 공용 함수로 재사용). `unquote_plus`로 +를 공백으로 바꾸지 않는다. httpx 예외·`response.url`·응답 본문 일부를 메시지/로그/예외 체인에 남기지 않는다. 게이트웨이가 JSON 요청에도 HTTP200의 XML/HTML 오류(키 미등록·한도 초과 등)를 돌려줄 수 있으므로 JSON 파싱 실패·`header/body` 부재는 원문 없이 고정 코드(`non_json_response`/`schema`)로 실패한다.

페이지 크기 1,000(소량 probe는 별도), 한 페이지 최대5MiB, 전체 최대250,000행/원시 누적256MiB, 파일 최대256MiB, 최대251요청(첫 페이지 재확인 포함)을 둔다. 모든 페이지에서 resultCode00, header 기준년월·totalCount가 첫 페이지와 **동일**한지, 반환 pageNo/numOfRows·기대 행 수(마지막 페이지는 나머지), 행별 시도코드11/대분류I2와 업소번호 유일성을 확인한다. 정렬 보장이 없으므로 페이지 간 밀림은 최종 **고유 ID 수 = totalCount**로 검사하고 다르면 실패한다. totalCount 0 또는 행 상한 초과는 수집 전에 실패한다. 마지막에 첫 페이지 projection/content를 재확인하고 다르면 실패한다. 이것은 공급자 전체 시점 원자성을 보장하지 않으며 manifest 한계로 기록한다.

최소 저장은 상가업소 ID·상호·지점·업종·지역·두 주소·건물관리번호·층/호·WGS84 경위도뿐이다. 기준년월/관측시각·고정 query/endpoint·총행수·정규화 스키마/정책 버전·선택 projection SHA256를 manifest에 둔다. 원문 raw 응답/사업자·대표자·전화·키·URL query는 저장하지 않는다. 누락·잘못된 좌표(서울 경위도 범위 밖·비유한값 포함)는 좌표 미확인으로 보존하고 무효값을 임의 좌표/0/위경도 교환으로 보완하지 않는다. 소진공 상호·지점·주소는 공개 상가 정보지만 저장소 밖 파일에만 두고 커밋·stdout·로그·LLM 입력에 넣지 않는다. 필수 식별자/지역/업종 불일치·중복 ID·스키마 오류는 실패다.

파일은 symlink를 해석한 실제 경로 기준으로 저장소와 `.git` 아래를 금지하고, 같은 디렉터리의 배타 생성 임시 파일에 쓴 뒤 덮어쓰지 않는 방식으로 최종 새 파일을 만든다(기존 파일이 있으면 실패). 저장 직후 오류면 이번에 만든 불완전 파일만 정리한다. 다시 읽을 때 스키마·hash·행수·중복 ID·기준월·출처·상한을 재검증한다. 승인 snapshot이 없는 수집 실패는 판별 false/기존 데이터 삭제로 이어지지 않는다.

## 5. 점포 대조와 dry-run

- 인허가 source+license_no 단위를 유지하고 SOURCE_SUPPORTED_STORES에서 스트리밍한다. 로컬 DB 가드 + READ ONLY REPEATABLE READ, timeout60초를 따른다. API 중 DB 쓰기/수집 금지다.
- 소진공에서는 상호/별도 지점 필드로 seed 승인 브랜드 후보를 만든다. 두 원천의 주소 형식이 달라(인허가는 건물명·층/호를 포함한 상세 주소, 소진공은 기본 주소+별도 층/호) 원문 전체 문자열 동일을 요구하지 않는다. 대신 기존 지번 `building_key` 정규화(소진공 `lnoAdr`에 같은 파서 적용) 또는 도로명 기본 주소(시군구+도로명+건물본번-부번) 키가 같고, 양쪽 층/호가 모두 있으면 일치해야 한다. 한쪽만 있으면 모순 없음으로 보되 층/호를 임의로 제거·추정하지 않는다. 같은 키에 소진공 승인 후보나 인허가 지원 기록이 복수면 1:1이 아니므로 보류/충돌한다. 원문 좌표 변경이나 운영 업종 정정도 하지 않는다.
- 주소 보완은 **이름 경로에서 이미 같은 승인 별칭이 이름 앞부분에 나타났지만 보류된 기록**(예: `short_alias_no_separator`, 미승인 지점 꼬리)에만 적용한다. 인허가 상호에 브랜드 토큰이 전혀 없는 기록을 주소만으로 브랜드에 연결하지 않으며(푸드코트·복합상가 오연결 방지), 이런 경우는 `address_only_candidate` 건수로만 보고한다.
- 보완 근거는 `semas_address_corroborated`로 **estimated**까지만 허용한다. 소진공은 브랜드·가맹계약 정답 원천이 아니므로 confirmed로 승격하지 않는다. 현재 상가 자료가 과거 폐업 인허가 기록을 증명하지 않도록, 주소 보완은 인허가 최신 상태가 영업이고 유효 개업일이 소진공 기준월 말 이하인 기록에만 적용한다. 폐업·날짜 결측/검토 대상 기록은 이름 추정까지만 허용한다.
- 출력은 상태·사유·브랜드별 집계, legacy 비교, 이름 제외 수, 현재/폐업 구분, source 기준월/관측일·registry 지문이다. raw name/address/license/키는 stdout·로그·Claude 입력에 넣지 않는다. 증거 계획이 필요하면 명시 외부 파일로만 저장한다.
- 키워드 감사 후보·추정 일치 수는 매장 정답/재현율이 아니다. 잘못된 이름 경계·짧은 별칭·동명이인·다중 점포·주소/기간 불일치 테스트를 함께 수행한다. 원본 stores와 legacy5테이블에 쓰기 없음·재실행 결정성을 확인한다. 결정성은 (source, license_no) 정렬 스트리밍·정렬 키 JSON·registry/정책/snapshot 지문 고정으로 보장하고, 같은 입력의 두 실행 출력 hash 동일로 검사한다.

## 6. 검증·완료 기준

구현 정밀화: 전역 지점 패턴은 seed 전용이다. 이와 별개로 공정위 유일 브랜드의 **정확한 소진공 상호**가 있고 별도 지점 필드·주소/층호·인허가1:1·전체 상호 동등 비교까지 충족하면 `semas_address_corroborated` 추정을 허용한다. catalog 전체 이름 뒤 `점`을 붙여 전역 매칭하는 규칙은 없다. 두 원천 상호가 단지 같은 브랜드 접두사를 포함하는 것만으로는 부족하다. 주소만 일치하거나 모호한 층호·복수 인허가가 있으면 보류한다. seed 지점 토큰의 구현 상한은40자다. 실제 출력은 검수 seed별 집계와 catalog 집계만 포함하며 원천 브랜드별 상세 분포는 stdout에 무제한 출력하지 않는다.

API 키 정규화는 기존 수집기와 동일한 `unquote` 규칙을 신규 모듈에서 사용하며 기존 코드는 변경하지 않는다. snapshot의 메타데이터와 rows를 포함한 envelope hash 및 행 content hash를 모두 검사한다. fsync한 같은 디렉터리 임시 파일을 hard link로 배타 공개하여 기존 파일 덮어쓰기와 불완전 최종 파일 노출을 막는다.

의미 있는 unit 검사는 이름 오탐 경계·복합 브랜드 identity·짧은 이름, 외부 bool 충돌, API 에러/키 인코딩·비밀값 미노출·반환 크기/페이지/기준월/중복/부분응답·snapshot변조·주소 중복/현재·과거를 포함한다. 최소 사례: `본죽`/`본죽 강남점`/`본죽(강남점)` 양성, `본죽강남점` 보류, `원조본죽집`·`본죽집` 비후보, `본죽&비빔밥 OO점`은 본죽&비빔밥, 미승인 꼬리가 붙은 `본죽&…`은 본죽으로 내려가지 않음, catalog 브랜드명+`점` 접미 비매칭, 공백 정규화 순서, legacy false+직영 체인 추정의 별도 구간, 같은 건물 다른 층·복수 후보·브랜드 토큰 없는 주소 단독, 폐업/개업일>기준월 기록의 주소 보완 거절, 페이지별 기준월/totalCount 변화·고유ID≠totalCount·HTTP200 XML 오류·예외 메시지 내 키 미노출. 로컬 실제 API 수집은 무결성 검사를 통과한 때만 완료로 기록한다. 실제 인허가 dry-run·기존 일반/격리 회귀·ruff/format/mypy를 수행한다.

사용자 승인 반영 및 seed/수집 설계를 실제 Claude Code가 먼저 검수하고, 구현 후 한 번 더 실제 코드·문서를 검수한다. 구현→검증 결과·한계·후속 v2/FE 연결은 이 문서에 추가한다. 자료를 확보하지 못한 확정 소속/직영·가맹 구분/역사 소속은 unknown 유지, 보류 이유를 기록한다.

### 7.1 실제 Claude Code 설계 검수 1회차 (2026-11-15, 구현 전)

- 범위: 이 MD만 Read/Edit. 제공된 `etl/brands/client.py`·`etl/brands/matching.py`·`app/services/store_scope.py` 발췌는 자료로만 대조했다. 셸·DB·네트워크·git·실제 API 호출은 하지 않았으며 1절의 호출 결과는 검증하지 않고 작성자 기록으로 둔다. 구현 코드는 아직 없으므로 구현 검수가 아니다.
- 수정한 차단 사항:
  1. 지점 패턴이 공정위 catalog 전체에도 적용될 여지 → catalog 경로는 전체 이름 정확 일치만, 지점 패턴은 seed 별칭 전용으로 한정(전역 오탐 방지).

  4. legacy `is_franchise=false`를 직영 체인 소속과 conflict로 처리 → 가맹 축과 소속 축을 분리하고 별도 비교 구간으로 보류.
  5. 주소 "전체 문자열 동일"은 두 원천 형식 차이로 비현실적이면서, 반대로 주소만으로 연결하면 복합상가 오연결 위험 → building_key/도로명 기본 키+층/호 비모순+1:1, 이름에 승인 별칭이 있는 보류 기록에만 적용.

### 7.2 실제 Claude Code 구현 검수 2회차 (2026-11-15)

- 범위: 이 MD만 Read/Edit. 요청에 포함된 `etl/chains/{__init__,__main__,common,compare,linking,matching,registry,semas,snapshot}.py`, 테스트 4개, 기존 `etl/brands/client.py`·`etl/brands/matching.py`·`app/services/store_scope.py` 발췌와 작성자 실행 기록을 자료로만 대조했다. 셸·DB·네트워크·git·테스트 실행은 하지 않았다. `etl/chains/registry.json`, `etl.brands.catalog`(normalize_name/parse_json), `Store.date_flag`의 정상값 표현, `app.core.operations.logged_import`의 허용 source는 입력에 없어 직접 확인하지 못했다. 아래 실행 수치는 검증한 값이 아니라 작성자 기록이다.
- MD 수정: 3절 지점토큰 문자 집합·길이 상한을 구현(`[가-힣a-z0-9][가-힣a-z0-9 ._-]{0,39}(지점|점)`, 40자)과 일치시켰다(이전 15자/영숫자·공백만 서술은 6절과도 불일치).

확인된 적합 사항(현재 범위):

- 오탐 경계: 지점 패턴은 `branch_patterns`가 있는 seed에만 적용되고 catalog 경로(`origin=ftc_exact`)는 validator가 패턴/짧은 별칭을 금지하며 정확 일치만이다. 전역 contains/fuzzy/LLM 판정 없음. 별칭은 (법인 접두사 제거 후) 앞부분 고정이며 `원조본죽집`·`우리집스타벅스`가 후보가 되지 않는다. `_BRANCH` fullmatch·거절어·다른 별칭 포함 시 보류, 미승인 `본죽&…` 꼬리는 짧은 별칭 무구분자 보류로 내려가 본죽으로 하향 매칭되지 않는다. 동일 별칭 다중 브랜드는 첫 브랜드 선택 없이 conflict다.
- 짧은 이름·두 본 브랜드: `본죽`은 seed의 `approved_short_aliases` 명시 시에만 허용되고 catalog의 3글자 하한은 그대로다. `본죽`과 `본죽&비빔밥`은 별도 key/UUID이며 같은 본부(JNG)라는 이유로 합치지 않는다. 더 긴 승인 별칭 `본죽&비빔밥`이 먼저 정렬되어 `본죽` 경로는 짧은 별칭 무구분자 보류가 되므로 conflict 없이 본죽&비빔밥이 된다.
- 운영 형태: 법인 접두사는 seed 승인분만 제거하며 접두사 단독으로는 후보가 없다. plan/summary에 `operation_type=unknown`·`time_basis=observed_record`·`estimate_not_contract_or_historical_membership`을 둔다. legacy false + 추정은 별도 구간으로 집계하고 외부 값을 덮지 않는다.
- 주소 보완: 이름이 승인 별칭(또는 catalog 정확 별칭)으로 시작하는 unknown 기록에만, 같은 lot/road 키에서 브랜드 판정된 소진공 점포 1개·인허가 영업 적격 기록 1개·층/호 비모순·(법인 접두사 제거 후) 전체 상호 = 소진공 상호/상호+지점 동등일 때만 `semas_address_corroborated` estimated다. 토큰 없는 주소 단독은 `address_only_candidate` 보고만 한다. 폐업·결측/플래그 날짜·임시·기준월 말 이후 개업은 제외된다. catalog 브랜드는 소진공 지점 필드가 있는 특정 점포의 정확 결합만 허용되어 전역 `점` 접미 규칙이 생기지 않는다. provider의 해석 불가 층/호는 비모순으로 취급하지 않는다.
- 수집 보안/한계: 고정 endpoint·서울11·I2 query, 쓰기 기능/임의 URL 미지원, redirect/재시도 0(호출 측 follow_redirects=True client에도 요청별 False), 요청 20초+스트림 60초 점검, 페이지 5MiB·누적 256MiB·251요청·25만 행 상한, totalCount 0/초과의 사전 실패, 모든 페이지 기준월/total 동일·pageNo/numOfRows/페이지 행 수, 행별 지역·업종·필수 필드, 고유 ID=totalCount, 첫 페이지 재확인을 구현했다. 키는 `unquote` 1회(`+` 보존) 후 params 전송, URL 로그 억제, `fail()`이 `from None`으로 예외 체인을 끊으며 CLI의 일반 예외도 고정 코드만 출력한다. 최소 projection만 저장하고 전화/대표자 등 추가 필드는 버린다(테스트 존재). 좌표 무효는 쌍으로 null이며 0/교환 보완 없음.
- snapshot: envelope SHA256(manifest 포함)과 행 content hash, schema/endpoint/query/consistency/기준월/관측시각/요청 수=ceil(행/1000)+1/중복 ID를 재검증한다. 저장은 저장소·다른 Git checkout 밖 경로만, fsync 임시 파일의 hard link 배타 공개라 덮어쓰기·부분 파일 노출이 없다.
- 비교: 로컬 대상 검사 후 READ ONLY REPEATABLE READ·60초/잠금5초, (source, license_no) C 정렬 스트리밍, legacy catalog 내용 hash/행 수 재검증, stores/legacy 5테이블 쓰기 없음. stdout은 집계·지문·내부 UUID뿐이고 원문 상호/주소/관리번호는 명시 외부 plan 파일에만 간다. 두 번의 스트리밍은 같은 RR 스냅샷이다. 결과는 set 순회 순서에 의존하지 않는다(후보 1개일 때만 채택).

차단 사항(이번 범위 안에서 보완 필요):

1. **seed↔공정위 catalog 대응 상태가 기록·보고되지 않는다.** 3절은 seed마다 수집 catalog의 대응 복합키 있음/없음/복수를 사실대로 기록하도록 요구하지만, `extend_catalog`는 승인 ref가 catalog에 없는 경우를 알리지 않고, 3글자 미만/비외식/반복 ID 필터가 승인 ref 검사보다 먼저 `continue`되어 `본죽` 같은 짧은 승인 ref의 이름 변경(`approved_catalog_alias_changed`)도 검사되지 않는다. 또 seed에 ref가 없거나 ref가 바뀐 경우 같은 정규화명의 catalog 행이 `ftc_exact`로 추가되어 seed 별칭과 정확 일치 충돌(conflict)이 생기는데, 이것이 seed 집계에서 조용히 빠진다(오탐은 아니지만 `본죽&비빔밥` 정확명 등의 건수가 원인 표시 없이 줄 수 있다). 보완: 승인 ref 검사를 필터보다 먼저 수행하고, seed별 `ftc_link=present|absent|multiple|name_changed`와 seed 별칭·catalog 정확명 충돌 수를 summary(원문 이름 없이 seed key 기준)에 넣는다. 충돌은 실패 또는 명시 conflict 사유(`seed_catalog_name_collision`)로 구분한다. 테스트의 `BRD_20141221`은 다른 관리번호(`BRD_20080100243`)와 자릿수가 달라 registry 실제값과 수집 2025 catalog의 실제 복합키로 대응 여부를 확인해 기록해야 한다.
2. **legacy 비교가 3절 계약보다 거칠다.** `legacy_positive`는 legacy true 또는 A안 정확명 매칭 행이 새 추정과 *같은 브랜드인지* 비교하지 않는다(legacy 매칭은 브랜드 없이 키 집합만 읽는다). 이 상태로는 3절의 "같은 브랜드면 일치, 다르면 conflict"가 구현되지 않았고, `legacy_positive` 수치가 브랜드 일치로 오독될 수 있다. 보완(둘 중 하나): legacy 매칭의 공정위 복합키/brand_id를 읽어 새 추정의 `ftc_refs`와 비교해 `legacy_same_brand|legacy_different_brand|legacy_brand_unresolved`로 나누거나, 최소한 집계명을 `legacy_positive_brand_unchecked`로 바꾸고 3절에 브랜드 수준 비교를 v2 전 후속으로 명시한다. legacy positive인데 새 판정 unknown인 건수도 함께 보고해야 v2 이행 시 누락을 볼 수 있다.
3. **실제 dry-run 최종값과 주소 보완 실효성이 미확정이다.** 작성자 기록상 최종 재실행이 진행 중이므로 8,871/346,964/2,032와 seed별 수치는 최종값이 아니다. 최종 실행에서 (a) 같은 입력 2회의 `plan_sha256`·summary 동일, (b) `reasons.semas_address_corroborated`·`address_only_candidate`·`multiple_outlets_or_licenses` 건수, (c) conflict 수와 원인을 기록해야 한다. 특히 `eligible()`은 `not row.get("date_flag")`를 정상으로 가정하므로, `stores.date_flag` 정상값이 NULL이 아닌 문자열(예: 정상 코드)이면 주소 보완이 전부 0건이 된다(오탐은 아니나 기능 무효). 정상값 표현을 확인하고 보완 0건이면 원인을 기록한다.

1. **두 본 브랜드 identity 오배정 경로가 남아 있다.** `본죽 비빔밥 강남점`·`본죽 앤 비빔밥 강남점`처럼 공백으로 쓴 형제 브랜드 상호는 승인 별칭(`본죽&비빔밥`, `본죽앤비빔밥` 등)과 정확히 같지 않아 그 경로가 실패하고, 짧은 별칭 `본죽` + 공백 구분자 + 지점토큰 `비빔밥 강남점`(또는 `앤 비빔밥 강남점`)이 `_BRANCH`에 맞고 `_DENIED`(`비빔밥집`만 있음)·다른 별칭 포함 검사(`본죽&비빔밥` 문자열 아님)를 모두 통과해 **`bonjuk-kr`로 estimated**된다. 체인 소속 자체는 같은 본부라 크게 틀리지 않지만 3절이 금지한 "지점토큰의 메뉴명/다른 브랜드어"를 통과시키고 본죽·본죽&비빔밥 별도 identity를 섞는다(실제 신고 상호에서 흔한 표기다). 보완(택1, 최소안 충분): (a) `_DENIED`에 `비빔밥`을 추가(`죽`은 `죽전점` 등 지명 오거절이 있어 추가하지 않음), 또는 (b) 지점토큰에서 공백·`&`·`앤`을 제거한 `별칭+토큰` 앞부분이 다른 seed 별칭의 같은 정규화형으로 시작하면 `sibling_brand_ambiguous` unknown. 회귀: `본죽 비빔밥 강남점`·`본죽 앤 비빔밥 강남점`·`본죽 & 비빔밥 강남점`은 본죽으로 추정되지 않고, `본죽 죽전점`은 본죽 양성을 유지. 수정 후 실제 dry-run을 재실행해 본죽/본죽&비빔밥 seed 건수·plan hash 변경과 반복 동일성을 7.3에 갱신한다(비공개 plan에서 현재 해당 패턴 건수를 먼저 세어 영향 규모를 기록하면 좋다).

### 7.7 실행 증빙과 Codex 최종 확인

실제 Claude Code2.1.322 비대화형 CLI를4회 실행했다.
