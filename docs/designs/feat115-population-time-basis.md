## 1. 원천 검증

## 2. 독립 계산 모듈

`app/analysis/day_night.py`는 DB/HTTP/설정/서비스에 의존하지 않는 순수 함수다. 공개 라우터·activity/Risk/AI·품질 진단기에는 연결하지 않는다. 이 계산 모듈은 공식 근거·공간/모집단 완전성·선택 날짜를 검증하는 수단이 아니다. 실제 소비자를 연결하기 전에 동일 격자·원천·행정동 구성·관측일과 모든 총계의 공개 여부를 별도로 검증해야 한다.

- 입력은 시간00~23 순서의 길이24 tuple이다. 각 원소는 Decimal 또는 None이다. None은 상위에서 결측/비공개/행 부재 등으로 해당 총계를 제공할 수 없는 상태를 뜻할 뿐, 그 원인 상태를 이 모듈이 합치거나 원자료에서 지우지 않는다. 상위는 비공개·셀 결측·행 부재를0으로 바꾸지 않고 None으로 전달하고 원인과 provenance를 보존해야 한다.
- 유효 값은 유한·0이상·원천 Numeric(20,5) 범위(1e15 미만)/소수5자리 이하다. bool/int/float/str/음수/비유한/범위·정밀도 초과는 값이 없는 고정 오류로 거절한다. 입력 범위는 이 내부 함수의 수치 계약이며 향후 합산 타입은 별도 검토한다.
- 모든 입력을 검사하고 None이 하나라도 있으면 불완전 시간 인덱스와 incomplete 상태, 수치 전부 None을 반환한다. partial SUM·0 채움·비공개 추정은 하지 않는다.
- 같은 날짜에서 D=06..17 합, N=00..05+18..23 합이다. 날짜에 걸친 연속 야간 체류 분석이 아니다. SpotON 구간이며 서울시 홈페이지의 주야간 정의를 대체하지 않는다.
- 비중은 D*100/(D+N), 배수는 D/N, 평균은 D/12·N/12다. 비중만 마지막에 HALF_UP 소수1자리, 야간은 표시된 주간의100% 보수로 계산한다. 합계를 하루 고유 방문자 수로 표시하지 않는다.
- Decimal localcontext precision50·ROUND_HALF_UP을 명시해 전역 precision/rounding 변화와 무관하게 계산하고 전역 설정을 보존한다. 평균/배수는 이 문맥의 Decimal 결과이며 표시용 인원 반올림은 별도다.
- D=N=0은 zero_total·비중/배수 None·평균0이다. D>0,N=0은100/0%·배수None, D=0,N>0은0/100%·배수0이다. 정상 수치는 calculated 상태이며 이는 산술 계산 성공만 의미한다.
- frozen dataclass 출력은 repr=False로 값의 우발적 노출을 줄이고 로그/외부 전송을 추가하지 않는다. validation 실패에는 입력값을 넣지 않는다.

## 4. Codex 최종 결정

Claude 검토의 조건을 채택한다. 입력은 정확한 tuple24개, 원소는 정확한 Decimal 또는 None, exponent>=-5로 제한한다. 양수 지수는 범위 안이면 허용하며 부호 있는0은 양수0으로 정규화한다. 구조→모든 원소→None 순서로 검사하고 불완전 시간은 전체 오름차순 tuple로 반환한다. 잘못된 입력은 `population_hours_invalid` 고정 ValueError로 처리한다.

새 Context의 prec50/ROUND_HALF_UP/Emin/Emax/clamp/traps를 명시해 전역 문맥을 상속하지 않는다. 비중은 D*100/(D+N) 후0.1 quantize, 야간은100.0의 보수다. 합계는 day_total/night_total, 산술 상태는 calculated/incomplete/zero_total이며 공식 검증 상태가 아니다. 평균/배수는50자리 문맥의 미정규화 Decimal 결과다. 결과 전체 repr=False·frozen을 적용한다.

비공개·행 부재·셀 결측의 원인과 provenance는 상위가 보존하며 이 모듈의 None을 원인 상태로 재해석하지 않는다. 독립 산술 테스트에24개 시각·최댓값·전역 traps/Emax·오류 우선순위·음의0·타입/자릿수 경계를 추가한다. API pending 검사의 실제 이름과 서비스 import 부재를 확인한다. 2026-11-14 사용자가 공식 답변은 아직 없으므로 문의 초안으로 진행하라고 답했다. 따라서 공식 근거/API 연결 후속은 열린 상태로 유지한다.

### 4.1 원천 적용 가능성(계산 범위와의 경계)

- 우려: 함수는 날짜·원천·모집단 인자를 받지 않으므로 "같은 날짜", "동일 모집단"은 호출자 계약일 뿐 함수가 보장하지 못한다. `calculated` 상태명이 "검증된 수치"로 오독될 수 있다.
- 우려: 공식 예제의 `*` 대체 코드를 쓰지 않는다는 정책은 있지만, 상위에서 비공개 값을 0으로 바꿔 넘기면 이 함수는 실제0과 구분하지 못하고 `calculated`/`zero_total`을 낸다.
- 우려: 24시간 합은 인원×시간(person-hour) 성격이다. 주야 모두 12시간이라 비중은 평균 비중과 같아 산술적으로 일관되지만, D·N 합계 자체를 인원으로 표시하면 안 된다.
- 수용 조건:
  1. 모듈 docstring과 상태 설명에 "calculated = 산술 성공, 원천·모집단·날짜 검증 아님"을 문장으로 명시한다.
  2. 상위 계약으로 "비공개/`*`/행 부재 → None, 0으로 변환 금지"를 이 설계와 원천 보고서 양쪽에 적는다.
  3. 출력 필드명은 `day_total`/`night_total`처럼 합계임을 드러내고, `population`/`visitors` 같은 인원 의미 이름을 쓰지 않는다.

### 4.2 Decimal 문맥

- 우려: `localcontext()`에 현재 문맥을 복사해 prec/rounding만 바꾸면 전역의 traps(예: Inexact/Rounded 활성)·Emax/Emin·clamp가 상속돼 전역 변화와 "무관"하다는 조건이 깨진다.
- 우려: 비중을 `D/(D+N)*100`으로 계산하면 나눗셈 결과가 50자리로 한 번 반올림된 뒤 곱셈·quantize가 이어진다. 입력 한계(합 < 1.2e16, 소수5자리)에서 참값과 반올림 경계(x.x5)의 거리는 50자리 오차보다 충분히 커서 이중 반올림 오류는 사실상 없지만, 계산 순서는 문서로 고정하는 편이 안전하다.
- 우려: 평균·배수는 1/12처럼 무한소수가 되어 50자리 유효숫자 Decimal로 나오며, 지수(exponent) 표현이 값마다 달라진다(`Decimal('1')` vs `Decimal('1.0')`). 소비자가 `str()`로 표시하면 형태가 들쭉날쭉해진다.
- 수용 조건:
  1. `localcontext(Context(prec=50, rounding=ROUND_HALF_UP, traps=[InvalidOperation, DivisionByZero, Overflow]))`처럼 **새 Context**를 명시한다(Emax/Emin 기본값 포함).
  2. 비중은 `(D * 100) / (D + N)`을 계산한 뒤 같은 문맥 안에서 `quantize(Decimal('0.1'), rounding=ROUND_HALF_UP)`로 한 번만 반올림하고, 야간 = `Decimal('100.0') - 주간표시값`으로 정의한다. 두 값의 합이 정확히 `100.0`임을 검사한다.
  3. 평균·배수는 "50자리 문맥 결과, 미정규화, 표시 반올림은 소비자 책임"이라고 명시하고, 테스트는 문자열이 아닌 Decimal 값 동등성으로 비교한다.
  4. 계산 중 예외가 나도 전역 문맥이 복원되는지(`with` 블록) 검사한다.

### 4.3 None 처리

- 우려: "불완전 시간 인덱스"가 첫 번째 결측만인지 전부인지, 자료형(tuple/list, 정렬 여부)이 정해져 있지 않다.
- 우려: None과 잘못된 값(float 등)이 섞인 입력에서 오류와 incomplete 중 무엇이 우선인지 정해져 있지 않다. "모든 입력을 검사"는 오류 우선으로 읽히지만 명시가 없다.
- 우려: 주간 12시간이 모두 있고 야간에만 None이 있을 때 D 합계를 노출하면 부분합이 새는 것이다.
- 수용 조건:
  1. 결측 인덱스는 **모든** 결측 시각의 오름차순 `tuple[int, ...]`이다.
  2. 우선순위: 구조 오류(타입·길이) → 원소 값 오류 → None 판정. 잘못된 값이 하나라도 있으면 None이 있어도 예외다.
  3. incomplete면 D·N 합계·평균·비중·배수가 모두 None이다(주간 전부 유효 + 03시 None 케이스로 검사).
  4. 24개 전부 None도 incomplete(인덱스 0..23)로 처리한다.

### 4.4 입력 검증

- 우려: `Decimal('sNaN')`은 비교 연산만으로 InvalidOperation을 일으킨다. 유한성 검사를 대소 비교보다 먼저 해야 고정 오류 계약이 지켜진다.
- 우려: `Decimal('-0')`은 `>= 0`을 통과하고, 전부 -0이면 합·평균이 `-0`으로 출력될 수 있다.
- 우려: "소수5자리 이하"가 지수 기준(`Decimal('1.000000')`의 exponent -6 거절)인지 값 기준(수치상 동일하므로 허용)인지 불명확하다. `Decimal('1E+3')`처럼 양수 지수도 기준이 필요하다.
- 우려: bool은 int의 하위 타입이고, Decimal 하위 클래스나 list 입력의 허용 여부가 정해져 있지 않다.
- 우려: 고정 오류여도 예외 체인(`__context__`)에 원래 InvalidOperation 등과 입력값이 남을 수 있다.
- 수용 조건:
  1. 검사 순서: `type(x) is Decimal`(하위 클래스·bool·int·float·str 거절) → `is_finite()` → 부호 비트(`is_signed()`로 -0도 거절하거나 `copy_abs()`로 정규화 중 하나를 명시) → 범위 `< Decimal('1e15')` → 소수 자릿수.
  2. 소수 자릿수 기준을 한 가지로 확정한다(권장: `as_tuple().exponent >= -5`, 지수 기준. 양수 지수는 범위 검사로 처리).
  3. 컨테이너는 정확히 `tuple`, 길이 24. list·generator·길이 23/25는 구조 오류다.
  4. 예외는 고정 메시지(시각 인덱스는 넣어도 되지만 값은 넣지 않음)를 쓰고 `raise ... from None`으로 체인을 끊는다. 메시지 문자열 동등성을 검사한다.

### 4.5 경계(시간·수치)

- 우려: 경계 6개 시각만 검사하면 중간 시각의 오분류(예: 범위 상한 off-by-one)를 놓칠 수 있다.
- 우려: 수치 상한에서 합 정확성이 보장되는지 검사가 없다.
- 수용 조건:

  4. 최소 양수 `0.00001`을 한 시각에만 넣는 케이스로 소수 하한을 검사한다.

### 4.6 0분모와 상태

### 6.2 Decimal 문맥

- 새 `Context(prec=50, ROUND_HALF_UP, Emin=-999999, Emax=999999, capitals=1, clamp=0, flags=[], traps=[InvalidOperation, DivisionByZero, Overflow])`를 쓰므로 전역 prec/rounding/traps/Emax/Emin/clamp/flags를 상속하지 않는다. `with localcontext(...)`라 정상·예외 종료 모두에서 전역 문맥이 복원된다. 적합.
- 문맥 밖에서 실행되는 검증 연산(`is_finite`, 유한값 간 `<`/`>=`, `as_tuple`, `is_zero`, `copy_abs`)은 유한값에 대해 문맥 정밀도·반올림을 쓰지 않고 신호도 내지 않는다. sNaN/NaN은 `is_finite()` 단락 평가로 비교 전에 거절된다. 적합.
- 합계 정확성: 입력이 소수5자리·1e15 미만이면 12개 합은 1.2e16 미만, 유효숫자 최대 22자리라 50자리 문맥에서 반올림이 없다. `day * 100`(≤23자리)과 `total`도 정확하다.
- 비중 이중 반올림: `day*100/total`은 50자리로 한 번 반올림된 뒤 0.1로 quantize된다. 참값이 x.x5 동점이면 나눗셈이 정확히 끝나 동점이 유지되고, 동점이 아니면 동점과의 거리는 최소 1/(20·T·10^5)(T<2.4e16)로 약 2e-23 이상이며 50자리 오차(≤1e-47 수준)보다 훨씬 크다. 따라서 이중 반올림 오류는 생기지 않는다. `Decimal("100.0") - share`도 정확하다.
- 평균·배수는 미정규화 50자리 결과다. 설계와 docstring 모두 이를 소비자 표시 책임으로 둔다. 적합.

### 6.3 입력 검증·결측·경계

- 순서: 구조(`type(hours) is tuple`, 길이24) → 원소별(`type is Decimal` → `is_finite` → `<0` → `>=1e15` → exponent>=-5) → None 판정. 앞쪽 시각에 None이 있어도 뒤쪽 잘못된 값이 예외를 낸다. 4.3-2 충족.
- 예외는 except 블록 밖에서 발생하므로 `__context__`/`__cause__`가 없다. `from None`이 없어도 4.4-4의 의도는 충족된다. 메시지에는 값과 인덱스가 모두 없다.
- `-0`은 허용 후 `copy_abs()`로 정규화한다. 합계 시작값이 `+0`이라 결과 부호도 양이다. §4 결정과 일치.
- 결측: 모든 None 시각을 오름차순 tuple로 반환하고 수치 필드는 전부 None이다. 부분합이 새지 않는다. 적합.
- 경계: `DAY_HOURS=6..17`, `NIGHT_HOURS=0..5,18..23`로 서로소이고 각 12개다. Numeric(20,5)의 최대값 `999999999999999.99999`는 허용되고 `1E+15`는 거절된다. 적합.
- 비차단 관찰:
  1. 지수 상한이 없어 `Decimal("0E+999999999")` 같은 큰 양수 지수의 0도 허용된다. 값은 0이고 합계 지수는 시작값 `_ZERO` 때문에 0이 되므로 현재 산술 오류는 없다. 다만 Numeric(20,5) 표현과는 다르다. 원하면 `exponent <= 14` 같은 상한을 두거나, 허용한다는 사실을 테스트로 고정한다.
  2. `DayNightSummary`는 직접 생성할 때 상태·필드 조합 불변식을 검사하지 않는다(예: `status="incomplete"`에 `day_total` 지정). 현재 생성 경로는 함수뿐이라 결함은 아니다. 공개 타입으로 확장할 때 `__post_init__` 검사나 생성자 비공개화를 검토한다.
  3. 4.1-3과의 이름 일관성: 합계는 `day_total`/`night_total`로 적합하다. 평균 필드 `day_avg_population`/`night_avg_population`은 "시간당 평균 추정치"라 인원 의미 이름이 완전히 틀리지는 않지만 "하루 인구"로 오독될 수 있다. 소비자 연결 전에 `day_hourly_mean` 같은 이름이나 docstring 한 줄을 검토한다. 비차단.
