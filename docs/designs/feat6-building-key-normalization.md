## 핵심 계약

### 1. canonical 형식

```text
{자치구}-{법정동}-{본번}-{부번}
```

- `마포구 서교동 123-4` → `마포구-서교동-123-4`
- `마포구 서교동 123` → `마포구-서교동-123-0`
- `마포구 상암동 산12-3` 또는 `산 12-3` → `마포구-상암동-산12-3`
- 본번·부번은 ASCII 10진 정수로 정규화한다. `0012-03`은 `12-3`이고, 부번을 생략하거나 `-0`으로 쓰면 둘 다 `0`이다.
- 값 범위는 본번 1~9999, 부번 0~9999다. 필지고유번호(PNU)가 본번·부번을 각각 4자리로 쓰는 것을 근거로 한다. 숫자 문자열은 leading zero를 포함해 1~4자리만 허용하고, 범위를 벗어나면 `INVALID`다.
- 산 여부는 key의 본번 앞 `산`으로만 표현한다. 음수·소수·문자 혼합 지번과 숫자 없이 `산`만 있는 지번은 허용하지 않는다.
- `{자치구}`에는 `SEOUL_AUTHORITY_CODES`의 값 문자열을, `{법정동}`에는 정규화된 법정동 토큰을 그대로 쓴다. key 구분자는 ASCII `-`로 고정한다. 원 주소의 공백·괄호·건물명·`번지`·`외 n필지`는 key에 넣지 않는다.
- 결정성: 정규화 결과가 같은 입력은 항상 같은 결과(같은 key 또는 같은 failure)를 낸다. 시각·로캘·환경변수·외부 조회·행 처리 순서에 의존하지 않는다.

### 2. 파서 입력과 반환

순수 모듈 `etl/address/building_key.py`를 만든다.

```python
@dataclass(frozen=True, slots=True)
class BuildingLot:
    gu_name: str
    legal_dong: str
    main_no: int
    sub_no: int
    is_mountain: bool

    @property
    def key(self) -> str: ...

class BuildingKeyFailure(StrEnum):
    EMPTY = "empty"
    NON_SEOUL = "non_seoul"
    GU_MISSING = "gu_missing"
    GU_CONFLICT = "gu_conflict"
    LEGAL_DONG_MISSING = "legal_dong_missing"
    LEGAL_DONG_UNSUPPORTED = "legal_dong_unsupported"
    LOT_MISSING = "lot_missing"
    AMBIGUOUS = "ambiguous"
    INVALID = "invalid"

@dataclass(frozen=True, slots=True)
class BuildingKeyResult:
    lot: BuildingLot | None
    failure: BuildingKeyFailure | None
```

- `parse_jibun_address(address: str | None, *, authority_code: str | None = None) -> BuildingKeyResult`는 성공과 실패를 예외 대신 typed result로 돌려준다. 그래야 대량 ETL에서 건별 실패를 집계할 수 있다.
  - 어떤 `str` 입력에도 예외를 던지지 않는다. `None`, 빈 문자열, 공백뿐인 문자열은 `EMPTY`다.
  - `str`가 아닌 타입은 프로그래밍 오류이므로 `TypeError`를 낸다. 메시지에는 값 없이 타입명만 넣는다.
- `BuildingKeyResult`의 `lot`과 `failure`는 정확히 하나만 값을 가져야 한다. `__post_init__`에서 이 조건을 검증한다.
- 실패 사유가 여러 개 해당하면 아래 단계 순서상 처음 실패한 단계의 사유 하나만 반환한다. 그래야 집계가 결정적이다.
  1. 입력 검사: `EMPTY`, `INVALID`(길이, 금지 문자)
  2. 전역 구조: `AMBIGUOUS`(나열 구분자), `INVALID`(괄호 불균형·중첩)
  3. 시·도와 관청 코드: `NON_SEOUL`
  4. 자치구: `INVALID`(구 이름 붙여쓰기), `GU_CONFLICT`, `AMBIGUOUS`(서울 문맥 없는 자치구), `GU_MISSING`
  5. 법정동: `LEGAL_DONG_MISSING`, `LEGAL_DONG_UNSUPPORTED`, `AMBIGUOUS`(법정동과 지번 사이 괄호·여분 토큰)
  6. 지번: `LOT_MISSING`, `INVALID`(형식·범위), `AMBIGUOUS`(대표 지번 직후 숫자, `외` 형식 위반)
- `build_from_parts(gu_name, legal_dong, main_no, sub_no=None, is_mountain=False) -> BuildingKeyResult`는 카카오 등 구조화 응답을 쓸 후속 작업용이다. 이번 작업에서는 외부 API를 호출하지 않는다.
  - 원천 파서와 같은 검증 함수를 쓴다. `gu_name`은 25개 자치구 값과 정확히 일치해야 한다. 빈 값은 `GU_MISSING`, 그 밖의 불일치는 `NON_SEOUL`이다.
  - `legal_dong`은 5절의 정규화를 거친 뒤 4절의 법정동 토큰 규칙을 그대로 적용한다. 구조화 입력이라도 `로` 법정동은 허용하지 않는다. 원천 파서와 생성 함수의 지원 범위를 같게 유지하기 위해서다.
  - `main_no`·`sub_no`는 `int`만 받고 `bool`은 거부한다(`bool`이 `int`의 하위 타입이기 때문). 범위는 1절과 같다. `is_mountain`은 `bool`만 받는다. 위반은 `INVALID`다.
- 파서는 주소 원문을 수정하거나 반환하지 않는다. 원문은 기존 `address_jibun`에 그대로 남는다.

### 3. 자치구 판정

- `SEOUL_AUTHORITY_CODES`의 공식 25개 매핑을 단일 원천으로 재사용한다. 자치구 이름 집합도 이 매핑의 값에서 파생하며, 별도 중복 목록을 만들지 않는다.
- `authority_code`는 다음과 같이 분류한다.
  - 25개 자치구 코드 → 해당 자치구가 관청 자치구다.
  - 서울 본청 `6110000`, `_ALL`처럼 자치구가 아닌 서울 코드 → 관청 자치구가 없는 것으로 본다. fallback에도, 충돌 검사에도 쓰지 않는다. 다만 서울 문맥으로는 인정한다.
  - `None` 또는 빈 값 → 관청 자치구 없음, 서울 문맥 없음.
  - 그 밖의 값(타 시·도 코드, 형식 오류) → `NON_SEOUL`. 주소가 서울이어도 임의로 채택하지 않는다.
- 서울 접두는 첫 토큰이 정확히 `서울특별시`, `서울시`, `서울` 중 하나일 때만 인정한다. 띄어 쓴 `서울 특별시`는 인정하지 않으며, 접두 뒤 토큰 규칙에 따라 거절된다.
- 다음은 `NON_SEOUL`이다.
  - 첫 토큰이 서울 접두가 아니면서 `시`·`도`로 끝나는 경우(예: `부산광역시`, `경기도`). 서울 법정동은 `동`·`가`·`로`로 끝나므로 이 판정이 서울 법정동을 잘못 거절하지 않는다.
  - 자치구 위치의 토큰이 `구`로 끝나지만 25개 값이 아닌 경우(예: `해운대구`, `수정구`). 서울 접두가 있든 없든 같다.
  - `경기`, `부산` 같은 축약형은 시·도 목록 없이 판별하지 않는다. 이런 토큰은 법정동 규칙에 맞지 않아 `LEGAL_DONG_UNSUPPORTED`나 `GU_MISSING`으로 거절되므로 key가 잘못 만들어지지 않는다.
- 자치구 토큰은 정확히 일치할 때만 인정한다. 25개 자치구 이름이나 `서울`로 시작하지만 정확히 일치하지는 않는 토큰(`마포구서교동`, `서울특별시마포구`)은 `INVALID`다. 구를 생략한 입력의 법정동 후보에도 같은 검사를 적용해, 붙여 쓴 구 이름이 법정동으로 오인되지 않게 한다.
- 주소 자치구와 관청 자치구가 모두 있으면 정확히 일치해야 한다. 다르면 `GU_CONFLICT`이며 어느 쪽도 임의로 채택하지 않는다.
- 주소에 자치구가 있지만 서울 문맥(서울 접두, 또는 25개·본청 서울 관청 코드)이 없으면 `AMBIGUOUS`다. `중구`·`강서구`처럼 타 시·도에도 있는 자치구명을 서울로 단정하지 않기 위해서다.
- 주소에 자치구가 없을 때만 관청 자치구를 fallback으로 쓴다(`서울 서교동 123`처럼 접두만 있는 경우 포함).
- 주소 자치구도 관청 자치구도 없으면 `GU_MISSING`이다. 본청 코드에 구 없는 주소가 붙은 경우도 여기에 해당한다.

### 4. 법정동과 대표 지번

허용 문법은 5절의 정규화와 토큰화를 거친 공백 단위 토큰 열이다. 주소 전체에서 숫자를 검색하지 않고 아래 위치만 읽는다.

```text
[서울접두] [자치구] 법정동 대표지번 [외 n필지] [후행 부가정보 ...]
```

#### 법정동 토큰

- 자치구 바로 뒤 토큰을 법정동으로 읽는다. 구를 생략한 입력이면 서울 접두 뒤 토큰이나 첫 토큰을 읽는다. 자동 파싱은 아래 두 형태만 한다(`re.fullmatch`, `re.ASCII`).
  - 한글로만 된 2자 이상 토큰 중 `동`으로 끝나는 것: `[가-힣]+동` (예: `서교동`, `상암동`, `여의도동`)
  - 한글 + ASCII 숫자 + `가`: `[가-힣]+[0-9]+가` (예: `종로1가`, `성수동1가`, `을지로3가`)
- 다음은 `LEGAL_DONG_UNSUPPORTED`다.
  - `로`·`길`로 끝나는 토큰. 서울에는 `세종로`처럼 `로`로 끝나는 법정동이 있다. 하지만 `양화로`·`세종대로` 같은 도로명과 형태만으로는 구분할 수 없고, 근거 있는 공식 법정동 allowlist도 이번 범위에 없다. 그래서 `로` 법정동은 이번 작업에서 지원하지 않는다. `종로구 세종로 1`은 key를 만들지 않고 실패로 집계한다. 도로명주소가 `동`/`가` 규칙을 통과하는 일은 없으므로, 도로명을 법정동으로 오인하는 일은 구조적으로 막힌다.
  - `동` 앞에 숫자가 있는 토큰(`상계1동`, `역삼1동`), `·`·`.`이 들어간 토큰(`종로1·2·3·4가동`). 행정동 표기일 가능성이 높아서, 법정동 key와 섞이면 같은 건물이 다른 key를 갖게 된다.
  - 그 밖의 접미사(`읍`, `면`, `리`, `시`, `군` 등)와 한글·숫자 외 문자가 섞인 토큰.
- 법정동 자리에 토큰이 없거나 그 자리에 지번 형태가 바로 오면(`마포구 123-4`) `LEGAL_DONG_MISSING`이다.
- 잔여 위험: 숫자 없이 `동`으로 끝나는 행정동명(법정동 여러 개를 합친 이름 등)은 allowlist 없이 구분할 수 없다. 원천 `address_jibun`이 법정동 기준이라는 전제에 의존한다.

#### 대표 지번

- 대표 지번은 법정동 토큰 바로 다음에 와야 한다. 사이에 괄호가 있으면 `AMBIGUOUS`다. 다음 토큰이 없거나 지번처럼 시작하지 않는 토큰이면(`서교동 서교빌딩 123`) `LOT_MISSING`이다. 뒤쪽 숫자를 찾아 쓰지 않는다.
- 지번 토큰은 아래 형태만 허용한다(토큰 단위 `re.fullmatch`, `re.ASCII`). 개념상 `(산)?[0-9]+(-[0-9]+)?(번지)?` 형태이며, 자릿수와 범위는 매칭 뒤 1절 규칙으로 검사한다.
  - `123`, `123-4`, `123번지`, `123-4번지`
  - `산12`, `산12-3`과 각각의 `번지` 붙임 형태
  - 따로 떨어진 `산` 토큰 + 숫자 토큰(`산 12-3`), 숫자 토큰 + 따로 떨어진 `번지` 토큰(`123 번지`)
- `[0-9-]`나 `산[0-9-]`로 시작하지만 위 형태와 완전히 일치하지 않는 토큰(`12.5`, `-3`, `12-3-4`, `123외`, `산0`)은 `INVALID`다. 범위 위반도 `INVALID`다.

#### 대표 지번 직후

- `외 n필지`: 대표 지번 바로 다음 토큰이 `외`이면 그 뒤는 `[0-9]+필지` 한 토큰이거나 `[0-9]+`와 `필지` 두 토큰이어야 한다. `외1필지`처럼 붙여 쓴 한 토큰도 허용한다. `외` 뒤 숫자는 부번·호수로 쓰지 않고 버린다. 형식이 다르면(`외 다수`) `AMBIGUOUS`다.
- 부번·호수 혼동 차단:
  - 대표 지번 직후 토큰이 `[0-9]+`만으로 되어 있거나 `-`로 시작하면 부번 유무와 무관하게 `AMBIGUOUS`다(`123 4`, `123-4 5`).
  - 부번 없는 대표 지번 직후 토큰이 `[0-9]+호`이면 `AMBIGUOUS`다(`123번지 4호`, `123 101호`). 옛 표기의 `4호`가 부번인지 호수인지 결정적으로 알 수 없기 때문이다.
  - 부번 있는 대표 지번 뒤의 `[0-9]+호`는 호수로 보고 무시한다(`123-4 101호` → `123-4`).
- 그 밖의 후행 토큰(건물명, `1층`, `지하1층`, `B1`, `162C호`, 괄호 내용)은 key 계산에서 무시한다.
  - `서초구 반포동 1109 반포래미안트리니원 162C호` → `서초구-반포동-1109-0` (`162C호`는 숫자만으로 된 호수가 아니어서 위 차단 규칙에 걸리지 않는다)

#### 나열과 괄호

- `,`, `/`, `~`, `;` 문자나 `및` 토큰이 주소 어디에든 있으면 `AMBIGUOUS`다. 후행 부가정보 안의 쉼표(`2층,3층`)도 거절된다. 대표 지번 판별 규칙을 단순하고 결정적으로 유지하기 위한 의도된 범위 축소이며, 실패 건수로 영향을 측정한다.
- 괄호는 대표 지번 뒤에서만 부가정보로 허용하며, 괄호 안 숫자는 지번으로 쓰지 않는다. 대표 지번 이전에 `(`나 `)`가 나오면 `AMBIGUOUS`다. 괄호 불균형이나 중첩은 `INVALID`다.

### 5. 안전한 정규화

정규화는 아래 순서를 고정한다.

1. 원문 길이가 1,000자를 넘으면 `INVALID`. NFKC를 하기 전에 검사한다.
2. 원문에 다음 문자가 있으면 `INVALID`.
   - 제어문자(Cc). 단 탭·CR·LF는 공백으로 취급한다.
   - 서식문자(Cf). ZWSP, BOM 등이 여기에 해당한다. 제거하면 `123​4`가 `1234`로 붙는 식으로 지번이 바뀔 수 있어서 제거하지 않고 거절한다.
   - 일반 범주 `No`(`①`, `²`, `½` 등). NFKC가 이런 문자를 ASCII 숫자로 바꿔 없던 지번을 만들 수 있다.
3. Unicode NFKC를 적용한다. 전각 숫자·괄호·공백·하이픈이 표준화되고 NFD 한글이 결합된다. NFKC 결과도 1,000자를 넘으면 `INVALID`다. NFKC는 일부 문자를 길게 확장하기 때문이다.
4. 다음 고정 목록의 하이픈 변형만 ASCII `-`로 바꾼다: U+2010, U+2011, U+2012, U+2013, U+2212, U+FE63, U+FF0D. U+2014·U+2015 같은 그 밖의 대시는 변환하지 않으며, 지번에 있으면 형식 실패가 된다. `/`, `~`, `,`, `_`는 하이픈으로 바꾸지 않는다.
5. `(`, `)` 앞뒤에 공백을 넣어 별도 토큰으로 만든 뒤, 인자 없는 `str.split()`으로 토큰화한다. 연속 공백·탭·개행은 이 과정에서 하나의 구분으로 합쳐진다.

규칙:

- 숫자는 ASCII `[0-9]`만 인정한다. 모든 정규식에 `re.ASCII`를 쓰거나 문자 클래스를 명시한다. 비ASCII 숫자(`١٢٣` 등)는 `\d`, `str.isdigit()`, `int()`에 넘기지 않는다. `int()`는 이런 문자도 변환에 성공하기 때문이다.
- 정규식은 토큰 단위 `re.fullmatch`로만 쓰고 중첩 수량자·역참조를 쓰지 않는다. 주소 전체에 대한 대형 정규식이나 `re.search` 전체 스캔은 쓰지 않는다. 처리 비용은 입력 길이에 대해 선형이다.
- 개인정보 비노출:
  - 실패 결과에는 enum만 담는다. `repr()`, 예외 메시지, 로그에 원문 주소나 그 일부(토큰, 지번)를 넣지 않는다.
  - 파서는 로그를 남기지 않는다. 성공 key도 로그에 쓰지 않는다.
  - 리포트에는 failure enum별 건수만 남긴다.

## ETL 연결

### StoreRecord 변경

- `StoreRecord`에 `building_key: str | None`을 추가한다.
- `transform_rows()`에서 `row.jibun_address`와 검증된 `row.authority_code`로 파서를 호출한다.
- 성공하면 canonical key를 저장하고, 실패하면 `None`으로 둔다. key 파싱 실패는 행 거절 사유가 아니다. 레코드는 그대로 변환·적재되므로 fetched/accepted/transformed 기존 항등식은 바뀌지 않는다.
- 파싱 실패 사유는 `TransformReport.flags`에 `building_key_<failure>`로 집계하고, 성공 건수는 `building_key_ok`로 집계한다. 기존 report 구조에 맞는 방식을 쓰되 `transformed = building_key_ok + Σ building_key_<failure>` 항등식이 성립해야 하며, 이를 테스트한다. 주소·관리번호·key 값은 리포트에 넣지 않는다.
- `address_jibun`이 비어 있으면 `building_key_empty`로 집계한다. 실패를 정상 0건처럼 숨기지 않는다.

### Repository 변경

- `building_key`를 upsert 갱신 허용 목록에 추가한다.
- BE-08에서는 후속 작업 보호를 위해 갱신하지 않았지만, BE-09부터 이 ETL의 책임 컬럼이 된다.
- 새 입력이 파싱에 실패했을 때 기존 key를 남길지 `NULL`로 갱신할지를 정해야 한다. 정제 결과의 최신성과 재현성을 위해 **새 정제 결과가 `None`이면 DB도 `NULL`로 갱신**한다. 과거의 잘못된 key를 유지하지 않는다.
  - SQL은 `building_key = EXCLUDED.building_key`를 그대로 쓴다. `COALESCE`나 `WHERE EXCLUDED.building_key IS NOT NULL` 같은 조건부 갱신은 금지한다.
  - 이 정책은 BE-09 ETL이 `building_key`의 **유일한 writer**라는 전제에서만 안전하다. 이후 BE-11 지오코딩 등 다른 경로가 `building_key`를 채우면 ETL을 재실행할 때 그 값이 지워진다. 그런 경로가 생기면 컬럼 소유권(출처 컬럼 또는 별도 컬럼)을 다시 설계하기 전까지 진행을 멈춘다(중단 조건 6).
  - 파서 규칙이 바뀌면(범위 축소 포함) 기존 key가 대량으로 `NULL`이 되거나 다른 값으로 바뀔 수 있다. 이번 작업은 실제 DB에 적재하지 않는다. 향후 실제 DB에서 실행하기 전에는 key 변경 건수와 `NULL`이 되는 건수를 보는 dry-run 리포트를 별도 게이트로 둔다.
- `floor_unit`, `location_level`, `deleted_at`, 브랜드 필드는 계속 갱신하지 않는다.
- migration은 추가하지 않는다. 기존 nullable `building_key`와 B-tree 인덱스를 사용한다.

## 테스트

### 순수 단위 테스트

모든 케이스는 기대 key 또는 기대 failure enum을 정확히 단언한다. 단순히 "실패함"만 확인하지 않는다.

- 정상: 일반 지번, 부번 없음, `-0`, 산 지번의 붙임·띄어쓰기, `번지` 붙임·띄어쓰기, leading zero(`0012-03`), 경계값 `9999-9999`.
- 법정동: `서교동`, `여의도동`, `종로1가`, `성수동1가` 성공.
- `로` 범위 축소: `마포구 양화로 123`, `마포구 양화로6길 12`, `종로구 세종대로 1`, `종로구 세종로 1`이 모두 `LEGAL_DONG_UNSUPPORTED`이고 key를 만들지 않음. 마지막은 알려진 제한으로 테스트 이름에 명시한다.
- 행정동 표기: `노원구 상계1동 123`, `종로구 종로1·2·3·4가동 1` → `LEGAL_DONG_UNSUPPORTED`.
- 후행 부가정보: 건물명, `1층`, `2층 201호`, `지하1층`, `B1`, `162C호`, `123-4(서교빌딩)`, `123-4 101호` 무시.
- 부번·호수 혼동: `123번지 4호`, `123 4`, `123 101호`, `123-4 5` → `AMBIGUOUS`.
- `외 1필지`, `외1필지`, `외 12 필지`는 대표 지번만 사용. `외 다수` → `AMBIGUOUS`.
- 자치구:
  - 구 생략 + 유효 authority_code는 fallback 성공.
  - 주소 구 + 같은 authority_code는 성공. 주소 구 + 다른 구 코드는 `GU_CONFLICT`.
  - 본청 `6110000` + 주소 구는 성공. 본청 + 구 없음은 `GU_MISSING`.
  - 서울 문맥 없는 `중구 ...`(authority None)는 `AMBIGUOUS`. 같은 주소 + 중구 코드는 성공.
  - `마포구서교동 123`, `서울특별시마포구 서교동 123` → `INVALID`.
- `NON_SEOUL`: `부산광역시 …`, `경기도 …`, `서울특별시 해운대구 …`, 타 시·도·형식 오류 authority_code.
- 그 밖의 거절: 구 누락, 법정동 누락, 읍·면·리, 지번 누락(`서교동 서교빌딩 123`), 본번 0, `00012`, `10000`, 음수·소수·`12-3-4`, 법정동과 지번 사이 괄호, 괄호 불균형·중첩.
- 나열: `,`, `/`, `~`, `;`, `및`, 후행 `2층,3층` → `AMBIGUOUS`.
- 실패 우선순위: 여러 사유를 동시에 가진 입력이 2절 단계 순서상 첫 사유만 반환하는지 확인.
- Unicode·결정성:
  - 전각 숫자, U+2212·U+2013 하이픈, NBSP·U+3000·탭·연속 공백, NFD 한글 입력이 ASCII 기준 입력과 같은 key를 내는지 확인.
  - `①`, `²`, ZWSP, BOM, 아랍-인도 숫자, U+2014 지번 → 기대 failure이고 key를 만들지 않음.
  - 같은 입력을 반복 호출하거나 입력 목록 순서를 바꿔도 결과가 같은지 확인.
- 자원 상한: 1,000자는 처리, 1,001자는 `INVALID`. NFKC 확장으로 1,000자를 넘는 입력(예: U+FDFA 반복)은 `INVALID`. 1,000자 악성 패턴(긴 숫자·하이픈·괄호 반복)도 즉시 끝나는지 확인한다.
- 무예외: 고정 seed로 생성한 임의 `str` 입력 집합에서 예외가 0건인지 확인. 새 의존성은 추가하지 않는다. 비 `str` 입력은 값이 없는 `TypeError`.
- `build_from_parts`: 원천 입력과 같은 key를 내는지, `bool` 본번, 범위 밖 번호, 25개 외 구, `세종로` 법정동 거절.
- 개인정보: 실패 결과, `repr()`, `TypeError` 메시지, `caplog`에 주소 canary 문자열이 없는지 확인.

### pipeline 단위 테스트

- 정상 주소의 `StoreRecord.building_key`와 실패 주소의 `None`을 확인한다.
- key 파싱 실패 행이 거절되지 않고 변환되는지 확인한다.
- failure enum별 report count, `transformed = building_key_ok + Σ building_key_<failure>`, fetched/accepted/transformed 기존 항등식이 유지되는지 확인한다.
- report와 로그에 주소·관리번호·key canary가 없는지 확인한다.
- 기존 BE-08 주소·원본·개인정보 최소화 테스트를 깨지 않는다.

### 실제 PostGIS 통합 테스트

- upsert의 insert, `A→B`, `NULL→A` 갱신을 확인한다. 기존 B-tree 인덱스가 존재하는지와 key 조건 조회 결과를 확인하되, 작은 테이블에서 흔들리는 실행계획(EXPLAIN) 강제 검증은 하지 않는다.
- 새 결과가 `None`이면 기존 key가 NULL로 바뀌는지(`A→NULL`) 확인한다.
- `floor_unit`, `location_level`, `deleted_at`은 계속 보존되는지 확인한다.
- 신규 building_key 통합 assertion이 실제 실행되며 skip·xfail이 0이어야 한다.

## 중단 조건

1. 대표 지번과 부가 숫자를 결정적으로 분리할 수 없어 임의 추정이 필요한 경우.
2. `로` 법정동이나 행정동 표기의 자동 파싱이 완료 조건으로 요구되는 경우. 근거 있는 공식 자료(예: 법정동코드 원천)를 확보하고 별도로 설계하기 전까지 멈춘다. 임의 allowlist를 작성해 우회하지 않는다.
3. 기존 stores 모델·migration 변경이나 실제 개발 DB backfill이 완료 조건에 필요해지는 경우.
4. 실제 PostGIS 통합 테스트가 실패·skip·미실행이거나 CI가 신규 assertion 실행을 확인하지 못하는 경우.
5. 주소 원문, 그 일부, 관리번호, 성공 key가 예외·로그·리포트에 노출되는 경우.
6. `building_key`를 쓰는 다른 writer(BE-11 등)가 생기거나, NULL 갱신 정책이 다른 작업의 데이터와 충돌하는 경우.
7. 파서가 임의 `str` 입력에서 예외를 던지거나, 1,000자 입력 처리가 선형 시간에 끝나지 않는 경우.
8. 구현 시 확인한 `SEOUL_AUTHORITY_CODES`가 25개 자치구와 서울 본청 구조가 아니거나 값이 `마포구` 같은 자치구명 형식이 아니어서 key 원천으로 쓸 수 없는 경우.

## Claude Code 검토 기록

### 2026-11-10 검토 (Claude Code)

범위: 이 파일만 처음부터 끝까지 읽고 직접 수정했다. 코드·다른 문서·Git·셸에는 접근하지 않았다. 따라서 `SEOUL_AUTHORITY_CODES`, `TransformReport`, repository upsert의 실제 구조는 확인하지 않았다.

주요 지적과 반영:

1. **도로명 오인(치명)**: 4절은 `로` 법정동을 허용하면서 테스트 절에서는 allowlist 없이 금지한다고 써서 서로 모순됐다. 원안대로라면 `마포구 양화로 123`이 `마포구-양화로-123-0`이 된다. 근거 없는 allowlist를 만드는 대신 `로`·`길` 토큰을 `LEGAL_DONG_UNSUPPORTED`로 거절하도록 범위를 줄였다. `build_from_parts`도 같은 범위로 맞췄다. `세종로`는 알려진 제한으로 남는다.
2. **법정동 표기**: 법정동 허용 형태를 `[가-힣]+동`과 `[가-힣]+[0-9]+가`로 정확히 정의했다. `상계1동`·`가동`·`·` 같은 행정동 표기는 거절하도록 했다. 이를 섞으면 같은 건물이 다른 key를 갖게 된다.
3. **부번·호수 혼동**: 부번 없는 지번 뒤의 `4호`, 대표 지번 뒤의 숫자만 있는 토큰이나 `-`로 시작하는 토큰을 `AMBIGUOUS`로 막았다. `162C호`가 통과하는 근거도 함께 적었다.
4. **지번 문법**: 토큰 단위 fullmatch, 형식 실패(`INVALID`)와 지번 없음(`LOT_MISSING`) 구분, 괄호 토큰화, `외 n필지` 허용 형태를 정했다. 나열 구분자는 위치와 무관하게 거절해 규칙을 단순하게 유지했다.
5. **번호 상한**: 근거 없던 "10자리" 상한을 PNU 본번·부번 4자리 체계(1~9999, 0~9999)로 바꿨다.
6. **자치구 판정**: authority_code를 자치구, 본청/`_ALL`, 없음, 비서울 네 가지로 분류했다. 서울 문맥 없는 동명 자치구(`중구`, `강서구`)는 `AMBIGUOUS`, 비서울 `…구`는 `NON_SEOUL`, 구 이름 붙여쓰기는 `INVALID`로 정했다.
7. **Unicode·정규식 안전성**: NFKC 전후 길이 검사, Cc·Cf·`No` 문자 거절, 하이픈 변형 고정 목록, ASCII 숫자 강제(`int()`가 비ASCII 숫자를 받아들이는 문제), 토큰 단위 정규식을 명시했다. `①`처럼 NFKC가 없던 숫자를 만드는 경로를 막았다.
8. **결정적 실패 집계**: 실패 단계 우선순위, result 불변식, 무예외 계약, 값이 없는 `TypeError`를 정했다.
9. **개인정보**: 원문 일부·관리번호·성공 key도 로그·리포트에서 빼도록 했고 canary 테스트 범위를 넓혔다.
10. **NULL 갱신**: `EXCLUDED` 그대로 갱신, `COALESCE` 금지, "유일한 writer" 전제를 명시했다. 향후 실제 DB에서 실행하기 전 dry-run 게이트를 두었다.
11. **테스트·게이트**: 기대 enum을 정확히 단언, key 성공·실패 건수 항등식, `A→B`/`NULL→A`/`A→NULL` 통합 검증을 추가했다. 흔들리는 EXPLAIN 검증은 빼고, 중단 조건 6~8을 추가했다.

잔여 조건(구현 착수 전·중 확인):

- R1. 구현 첫 단계에서 `SEOUL_AUTHORITY_CODES`가 25개 자치구 코드→`○○구` 값과 본청 `6110000`·`_ALL`의 구조인지 확인한다. 다르면 중단 조건 8에 따라 멈춘다.
- R2. `TransformReport`에 성공 건수(`building_key_ok`)를 넣는 방식이 기존 flags 의미(문제 건수)와 충돌하지 않는지 확인하고, 필요하면 별도 카운터로 구현한다. 항등식 테스트는 반드시 유지한다.
- R3. `로` 법정동(`세종로` 등)과 숫자 없는 행정동명은 알려진 제한이다. `로` 법정동 지원은 법정동코드 등 공식 원천을 바탕으로 별도 작업에서 설계한다.
- R4. 나열 구분자 전역 거절, 부번 없는 지번 뒤 `N호` 거절 등 범위 축소로 실제 원천에서 실패율이 얼마나 될지는 실제 데이터 없이 알 수 없다. 실제 DB 적재 전에 dry-run으로 enum별 비율을 측정하고, 규칙을 완화할지는 별도로 검토한다.
- R5. NULL 갱신 정책은 BE-09 ETL이 유일한 writer일 때만 유효하다. BE-11 설계 시 `building_key` 소유권을 다시 결정해야 한다.
- R6. 원천 `address_jibun`이 법정동 기준이라는 전제는 실제 데이터로 검증되지 않았다(R4의 dry-run에서 함께 확인).
