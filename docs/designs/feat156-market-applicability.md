# 상권 경계·공식 통계 적용 기간 검증 (#156)

- 기준: develop `e3cdd5c`, 2026-11-15, BE 전용. [이슈 #156](https://github.com/sigoreu-jabeujong/SpotON-BE/issues/156).
- 사용자 후속 요청에 따라 미구현 기능 중 매출·상권변화의 선행 근거를 확인한다. 검증된 2025년 역사 자료 우선, 공식 근거 없는 수치만 보류한다는 기존 결정을 유지한다.
- 이번 산출물은 원본/DB 대조 결과, 공식 설명의 불확실성, 제공기관 확인 질문과 후속 구현 조건이다. FE·API·마이그레이션·환경값·운영 DB 변경은 없다.

## 1. 결론

기존 경계와 2025년 통계의 **코드 연결·파일 보존·DB 내용 무결성**은 확인했다. 그러나 해당 경계 도형이 각 분기에 공식 적용된 도형이라는 근거와 매출 필드의 기간 정의가 부족하다. 현재 매출·상권변화 pending을 유지한다. `RISK_BOUNDARY_VERSION_ID` 지정만으로 해결할 수 있는 설정 누락으로 취급하지 않는다.

기간 정의는 보완 설명이 필요하다. 데이터셋 FAQ는 분기 매출이라는 표현을 쓰고, 별도의 서울시 보도자료는 월평균으로 설명한다. 화면 제목이나 분기 키만으로 둘 중 하나를 선택하지 않는다. 제공기관 확인 전에 기존 원천값을 3으로 나누거나 곱하지 않는다.

전체 개발을 중단하는 결론은 아니다. 이 검증 단계는 문서로 완료하고, 아래 공식 답변이 필요한 두 기능의 활성화만 후속으로 남긴다. 로그 보존·삭제 등 독립 작업은 진행할 수 있다. 삭제된 공식 폐업률·창업위험도, 분식, 자체 점수는 재도입하지 않는다.

## 3. 실제 보관 자료·DB 검증

로컬 `spoton_dev`, schema `0012`에서 REPEATABLE READ READ ONLY 트랜잭션으로 실행하고 rollback했다. 원본 파일을 읽고 집계 결과만 기록했다. 운영 DB 검증/수정, ETL 재적재, 최신 통계 추가 확보를 실행하지 않았다.

원본 4개 모두 manifest의 input hash/bytes와 일치했다. 저장된 경계는 NDR EWKB와 허용 속성, 점포/매출/상권변화는 기존 importer의 정규 직렬화 함수로 content SHA256을 재계산해 manifest 4개 모두와 일치했다. 경계 무효/빈 도형은 각 0개다. 파일 해시는 공급기관 서명이나 효력일의 증거가 아니다.

경계 `boundary_as_of=null`, 통계 3종 `boundary_compatibility=unverified`, 매출 `amount_period_status=unverified`를 확인했다. 이를 갱신하지 않았다.

| 2025Q1 | 6,219 / 1,619 | 3,617 / 1,453 | 1,650 / 1,650 |
| 2025Q2 | 6,215 / 1,620 | 3,596 / 1,449 | 1,650 / 1,650 |

지원 업종은 한식/중식/일식/양식/커피-음료 5종이다. 위 상권 수는 **저장된 지원 업종 행** 기준이다. 원본 전체 업종을 검사한 기존 manifest의 상권 수(매출 Q1 1,572 등)와 모집단이 다르므로 혼동하지 않는다.

각 분기·자료의 저장 상권을 지정 경계와 다시 대조했을 때 경계에 없는 코드와 유형 불일치는 모두 0개다. 이름 불일치는 점포/매출 각각 분기당 1개, 상권변화 분기당 3개다. 공식 상권 코드의 동일성이 도형 동일성을 보장하지 않으므로 이름만 보정하거나 도형을 추정 교체하지 않는다. 코드/원문 이름의 전체 명부는 저장소에 추가하지 않는다. 기존 `check_boundary`는 코드·유형·이름만 비교하며, 같은 파일 안 직전 분기 대비 `changed_markets=0`도 코드·유형·이름이 바뀌지 않았다는 뜻일 뿐 도형·효력 기간의 동일성을 뜻하지 않는다.

매출이 없는 점포 조합은 Q1~Q4 각각 2,602 / 2,619 / 2,594 / 2,604개(기존 manifest 기준)다. 모집단은 점포 통계에 있는 지원 업종 (상권, 업종) 조합이며, 위 표의 지원 점포 행 − 지원 매출 행과 같다. `sales_only_combinations=0`이므로 지원 매출 조합은 모두 점포 통계 조합에 포함된다. 행 부재를 매출 0으로 간주하면 안 된다. 지원 업종 전부/모든 상권에 매출이 있다고 가정하지 않는다. 1차 검수 후 추가 읽기 전용 집계에서 저장 매출 14,391행의 `est_sales`/`source_sales_count`는 모든 분기에서 실제0·null 각0개였다. 이는 저장한 지원 업종 범위만의 관측이며 다른 원본/업종/미존재 조합에 일반화하지 않는다. API는 미래의 실제0/null/행 부재도 각각 처리해야 한다.

## 4. 현재 코드에서 유지할 안전 조건

- `app/schemas/market_judgement.py`: applicability는 unverified 전용 Literal이다. 지정 경계로 한 공간 판정과 공식 시점 적용성을 분리한다.
- `app/models/market_sale.py` 등: 기존 버전의 출처/기간 unverified CHECK를 그대로 둔다. 기존 불변 버전을 UPDATE로 verified로 승격하지 않는다.
- `app/services/risk.py`: 경계 설정 부재/적용 기간 미검증을 구분하고 `market_change` pending을 유지한다. 여러 세부 상권의 겹침에서 임의 하나를 고르지 않는다.
- `app/services/market_activity.py`: `sales=null`, `source_period_and_boundary_unverified`를 유지한다. 반경 내 인허가 수와 공식 상권 매출을 동일 공간·동일 필터 수치로 설명하지 않는다.
- 공식 통계에 브랜드/가맹·직영·소규모 체인 필터를 그대로 적용할 점포 단위 근거가 없다. 미래 API는 `brand_filter_applied=false`에 해당하는 명시적 메타를 검토하고 인허가 필터 수치와 구분해야 한다. **이 메타는 제안이며 현재 구현된 필드가 아니다.** OA-15577의 `FRC_STOR_CO`(가맹)·`STOR_CO`(일반)를 Spot:ON v2의 chain/non_chain에 대응시키지 않는다. 사용자가 chain/non_chain 조건을 지정해도 매출은 상권·업종 코드별, 상권변화는 업종 차원 없는 상권 전체의 공식 값이며, 그 조건(또는 세부 업종 조건)으로 걸러진 값처럼 표시하지 않는다.
- Claude 2차 검토에서 제공된 발췌로 대조한 범위: `risk.py`는 설정 부재 시 `boundary_version_not_selected`, 설정 시 `boundary_period_not_verified`로 구분하고 `market_change`를 `boundary_period_not_verified` pending으로 반환한다. `market_activity.py`의 `sales` pending 사유는 `source_period_and_boundary_unverified`다. `sales=null` 반환과 서비스 전체 흐름은 발췌 밖이라 Codex 보고에 근거한다. 겹침 시 임의 선택 금지는 `market_judgement.py`의 ambiguous/candidates 검증으로 확인된다. `market_sale.py`의 unverified CHECK, `check_boundary`의 코드·유형·이름 전용 대조도 제공 소스와 일치한다.

## 5. 제공기관 확인 요청 초안

대상은 S1~S3의 제공기관인 서울신용보증재단 데이터분석팀이다. 이 담당 부서명은 Codex의 웹 열람 결과이며, Claude 검토에 제공된 발췌에는 없었다. 문의 제출 시 각 데이터셋 페이지의 제공기관/담당 표시와 다시 대조한다. 포털 문의에 복사할 수 있도록 질문을 정리했다. 연락/문의 제출은 실행하지 않았다. API 키·DB URL·개별 사업장 정보는 질문에 필요 없다.

> 서울시 상권 통계를 활용하는 Spot:ON 프로젝트입니다. OA-15560의 2023-10-23 수정 ZIP과 OA-15572의 2025년 ZIP(2026-05-18 수정), OA-15576 CSV(SHA256 `0a2ea421607c167fe3a5005719a3118e064fef74d8a4513d030eecc29719a128`)의 2025년 자료를 결합하려고 합니다. 잘못된 공간/기간 해석을 방지하기 위해 다음 사항을 확인 부탁드립니다.

## 6. 근거 확보 후 구현 순서와 완료 조건

7. 명시 버전·단일/중첩/밖·관광특구 병기·분기 미존재·이름 변경·stale 증거·미지원 업종·실제0/null/행 부재를 테스트한다. 미검증 조합은 계속 pending이며 최신 UUID 자동 선택이나 가까운 분기 대체가 없어야 한다.
