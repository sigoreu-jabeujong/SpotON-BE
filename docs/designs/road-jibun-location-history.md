# 도로명·지번을 함께 사용하는 점포 이력 조회 설계

최신 범위(2026-11-17 후속 승인): 사용자가 구현과 테스트를 요청해 FE·BE 구현을 진행했다. 아래 1~9절은 이전 설계·검토 이력이며 현재 구현 선택과 검증은 10절을 우선한다. 운영 배포와 운영 DB 변경은 이번 범위에 포함하지 않는다.

작성일: 2026-11-17. BE 신규 조회 구조는 설계·Claude Code 검토까지만 진행한다. 이번에 허용된 앱 변경은 FE의 상세주소 설정 화면 및 이력 비교 옵션·요약 문구 제거다. 테스트·빌드·운영 배포·DB 변경은 수행하지 않는다.

## 1. 목표와 현재 상태

입력한 도로명주소와 그 주소에 대응하는 지번주소를 함께 사용해 같은 주소의 점포 기록을 찾는다. 도로명 또는 지번 중 하나만 있는 점포도 검토 대상에 포함하되, 서로 다른 주소를 같은 장소로 합치지 않는다. 현재 영업 중·폐업·기타 상태를 모두 포함한다.

현재 배포 기준은 BE PR218 병합 커밋 `8cd2d73`, FE 릴리스 PR115 커밋 `3582b46`이다. 아래 내용은 코드 분석이며 신규 실데이터 조회 결과가 아니다. 사용자가 제시한 3건/영업 중 1건/폐업 2건/미확인 58건도 이번에 재측정한 값이 아니다.

| 현재 코드 | 확인한 동작 | 한계 |
| --- | --- | --- |
| `app/services/kakao_local.py` | 한 공급자 후보 문서에서 도로명·지번·좌표를 받고 지번 기반 building_key 생성 | 도로명 구조 코드·건물관리번호·주소 쌍의 검증 버전을 보존하지 않음 |
| `app/services/store_history.py` | 지원 점포 중 building_key가 같은 행 조회 | 도로명만 유효한 기록을 추가로 찾지 못함 |
| `app/services/location_history.py` | 위 지번 후보를 다시 층·호수 exact로 비교 | 다른 지번의 도로명 일치 기록을 추가 탐색하지 않음 |
| `app/models/store.py` | 원문 address_road/address_jibun과 building_key/floor_unit 보유 | 정규화 도로명 키·검색용 별칭 인덱스 없음 |
| FE `InputPage.tsx` | 입력과 유일하게 일치하는 후보 선택 후 상세 정규화 | 배포 기준에서는 이전 상세 입력 패널이 selected 상태만으로 노출돼 전환 중 깜빡임 발생. 검토 시점의 로컬 작업본에서는 패널·selected 상태가 이미 제거돼 있음(6절, 미커밋·미배포 여부는 별도 확인) |

현재 building_key는 지번 구역 식별자다. 동일 물리 건물·동의 고유 식별자로 승격하지 않는다. 도로명·지번을 함께 사용해도 임대차상의 같은 점포 자리까지 증명되지는 않는다.

## 2. 주소 선택 원칙

예시 입력 `서울특별시 마포구 양화로 45 2층`을 기본 주소 `서울특별시 마포구 양화로 45`, 상세주소 `2층`으로 분리한다. 공백·서울/서울특별시 표기는 정규화하되 의미 있는 구·도로명·본번·부번·지하 표시는 유지한다.

- `양화로 45`와 `양화로 지하 45`는 다른 도로명 키다. 도로명주소의 지하 표시는 건물번호 속성이고 `B1` 같은 상세 층 정보와 별개다.
- 입력과 정확히 일치하는 후보가 하나면 선택한다. 유일한 후보라도 입력과 다르거나 정확 일치 후보가 여럿이면 사용자가 선택한다. 서로 다른 후보의 도로명과 지번을 교차 조합하지 않는다.
- 현재 코드에서 확인한 예시 대응은 지상 45 → 서교동 490, 지하 45 → 합정동 414다. 이는 과거 후보 관측값이며 모든 주소에 적용할 상수나 새 공식 검증 결과가 아니다.
- 선택된 공급자 **같은 문서 안의** 도로명과 지번만 1차 주소 쌍으로 인정한다. 여러 필지·건물 연결은 공급자 또는 공식 자료의 개별 근거가 있을 때만 추가한다. 좌표가 가깝거나 번호가 같다는 이유로 연결하지 않는다.
- 건물관리번호가 확보되면 추가 근거로 보존할 수 있지만, 현재 후보 모델에는 없으므로 구현 전 필드·공급자 제공 범위부터 확인한다.
- 현재 `KakaoAddress`는 도로명 문서에도 지번용 필드만 읽고(`extra="ignore"`) 지하 여부·도로명·건물 본번/부번을 구조화하지 않는다. 지상/지하 구분은 지금은 표시 문자열 `address_name`에만 남는다. 도로명 키는 표시 문자열 재파싱이 아니라 공급자 구조 필드(지하 여부·도로명·건물 본번/부번, 확보 시 도로명 코드)로 만들고, 필드가 없거나 표시 문자열과 모순되면 도로명 키를 만들지 않는다.
- 공급자 문서에 도로명주소가 없으면 도로명 검색은 생략하고 지번 근거만 사용함을 응답에 표시한다. 현재 코드는 지번 문서가 없는 후보를 선택 불가로 처리하므로 도로명 전용 후보 지원은 별도 결정이다.

## 3. 제안 데이터 구조

원본 stores 주소를 덮어쓰지 않고 별도 파생 조회 모델을 둔다. 아래 표·필드는 제안이며 이번에는 migration이나 적재 코드를 작성하지 않는다.

| 파생 모델 | 주요 필드 | 용도 |
| --- | --- | --- |
| history_address_version | id, rule_version, source_batch_ids, input_digest, state, built_at | 점포 원천 배치·정규화 규칙에 묶인 파생 점포 주소 인덱스의 준비/활성 버전 |
| history_address_anchor (선택) | anchor_rule_version, road_key, lot_key, provider_evidence_ref, evidence_status | 오프라인으로 검증한 다필지·다도로명 추가 관계만 보관. 사용자 요청마다 쓰지 않으며 물리 건물 보증 아님 |
| history_store_address | version_id, source, license_no, raw_input_hash, source_batch_id, road_key?, lot_key?, floor?, unit?, detail_basis, conflict_reason? | 점포별 검색·상세 비교에 쓰는 파생 정보 |

도로명 키는 시도·시군구·도로명(코드 확보 시 코드)·지하 여부·건물 본번·부번을 모두 포함한다. 지번 키는 시군구·법정동·산 여부·지번 본번·부번을 포함한다. 기존 building_key와 의미가 일치할 때만 재사용한다. 건물동 표기(예: A동)는 별도 정보이며 건물번호나 법정동과 섞지 않는다.

한 점포는 `(version_id, source, license_no)`로 유일하게 관리한다. 도로명/지번별 B-tree 인덱스를 각각 둔다. 별칭이 여러 개인 경우 관계 행으로 관리하며 단순 배열 문자열 검색으로 전 테이블을 훑지 않는다.

적재 시 원문 주소에서 층·호수도 별도로 파싱한다. 기존 floor_unit, 도로명 원문 상세, 지번 원문 상세가 서로 다르면 conflict로 남긴다. 검색자가 입력한 2층을 원본 점포의 결측 층에 채워 넣지 않는다. 원문만으로 하나의 층·호수가 명확한 경우에만 그 원문과 규칙 버전을 근거로 파생 상세를 생성한다.

활성 버전 전환은 원천별 배치와 입력 해시가 검증된 완성 세대만 원자적으로 수행한다. 요청은 같은 READ ONLY REPEATABLE READ에서 활성 버전·점포 원본 배치·브랜드 보강을 읽는다. 원본이 변경돼 파생 해시/배치가 맞지 않으면 해당 자료를 정상 결과로 섞지 않고 준비 불일치 상태로 반환한다. 새 버전이 준비되지 않았다고 다른 조건의 이전 정상값을 반환하지 않는다.

(검토 보완) 불일치 판정 단위는 응답 전체다. 한 원천만 재적재돼 그 원천 행이 활성 버전의 source_batch_ids와 다르면 다른 원천 행만 반환하는 부분 결과를 만들지 않고 전체를 `index_stale`로 반환한다. 일부 원천만 빠진 합계가 정상 total처럼 보이는 것을 막기 위해서다. 사용자 선택 주소 쌍(4·5절)과 이 점포 주소 인덱스 버전은 서로 다른 축이다. 점포 재적재가 공유 URL의 주소 선택을 무효화하지 않도록, 주소 쌍은 공급자 근거 규칙 버전으로, 점포 측은 인덱스 버전으로 따로 관리한다.

## 4. 조회 순서와 충돌 처리

1. BE가 검증한 선택 주소 쌍을 확정한다. FE가 보내는 도로명·지번 두 문자열을 검증 없이 OR 검색하지 않는다.
2. 동일 활성 버전에서 도로명 키 exact 조회와 지번 키 exact 조회를 각각 실행한다. 두 조회 모두 기존 이력과 같은 지원 점포 조건(`SUPPORTED_STORES`: 지원 업종·삭제/검토 대기 제외·이름 키워드 제외 버전)을 원본 stores와 조인해 적용하고, 그 버전을 meta에 남긴다. 파생 테이블만으로 모집단을 판단하지 않는다.
3. 두 후보 집합을 `(source, license_no)`로 합쳐 중복을 제거한다. 같은 상호·좌표·관리번호 단독으로는 합치지 않는다.
4. 각 점포의 양쪽 주소 근거를 함께 판정한다. 긍정 근거 하나가 있어도 다른 명확한 근거와 모순되면 자동 포함하지 않는다.
5. 입력한 상세주소 수준에 맞게 층·호수를 비교하고 영업 중·폐업·기타를 모두 보존한다.
6. 해당 원천 배치 기준으로 영업 기간·폐업일 품질을 계산한다. 개업일 최신순, 결측 마지막, source/license_no 순으로 안정 정렬한다.

| 점포 주소 근거 | 판정 |
| --- | --- |
| 도로명과 지번 모두 선택 주소 쌍과 일치 | 포함 후보, evidence=both |
| 도로명 일치, 지번 부재 | 포함 후보, evidence=road |
| 지번 일치, 도로명 부재 | 포함 후보, evidence=jibun; 물리 건물 확정 아님 |
| 도로명 일치, 점포의 명확한 지번은 다른 곳 | 주소 충돌. 검증된 다필지 관계가 없는 한 제외/보류 |
| 지번 일치, 점포 도로명은 지하45 등 다른 주소 | 주소 충돌. 지번 일치만으로 포함하지 않음 |
| 한쪽 일치, 다른 쪽 원문은 있으나 파싱 불가 | 미확인. 부재와 구분하고 확정 목록에는 자동 포함하지 않음 |
| 둘 다 부재 또는 불일치 | 확정 목록 제외 |

(검토 보완) 합친 각 고유 점포는 다음 중 **정확히 하나**의 최종 분류를 가진다: `matched`, `address_conflict`, `address_unresolved`, `detail_excluded_floor`, `detail_excluded_unit`, `detail_unresolved`. 주소 판정(위 표)을 먼저 하고 주소가 포함 후보인 점포에만 상세 비교를 적용한다. 따라서 `total + 주소 충돌 + 주소 미확인 + 상세 제외 + 상세 미확인 = 합친 고유 후보 수`가 성립해야 하며, 어긋나면 부분 응답 없이 서버 오류로 처리한다. 현재 v2의 `unresolved_count`는 상세 미확인만 뜻하므로 v3는 주소 미확인과 상세 미확인을 별도 필드로 둬 같은 이름의 의미를 바꾸지 않는다.

(검토 보완) v3는 v2의 상위 집합이 아니다. v2는 같은 building_key 행을 도로명과 무관하게 포함하지만 v3는 지번만 일치하고 도로명이 다른 주소(예: 지하45)인 행을 충돌로 뺀다. 같은 주소에서 v3 total이 v2보다 작거나 클 수 있으며, FE·보고서·AI는 두 결과를 합치거나 비교 증감으로 표시하지 않는다.

다필지/다도로명 관계는 근거가 있는 주소 anchor 관계에 한정한다. A와 B, B와 C의 개별 연결을 이유로 A와 C를 무조건 같은 물리 건물로 취급하지 않는다. 과거 주소 변경도 적용 기간과 근거가 확보되기 전 자동 소급하지 않는다.

| 사용자 입력 상세 | 서버의 자동 비교 수준 |
| --- | --- |
| 상세주소 없음 | address: 주소가 일치하는 점포 전체. 같은 층·자리라고 표시하지 않음 |
| 2층 | floor: 명확히 2층인 점포만 확정 목록에 포함 |
| 2층 201호 | unit: 층과 호수 모두 일치하는 점포만 포함 |
| 201호만 입력, 복수 층, 파싱 실패 | 상세 수정 필요. 주소 전체로 몰래 확대하지 않음 |

점포 쪽 상세가 복수 층(예: 1~2층)이거나 층 없이 호수만 있으면 floor/unit 비교에서 `detail_unresolved`로 둔다. 도로명 건물번호의 `지하`와 상세의 `B1`/`지하1층`은 파서가 서로 다른 토큰으로 처리해야 하며, 원문에 둘이 함께 있는 사례(`양화로 지하 45, 지하1층`)를 검증 사례에 포함한다.

층·호수 미확인 기록은 상세 조회의 확정 목록에서 빠지며 별도 미확인 상태를 유지한다. 화면에서 긴 설명이나 계수를 숨겨도 이력 0건을 과거 점포가 전혀 없다는 뜻으로 표현하지 않는다. 원천상 영업 중 기록은 포함하지만 실제 현장 영업을 확인한 것으로 표시하지 않는다.

## 5. 제안 API와 FE 연결

기존 `/api/stores/history`, `/api/v2/stores/history`, `/api/v2/stores/location-history`와 구 AI 문맥은 보존하고 별도 v3 계약으로 도입한다. 이번에는 BE API를 구현하지 않는다.

- 제안 `POST /api/v3/address-context`: 사용자가 입력한 주소와 선택 후보를 서버가 공급자에 재조회해 같은 문서임을 확인하고, 그 **한 문서**의 구조 필드로 도로명 키·지번 키·표시값·정규화 상세주소·주소 규칙 버전을 만든다. 클라이언트가 보낸 도로명/지번 문자열이나 다른 후보의 값을 조합하지 않는다.
- (검토 수정) 운영 BE는 조회 전용 DB 역할만 사용하므로 이 POST가 anchor를 DB에 생성·등록할 수 없다. 또 모든 서울 주소를 미리 준비할 수 없으므로 "준비된 anchor가 없는 주소는 address_pending"이라는 원안은 대부분의 주소를 조회 불가로 만든다. 따라서 주소 컨텍스트는 DB 행이 아니라 **서버 서명 토큰**으로 반환한다: `{road_key?, lot_key, anchor_rule_version, issued_at}`과 지속 비밀키로 만든 HMAC. 토큰에는 공개 주소 키만 넣고 사용자 원문 입력·좌표 원문·검색 이력 식별자는 넣지 않는다. 앱 수명 난수 키(#74 캐시)는 재시작 후 공유 URL을 깨뜨리므로 쓰지 않는다. 별도 지속 비밀 환경변수와 키 교체 정책이 필요하며 이는 현재 "환경값 변경 금지" 범위 밖의 별도 승인 사항이다.
- 이력 GET은 토큰 서명·규칙 버전만 검증하고 공급자를 호출하지 않는다. 위·변조·형식 오류는 422, 지원하지 않는 이전 규칙 버전은 `context_stale`(새 컨텍스트 재발급 안내)로 구분하며 다른 주소로 자동 보정하지 않는다. 서명 키 미설정은 정상 no_data가 아니라 서비스 미준비(503 계열)다. 오프라인 anchor(3절 선택 테이블)는 검증된 추가 다필지 관계에만 쓰고 기본 조회의 선행조건으로 삼지 않는다.
- 제안 `GET /api/v3/stores/location-history?context=...&floor_unit=...`: floor_unit은 생략 가능하다. scope/identity 선택은 UI에서 받지 않고 정규화 상세주소에서 자동 결정한다. category는 기존처럼 조회 업종 문맥이며 지원 점포 전체 이력의 임의 축소에 쓰지 않는다.
- 응답: selection(도로명/지번 키·표시값/anchor_rule_version/effective_scope/정규화 상세), result_status(matched/no_data/detail_required/index_stale/context_stale), stores, total, coverage, 4절의 분류별 계수(address_conflict/address_unresolved/detail_excluded/detail_unresolved), 점포 인덱스 버전, source/date metadata. 오류·미준비·정상 no_data를 분리하고 날짜·상태·브랜드 필드는 v2 의미를 유지한다. 평가 완료 뒤 total>0이면 matched, total=0이면 no_data이며, no_data는 요청 조건의 확정 결과가 없다는 뜻이다. 다른 층·호수 제외만 있어도 no_data가 될 수 있다. 충돌/미확인이 있으면 total과 무관하게 coverage=partial로 표시하고 과거 점포 자체가 없다고 해석하지 않는다. index_stale/context_stale/detail_required는 집합 평가가 완료된 0건이 아니므로 total·계수는 null, stores는 빈 배열, coverage=not_evaluated로 반환한다.
- 각 행에는 match_evidence(road/jibun/both), effective_scope와 상세 근거를 둔다. source/license_no로 합친 고유 행 기준 total을 사용한다. 응답 echo와 query key에는 컨텍스트 토큰(또는 그 키·규칙 버전)·정규화 상세·정책 버전·점포 인덱스 버전을 모두 포함한다.
- (검토 보완) 화면에서 계수·장문을 숨기는 것은 표시 정책이며 API 계약에서 필드를 제거하는 것이 아니다. 분류별 계수·coverage·버전 metadata는 응답에 유지하고 PDF/이미지 생성도 같은 응답을 쓴다. total=0이면서 coverage=partial이면 짧게라도 "상세 위치·주소를 확인할 수 없는 기록은 제외됨"을 표시해 0건을 과거 점포 부재로 읽히지 않게 한다.
- 공유 URL 복원은 서버가 컨텍스트 토큰의 서명·규칙 버전을 다시 확인한다. 예전 bk만 있는 URL을 도로명·지번 검증 완료로 승격하지 않는다. 구 링크는 재해석 후 새 컨텍스트를 만들거나 기본 입력으로 안내한다. 새 URL의 위·변조/버전 불일치는 다른 주소로 자동 보정하지 않는다.
- 원문 주소를 로그·예외·원격 LLM에 추가하지 않는다. POST와 이력 응답은 no-store를 유지한다. 컨텍스트 토큰은 공개 주소 키의 서명일 뿐 사용자별 검색 이력을 저장·추적하는 식별자로 쓰지 않으며 서버에 발급 기록을 남기지 않는다.

정상 결과 UI는 점포 목록과 개별 영업 상태·날짜·출처를 표시한다. 이력 비교 범위/주소 확인 기준 선택기, '같은 주소 범위·층의 확인된 점포 이력 N건', 상태별 합계/58건 미확인 장문은 제거한다. 오류·자료 갱신 중(index_stale)·주소 재확인 필요(context_stale)·상세 수정 필요·조회된 기록 없음은 짧게 표시한다. PDF/이미지도 동일한 표시 정책을 따른다.

## 6. 이번 FE 변경과 다음 구현의 경계

이번 FE 변경은 상세주소 입력 패널·확인 버튼·selected 상태와 그 focus effect를 삭제한다. 자동 선택 뒤에는 별도 화면 없이 정규화 대기→진단으로 이동한다. 정규화 실패 시 기존 주소 입력칸 아래 오류만 표시한다. 후보 선택이 필요한 경우 후보 목록은 남기고 입력한 상세를 선택 주소에 함께 전달한다.

이력 선택기는 제거하고 현재 v2에는 입력 상세에서 정한 floor/unit 및 address_scope를 자동 전달한다. 과거 URL의 historyScope/historyIdentity를 이 훅에서 다시 선택 조건으로 사용하지 않는다. 층 없는 주소의 이력 조회는 현재 v2가 지원하지 않으므로 기존 안내를 유지한다. **상세 없는 주소도 이력을 조회하는 address 수준은 v3 후속 구현 사항**이다. UI 삭제만으로 도로명·지번 동시 조회가 구현됐다고 보고하지 않는다.

BE 코드·모델·API·DB·원본 데이터·운영 환경은 이번에 변경하지 않는다. 테스트/빌드/PR/배포도 수행하지 않는다. 이전에 배포된 기능과 이번 로컬 UI 변경을 구분한다.

### 8.3 차단 사항과 MD 직접 수정 내용

1. **주소 컨텍스트의 진위·준비 모델이 실행 불가능했음(5절, 3절).** 원안은 POST가 활성 anchor의 `address_id`를 반환하고, anchor는 별도 준비 절차로 만들며 미준비 주소는 `address_pending`이라 했다. 그러나 운영 BE는 조회 전용 DB 역할만 쓰므로 요청 중 anchor를 쓸 수 없고, 서울 전체 주소를 미리 준비할 근거도 없어 대부분 주소가 `address_pending`이 된다. 또 FE가 받은 `address_id`/쌍의 위·변조·교차 조합을 막는 수단이 정의되지 않았다. → 단일 공급자 문서에서 서버가 만든 키를 **지속 비밀키 HMAC 서명 토큰**으로 반환하고, GET은 서명만 검증하도록 수정했다. 오프라인 anchor 테이블은 선택적 다필지 근거로 강등했다. 지속 비밀 환경변수는 현재 환경값 변경 금지 범위 밖의 별도 승인 사항으로 명시했다.
2. **주소 쌍 버전과 점포 인덱스 버전이 한 version_id에 묶여 있었음(3절).** 점포 재적재마다 공유 URL의 주소 선택이 무효화된다. → 두 축을 분리했다.
3. **원천 버전 불일치 상태가 응답 enum에 없었음(3·5절).** 3절은 "준비 불일치 상태로 반환"이라 했지만 5절 result_status에 해당 값이 없었고, 한 원천만 재적재됐을 때 부분 결과 허용 여부도 불명확했다. → 응답 전체 `index_stale`, 규칙 만료 `context_stale`을 추가하고 부분 결과를 금지했다.
4. **union 후 분류·계수의 상호 배타성이 정의되지 않았음(4절).** `conflict_count`/`unresolved_count`가 겹치거나 v2의 `unresolved_count`(상세 미확인 전용, `location_history.py` 확인) 의미가 조용히 바뀔 수 있었다. → 고유 후보당 최종 분류 6종·주소 판정 우선·계수 합 불변식·주소/상세 미확인 필드 분리를 추가했다.
5. **양쪽 조회의 모집단 조건이 누락됐음(4절).** 기존 이력은 `SUPPORTED_STORES`(업종·삭제·검토·이름 제외)로 모집단을 정한다(`store_history.py`). 원안은 파생 테이블 조회만 기술해 도로명 쪽 조회에 이 조건이 빠질 위험이 있었다. → 두 조회 모두 원본 stores 조인으로 같은 조건을 적용하도록 명시했다.

### 8.4 조건부 사항(구현 전 결정 필요)

| 원천별 버전 정합 | 같은 RR 세션·배치 대조 원칙은 적절. 응답 단위 `index_stale`로 보완(8.3-3). 영업 기간을 점포별 원천 배치 기준일로 계산하는 원안은 현재 `location_history.py`의 per-batch 기준과 일치 |
| 상세 없는 주소/층/호수 자동 범위 | 표 4종 적절. 점포 측 복수 층·호수만 기록을 `detail_unresolved`로 명시. FE `closedHistoryParams`는 층 없는 상세·`201호`만 입력을 null로 처리하고 scope를 호 포함 여부로 자동 결정함을 확인(6절과 일치) |
| 영업 중 포함 | 원안과 현재 v2(location-history-all-status) 모두 open/closed/other 포함. 원천상 영업 중을 현장 확인으로 표시하지 않는 원칙 적절 |
| 주소 컨텍스트 진위/준비 | 원안 차단 → 서명 토큰으로 수정(8.3-1). 남은 조건 C1 |
| 현재 v2와 미래 v3 경계 | 6절 서술 정확. 현재 FE는 v2에 `identity_requirement: 'address_scope'`와 자동 scope만 전달하고 `pending_identity` 분기는 사실상 도달하지 않음. v3는 별도 경로·별도 query key이며 결과를 v2와 합치지 않도록 4절에 추가 |
| 삭제된 FE 상세 패널의 오류 복구 | 로컬 `InputPage.tsx`에서 패널·selected·focus effect 부재 확인. 정규화 실패/네트워크 실패 시 `role="alert"` 오류만 남고, 입력 변경(`onChange`)이나 재검색(`onSubmit`)으로 오류가 지워져 복구 경로가 있다. generation 토큰으로 이전 요청 결과를 무시한다. 비차단 권고 R1 참조 |
| 숨긴 UI와 metadata 구분 | 원안은 UI 제거만 기술해 API 필드 제거로 오해될 수 있었음 → 5절에 표시 정책과 계약을 구분하고 total=0·partial의 짧은 고지를 추가. 현재 `HistorySection.tsx`는 total=0이면 `unresolved_count`와 무관하게 "조건에 맞는 점포 이력이 조회되지 않았어요"만 표시한다(R2) |

### 8.6 비차단 권고

- R1: 후보 목록에서 선택한 뒤 상세 정규화가 실패하면 `onSelect`가 목록을 먼저 비우므로 사용자는 재검색해야 한다. 6절의 "후보 목록은 남기고"와 맞추려면 실패 시 목록을 복원하는 편이 낫다. 자동 선택 경로도 같은 이유로 재시도 버튼 없이 재검색에 의존한다.
- R2: 현재 v2 화면에서도 `location.location_coverage === 'partial'`이고 total=0이면 짧은 제외 고지를 붙이는 것을 권고한다(FE 로컬 작업 범위 판단은 Codex/사용자).
- R3: `closedHistoryTitle`/`closedHistoryNotice`의 `pending_identity` 분기와 `detailUnverified`(이제 `confirm`이 정규화 실패 시 이동을 막으므로 구 URL에서만 발생)는 구 링크 호환용으로 남기되, 구 URL에서 "층·호수를 입력해" 안내가 상세 파싱 실패 상황과 구분되지 않는 점을 인지할 것.
- R4: 현재 `kakao_local.py`는 지번 문서가 없는 후보를 선택 불가로 처리한다. 도로명 전용 후보 지원은 별도 결정이며 2절에 명시했다.
- R5: 토큰에 `issued_at`을 넣되 만료를 너무 짧게 두면 공유 URL이 깨진다. 만료보다 규칙 버전 기반 `context_stale`을 주 수단으로 두는 것을 권고한다.
- R6: 읽지 않은 `addressSelection.ts`의 기본주소/상세 분리가 `지하 45`를 상세로 떼어내지 않는지 후속 검증 사례에 포함할 것.

## 9. Codex 최종 반영 기록

2026-11-17 실제 Claude Code CLI 검토가 종료 코드 0으로 완료됐다. Read/Edit만 허용하고 Edit 대상은 이 MD로 한정했다. 상세 검토 범위·원안 문제·문서 직접 수정·조건부 PASS는 8절에 기록돼 있다. 검토 결과 원문은 워크스페이스 밖 `road-jibun-claude-review.json`에 보관했다. 이 파일은 실행 증거이며 테스트 결과가 아니다.

Codex 결정:

- 주소 컨텍스트는 요청 중 DB 쓰기 없이 서버가 만든 서명 토큰을 사용하는 안을 채택한다. 오프라인 anchor는 검증된 추가 별칭 근거로만 둔다. 조회가 READ ONLY 세션에서 수행된다는 것은 코드로 확인했지만, 이번 작업에서 운영 DB 역할의 전체 권한을 새로 실증하지는 않았다.
- C1은 구현 전 설정 항목으로 남긴다. 새 전용 지속 서명 키와 key-id, 현재/이전 검증 키 교체, 키 미설정 시 공개 비활성화, 퇴역 키·미지원 규칙은 context_stale로 재확인하는 정책을 제안한다. 공급자 API 키나 프로세스별 캐시 난수는 재사용하지 않는다. 실제 키 생성·환경변수 추가는 이번 범위 밖이며 수행하지 않았다. 이 설계 검토를 마치기 위해 지금 사용자 확인을 요청할 필요는 없다.
- C2는 후속 구현의 선행 확인 항목으로 남긴다. 공급자 실제 구조 필드 확보와 공식 명세 대조 전에는 해당 필드를 이미 받는다고 가정하지 않으며 표시 문자열에서 모호한 주소를 추측해 확정하지 않는다. 이번에는 공급자 API 호출이나 새 데이터 수집을 하지 않았다.
- 주소 선택과 점포 인덱스의 버전 분리, 전체 index_stale 처리, 주소/상세 미확인 분리, 고유 후보 계수 합, 양쪽 조회의 동일 지원 모집단 조건을 설계에 반영한다. v3 결과가 기존 v2보다 항상 늘어난다고 주장하지 않는다.
- 검토 후 no_data 정의를 추가 정리했다. 다른 층·호수로 제외된 후보만 있는 정상 0건도 no_data로 표현하고, 충돌/미확인은 coverage로 분리한다. 준비 불일치·상세 수정 필요를 total=0으로 위장하지 않도록 미평가 시 수치는 null로 명시했다. 계수 합 불변식은 평가가 완료된 응답에만 적용한다.
- R1 반영: FE 수동 후보 선택 시 후보 목록을 정규화 전에 지우지 않고, 처리 중 후보 버튼만 비활성화한다. 실패하면 같은 목록에서 다시 선택하거나 원래 주소 입력칸을 수정할 수 있다. 상세 설정 화면은 복원하지 않는다. 오류는 기존 주소 입력칸의 오류 영역과 연결한다.
- R2 반영: 현재 v2의 0건·partial일 때만 상세 미확인 기록 제외를 짧게 알린다. 요청한 정상 결과의 집계·N건 미확인 장문·선택기는 제거한 상태를 유지한다. PDF/이미지도 공통 표시 함수를 쓴다.
- R3은 구 URL 호환을 위해 유지한다. R4 도로명 전용 공급자 후보 지원은 지번 필수인 현 API와 다른 작업이므로 후속 검토로 분리한다. R5 장기 공유 링크는 규칙/키 유효성 확인 후 복원하도록 설계하고 임의의 짧은 만료는 정하지 않는다.
- R6의 FE addressSelection.ts는 Codex가 정적으로 읽었다. 도로명 파서의 지하 그룹을 base에 보존하고 그 뒤 detail만 분리하는 코드를 확인했다. 실행 테스트를 한 것은 아니며 복합 지하 표기 사례는 후속 검증 목록에 남긴다.

완료 범위: 설계 문서·실제 Claude Code 검토·FE UI 삭제와 관련 기존 테스트 기대값 수정(미실행). 신규 BE 이력 API·migration·적재·실데이터 검증·테스트·빌드·PR·배포는 수행하지 않았다. C1/C2를 해소하기 전 신규 v3의 공개 구현 완료 또는 배포 준비 완료로 판정하지 않는다.

## 10. 후속 승인에 따른 구현·테스트

### 실제 구현 선택

사용자가 구현과 테스트를 승인했다. 이전의 설계 전용/테스트 금지 제한은 이 단계에서 대체하며 배포는 하지 않는다.

1. 카카오 [공식 REST API 명세](https://developers.kakao.com/docs/ko/kakaomap/rest-api)의 `road_name`, `underground_yn`, `main_building_no`, `sub_building_no`를 후보 모델에 추가했다. 컨텍스트 POST에서 같은 공급자 문서의 지번·좌표·도로명 표시와 구조 키가 일치하는지 확인한다. 누락·모순은 정상 주소 쌍으로 서명하지 않는다. 기존 geocode 응답 형식은 유지한다.
2. `POST /api/v3/address-context`는 선택한 기본 주소·building_key·좌표·업종을 받아 서명 컨텍스트를 반환한다. 선택 주소는 입력 화면에서 후보 선택과 정확 일치 확인을 마친 값이며, 서버는 임의 문자열 조합을 신뢰하지 않고 공급자 재조회로 확인한다. DB 쓰기는 없다.
3. `GET /api/v3/stores/location-history`는 서명·규칙·상세주소를 DB 접속 전에 검증하고 같은 READ ONLY REPEATABLE READ에서 지번/도로명 indexed UNION을 수행한다. 영업 상태는 open/closed/other를 모두 포함한다. 상세가 없으면 address, 층이면 floor, 층·호수면 unit으로 자동 결정한다. 호수만 있거나 모호한 상세는 422다.
4. **파생 세대 테이블 대신 트랜잭션에 의해 자동 유지되는 표현식 인덱스를 채택했다.** migration0014의 immutable 함수 `spoton_history_road_key_v1(address_road)`와 B-tree 인덱스는 stores 원문을 수정하지 않는다. PostgreSQL이 INSERT/UPDATE/DELETE와 같은 트랜잭션에서 인덱스를 갱신하므로 별도 배치 적재/활성 버전/원본 드리프트 검사 없이 같은 snapshot에서 원문과 키가 일치한다. Python/SQL 정규화 결과는 같은 사례로 비교 테스트한다. 함수 규칙 변경은 기존 함수를 덮어쓰지 않고 새 함수·인덱스 migration으로 진행해야 한다.
5. 도로명·지번 충돌, 주소 파싱 불가, 상세 미확인, 다른 층/호수 제외를 각각 계수하고 고유 후보 분할 합을 DTO에서 검증한다. 실제 반환 total과 영업 상태·폐업일 품질 합도 검사한다. 각 점포의 영업 기간은 자기 원천 배치 기준일로 계산한다.
6. FE는 주소·좌표를 서버에서 확인해 컨텍스트를 받은 뒤 v3 이력을 조회한다. 공유 URL에는 서명 토큰을 저장하지 않고 기존 기본 주소·상세를 보존하며 복원/재조회할 때 새 컨텍스트를 발급한다. 따라서 서명 키 교체로 영구 공유 링크가 깨지지 않는다. row의 history_scope/match_evidence와 selection·각 계수를 검증하고 표·PDF·이미지는 같은 쿼리를 공유한다. 긴 집계 문구·범위 선택기·별도 상세 설정 패널은 제거한 상태다.
7. 오류/준비 불가는 기존 공통 오류 외피를 쓰며 `HISTORY_UNAVAILABLE` 503을 추가했다. 함수가 없는 DB, 서명 키 미설정·이전 컨텍스트 규칙은 정상 0건으로 표시하지 않는다. 별도 파생 세대가 없으므로 현재 구현은 index_stale/context_stale를 정상 200 데이터 enum으로 반환하지 않는다. 구 컨텍스트는 503으로 재조회하게 한다. 잘못된 서명·미래 발급시각·입력은422다.

### 설정과 운영 반영 경계

- 기본 기대 스키마와 로컬 적재 guard는0014로 올렸다. 기존 테스트의 현재 head 기대값도 같이 변경했다. 역사 migration0013은 수정하지 않았다.
- 새 설정 `HISTORY_CONTEXT_SIGNING_KEY`는 32자 이상의 전용 지속 난수다. 빈 값은 미설정으로 취급한다. 공급자/LLM 키나 캐시 난수를 재사용하지 않는다. 실제 `.env`와 Render 환경은 수정하지 않았고 테스트에서는 합성 키만 주입했다.
- 미래 배포에는 migration0014 적용, `DATABASE_EXPECTED_REVISION=0014`, 전용 서명 키, BE 선배포 후 FE 전환이 필요하다. 이번에는 운영 및 기존 개발 DB에 migration을 적용하지 않았다. 새 DDL은 폐기용 로컬 PostGIS DB에서만 실행했다.
- 이전 v1/v2 API와 기존 Risk/AI 이력 문맥은 유지한다. 새로운 조회의 결과를 기존 AI 집계와 합치지 않는다. 실제 주소별 점포 건수·누락률·운영 지연을 측정한 것으로 보고하지 않는다.

### 검증 기록

2026-11-17 최종 검사 완료. 이전 검토의 '미실행' 기록은 당시 범위다. 아래 결과는 현재 로컬 구현의 실행 결과이며 공개 배포를 뜻하지 않는다.

- FE: 단위231개·배포 프로필4개, 린트·TypeScript 포함 빌드 통과.
