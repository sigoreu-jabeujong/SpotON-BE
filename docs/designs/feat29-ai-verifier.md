### 중단 조건

- 실제 개발 DB가 필요 없다.
- 검증 규칙이 특정 지표 이름·응답 필드명을 확정해야만 성립하면 임의로 정하지 않는다. 작업계획에 이미 있는 관례(지표 객체의 `id`·`value`·`status`, 7절 예시)만 쓴다.

## 1. 검증 대상

- 입력: LLM 응답 텍스트(`LlmResult.text`), 그 요청에 쓴 집계 `context`, 선택적 응답 모델.
- 응답은 JSON이어야 한다(BE-29가 `responseMimeType: application/json`으로 요청). 파싱한 값에서
  - **문장**: 모든 문자열 값(키 제외)
  - **숫자**: 모든 JSON 숫자 값(불리언 제외)과 문장 안의 숫자 표기
  를 모아 검사한다.

## 2. 실패 종류와 규칙

`VerifyFailure`(StrEnum). 한 응답에서 해당하는 종류를 모두 모은다.

| 종류 | 규칙 |
|---|---|
| `malformed_json` | JSON 파싱 실패 |
| `not_object` | 최상위가 객체가 아님 |
| `schema_mismatch` | 응답 모델이 주어졌고 `model_validate`가 실패 |
| `unknown_number` | 입력에 없는 숫자 사용(3절) |
| `forbidden_expression` | 금지 표현(4절) |
| `pending_as_value` | 입력에서 pending·no_data인 지표에 출력이 값을 붙임(5절) |
| `unknown_source` | 입력에 없는 출처 사용(5절) |
| `personal_info` | 개인정보·식별정보 패턴 또는 식별정보 키(6절) |
| `too_long` | 문장 전체 글자 수가 상한 초과 |
| `repetition` | 같은 문장이 두 번 이상 |

- `malformed_json`·`not_object`면 나머지 검사는 하지 않는다.
- 결과 `VerifyResult(failures: tuple[VerifyFailure, ...])`, `ok`는 failures가 비었는지다. 실패 종류만 담고 문제 문장·숫자·응답 원문은 담지 않는다.

## 3. 숫자 규칙 (`unknown_number`)

**허용 숫자 집합**은 `context`에서 모은다.

- JSON 숫자 값(불리언 제외)
- 문자열 값과 **키** 안의 숫자 표기. 예: `"as_of": "2026-09"` → 2026, 9 / `"survival_rate_3y"` → 3 / `"recent_12m"` → 12 / `"R8"` → 8
  - 키를 포함하는 이유: "최근 12개월", "3년 생존율"처럼 지표 이름에 들어 있는 숫자를 해석문이 자연스럽게 쓴다.

**숫자 표기 추출** 정규식: `\d{1,3}(?:,\d{3})+(?:\.\d+)?|\d+(?:\.\d+)?`

- 천 단위 쉼표는 지우고 `Decimal`로 비교한다(`1,200` = `1200`, `12.50` = `12.5`, `09` = `9`).
- 부호는 보지 않는다. 날짜의 `-`를 음수로 오인하지 않기 위해서다. 비교도 절댓값으로 한다.
- `%`·단위는 숫자와 따로 보지 않는다. 폐업률은 작업계획 7절대로 `× 100`된 값이 입력에 있으므로 출력 `12.5%`는 입력 `12.5`와 비교한다. 비율(0.125) ↔ 백분율(12.5%) 환산은 허용하지 않는다(새 숫자 계산이므로).

**반올림 허용**: 출력 숫자가 소수점 `d ≥ 1`자리이고, 허용 숫자 중 하나를 `d`자리로 반올림한 값과 같으면 허용한다(예: 입력 12.53 → 출력 12.5). 출력이 정수면 정확히 같아야 한다. 정수로 반올림까지 허용하면 0.6 → 1처럼 다른 의미의 숫자가 통과하기 때문이다.

한계: "세 곳", "절반"처럼 한글로 쓴 수는 잡지 못한다. 입력 `2026-09`를 출력에서 `2026.09`로 쓰면 하나의 소수로 읽혀 `unknown_number`가 된다(시스템 지침이 기준 시점을 입력 그대로 쓰도록 하므로 허용 범위로 본다).

## 4. 금지 표현 (`forbidden_expression`)

작업계획 2절 제외 지표와 8절 금지 표현, 시스템 지침 5번 규칙에 맞춘다. 공백 차이는 `\s*`로 흡수한다.

- 성공률, 성공 확률, 성공 가능성
- 추천(추천·비추천 모두)
- 위험 점수, 위험 등급
- LQ, 입지계수
- 단정적 예측: `반드시|무조건|확실히|틀림없이` 뒤에 `성공|실패|폐업|망`이 오는 경우, `(성공|실패|폐업)할 것입니다`, `망할`

`창업위험도`(서울시 공식 안내 이름, 작업계획 7절 `official_risk`)는 금지어가 아니다. `위험점수`·`위험등급`만 막는다.

## 5. 지표 상태·출처 (`pending_as_value`, `unknown_source`)

응답 스키마가 미확정이므로 작업계획 7절 지표 객체 관례(`id`, `value`, `status`)를 따를 때만 검사한다. 관례를 따르지 않는 응답에는 적용되지 않는다.

- 입력에서 `status`가 `pending`·`no_data`인 객체의 `id`를 모은다.
- 출력 어디든 같은 `id`를 가진 객체에 null이 아닌 `value`가 있으면 `pending_as_value`.
- 입력의 `source`·`sources` 키 값(문자열 또는 문자열 목록)을 허용 출처로 모은다. 출력의 `source`·`sources` 값 중 허용 출처에 없는 것이 있으면 `unknown_source`.
- 문장 속 출처 언급은 검사하지 않는다. 형식이 자유로워 오탐이 많다.

## 6. 개인정보 (`personal_info`)

출력 문장에서 다음 패턴을 찾는다. 작업계획 8절이 외부 전송·로그에서 빼도록 한 정보다.

- 전화번호: `0\d{1,2}[-.\s]?\d{3,4}[-.\s]?\d{4}`
- 이메일
- 도로명 주소 번호: `[가-힣0-9](?<!으)(로|길)\s?\d+(-\d+)?` 뒤에 수량 단위(`개`·`곳`·`건`·`명`·`년`·`월`·`일`·`분기`·`위`·`배`·`%`·`m`·`km`·`미터`·`호점`·`점포`)가 오지 않는 경우 (예: 양화로 160, 와우산로29길 5)
  - `으로`는 조사라서 앞 글자가 `으`인 `로`는 제외한다. 예: "기준으로 12개 점포"는 주소가 아니다.
- 지번: `동\s*\d+(-\d+)?\s*번지` 또는 `\d+-\d+\s*번지`
- 층·호: `\d+\s*층`, `\d+\s*호(?!점)`, 영문 앞뒤가 아닌 `B\d+` (floor_unit 형태). `1호점`은 지점 번호라 제외한다.
- 좌표처럼 보이는 소수: `\d{2,3}\.\d{4,}` 중 **허용 숫자 집합에 없는 값**. 입력에 정밀한 비율 값이 있으면 그대로 인용할 수 있어야 하기 때문이다.
- building_key 형태: `[가-힣]+구-[가-힣0-9]+-산?\d+-\d+`

이 패턴들은 주소·층호 숫자가 입력에 없으면 `unknown_number`로도 걸린다. 그래도 따로 두는 이유는 실패 종류가 "개인정보"로 구분돼야 BE-35 운영 로그에서 원인을 볼 수 있기 때문이다.

또 출력 JSON 키에 BE-30의 `FORBIDDEN_CONTEXT_KEYS`가 있으면(대소문자 무시) `personal_info`다. 같은 상수를 써서 규칙을 한 곳에 둔다.

한계: 상호·사람 이름은 패턴으로 잡지 않는다. 입력에서 식별정보가 빠지므로(BE-28·30) 모델이 알 수 없다는 전제다.

## 7. 분량·반복 (`too_long`, `repetition`)

- 상한은 `VerifyPolicy.max_chars`(기본 2000자, 문장 전체 합). 작업계획 10절에 따라 명명된 값으로 두되, 화면 분량이 정해지지 않아 환경변수로는 노출하지 않는다.
- 문장은 `.`·`!`·`?`·줄바꿈으로 나누고 공백을 정리한다. 10자 이상인 같은 문장이 두 번 이상 나오면 `repetition`. 짧은 문구("자료 없음")는 반복이 자연스러워 제외한다.

## 8. 재생성 흐름 (`app/ai/verified.py`)

```text
async generate_verified(
    client: LlmClient,
    request: LlmRequest,
    *,
    context: Mapping[str, JsonValue],
    response_model: type[BaseModel] | None = None,
    policy: VerifyPolicy = VerifyPolicy(),
) -> VerifiedOutput(result: LlmResult, data: dict[str, JsonValue], generations: int)
```

1. `client.generate(request)` → 검증
2. 실패하면 **같은 요청으로** 1회 다시 생성 → 검증
3. 또 실패하면 `AiVerifyFailedError(failures)` 발생. `to_app_error()`는 `AppError(ErrorCode.AI_VERIFY_FAILED)`(503)
- 재생성 요청에 "이전 응답이 규칙을 어겼다" 같은 문장을 덧붙이지 않는다. 덧붙이면 BE-30 버전 관리 밖의 프롬프트가 생긴다.
- `client.generate`의 `LlmError`는 잡지 않고 그대로 올린다. 호출자가 `AI_UNAVAILABLE`로 매핑한다. 공급자 장애와 검증 실패를 섞지 않는다.
- 두 번째 생성도 BE-29 한도·시간 예산을 따로 쓴다. 전체 대기 시간 상한은 BE-32에서 정한다.
- `AiVerifyFailedError`의 메시지·repr에는 실패 종류 이름만 넣는다.

## 9. 보안·개인정보

- 검증기·흐름은 로그를 쓰지 않는다. 실패 결과에 문제 문장·숫자·응답 원문·입력 집계를 담지 않는다.
- JSON 파싱·Pydantic 검증 예외는 `except` 밖에서 결과를 만들어 원인 예외(응답 원문 포함)가 체인에 남지 않게 한다(BE-29와 같은 방식).

## Claude Code 검토 기록

### 1차 작성 후 재검토 (2026-11-11, Claude Code)

설계 MD를 처음부터 다시 읽고 이슈 #29 범위, 작업계획 2·7·8·10절, BE-29 `LlmClient`·`LlmError`, BE-30 시스템 지침·`FORBIDDEN_CONTEXT_KEYS`와 대조했다. 아래를 이 파일에 직접 고쳤다.

1. **도로명 패턴 오탐**: 처음 패턴 `(로|길)\s*\d+`는 한국어 조사 "으로"와 겹쳐 "기준으로 12개 점포" 같은 정상 해석문을 개인정보로 거절한다. 해석문에서 가장 흔한 문형이라 거의 모든 응답이 재생성 후 실패할 수 있었다. 앞 글자가 `으`인 경우와 뒤에 수량 단위가 오는 경우를 제외했다.
2. **좌표 패턴과 허용 숫자 충돌**: 입력의 정밀한 비율(예: 12.3456)을 그대로 인용해도 좌표 패턴에 걸렸다. 허용 숫자 집합에 있는 값은 좌표로 보지 않도록 했다.
3. **`호` 오탐**: `\d+호`가 "1호점"(지점 번호)에 걸려 `호점`을 제외했다.
4. **중복 실패 사유 근거**: 주소 숫자는 `unknown_number`로도 걸리는데 왜 `personal_info`를 따로 두는지 적었다.
5. **숫자 규칙 한계 추가**: 날짜를 소수점 표기로 바꿔 쓰는 경우를 한계로 적었다.

검토 후에도 유지한 판단과 이유:

- 재생성 때 요청을 바꾸지 않는다. 바꾸면 BE-30 버전 관리 밖의 프롬프트가 생기고 캐시 키(BE-34)도 흔들린다.
- 공식/참고 혼동 같은 의미 검사는 지표 필드가 확정된 뒤로 미룬다. 지금 정하면 작업계획 9절 확인 대기 항목을 임의로 확정하게 된다.
- 정수 반올림은 허용하지 않는다. 오탐보다 새 숫자가 통과하는 쪽이 더 위험하다고 봤다(작업계획 8절 "없는 숫자" 검증이 BE-T08 필수 사례).
- 분량 상한은 환경변수로 노출하지 않는다. FE 화면 분량이 정해지지 않았고, 운영 중 바꿀 이유가 아직 없다.

남은 제한: 13절과 같다.
