## 1. 범위·현재 확인

기존1166일반/146통합·22개 BE연속 검사는 과거 결과이며 이번 실행으로 갱신한다. 개발DB와Kakao/LLM 키는 값이 아닌 존재 여부만 확인했다. 개발DB컨테이너는 healthy이고 BE/FE 워킹트리는 깨끗했다. 이전 API 흐름의 모의 AI 성공을 실제 공급자 성공으로 바꾸어 보고하지 않는다.

FE 직접 수정/설정/문서/이슈/PR 금지 지시는 유지한다. FE는 lint/build·실제 브라우저에서 요청/화면/오류를 검사하고 문제는 BE의 docs/fe-system-audit-request.md에 담당자 변경 요청으로 적는다. 테스트용 env는 자식 process/Settings 복사본에만 주입하고 실제 .env/Docker·원본/의존성/기존FE파일은 바꾸지 않는다. 브라우저 도구만 임시폴더에 준비할 수 있으며 repo 의존성에 추가하지 않는다.

브랜드57 미신청/승인대기는 재인증하지 않는다. 공식/조건부 수치의 pending·지원기관 공통링크의 맞춤정렬 미적용·AI추가문맥/자유문장 의미검증 전체·로그30일보관삭제는 미완료 항목이다. 검사로 구현 완료라고 표시하지 않는다. 새 필수 키/권한/자료 부재를 발견하면 해당 의존 작업은 중단·요청한다.

## 3. 실제/격리 실행 계획

- 실제개발DB: 기존 local target guard·READ ONLY RR API/검증세션 사용. 임시settings로hash검증 세션제한만120초 허용한다. migration/원천적재/UPDATE/DELETE는 하지 않는다. 검사전/후14테이블 전체행/geometry hash를 기존baseline과비교하고 metadata/index/버전/불변성/데이터준비상태를집계한다.
- 격리DB: 별도loopback포트55478/명시된일회용PostGIS컨테이너. 기존integration安全guard를유지하고실제개발URL과다른fixtureDB만쓴다. 종료시이작업이만든ID/name을검증한컨테이너만중단한다.
- 실제API: 기존검증helper는먼저읽고쓰기/오래된주입/원문출력이없음을확인한것만사용한다. 필요하면 ignored helper로API별순차matrix/오류코드/지표/출처/날짜/캐시검사를실행하고집계JSON만남긴다. 실제Kakao는공개주소/필요한실패대조만소수요청하며기존로컬키를사용한다. 인증/권한실패시연계를중단하고요청한다.
- 실제AI: 기존env모델/키·서버클라이언트를사용한다. client retry0, 사례최대2개/각검증재생성1회로 외부HTTP시도최대4개를강제한다. 외부원문/토큰/키/위치/점포ID를기록하지않고HTTP상태/검증사유/후보수/지연/호출수만수집한다. 한도/인증에막히면반복호출하지않는다. 같은모델명의가용성과응답형식을실제관측하며현재모델의범용안전성을보장하지않는다.
- FE: 현재checkout와원격developSHA를비교해검사기준을명시한다. npm lint/build는추적파일변경없이실행한다. 별도Viteprocess의env로VITE_USE_MOCK=false/API기본주소, BE프로세스settings복사본의CORS에해당테스트origin을허용한다. FE실제.env는수정하지않는다. headlessChrome/Playwright로경로/표/필터/보고서/실패를보며APIpath/status·pageerror종류·검사결과만기록한다. 브라우저자동AI는모의공급자로검증하고실제모델검사는위별도제한호출로구분한다. 실제주소/화면원문을저장/로그로유출하지않는다.
- 원천파일ETL: 기존대용량입력/manifest가없으면다운로드/확보를임의확장하지않고현재필수자료경계에서보고한다. 읽기dry-run외새적재는하지않는다. 브랜드57은既知차단이다.

## 4. 결함 수정/보고

## 6. Claude 검토 결과 (2026-11-12)

- 검토 방법: 이 MD만 Read/Edit했다. 코드·DB·.env·다른 파일·네트워크·Git은 접근하지 않았다. 따라서 아래 내용은 문서 정합성 기준의 지적이며 실제 구현 여부는 확인하지 않았다(Codex 대조 필요).
- §1~§5 본문은 수정하지 않았다. 본문 변경이 필요한 사항은 아래 권고(R-번호)로만 남겼으며, 채택 여부와 본문 반영은 Codex가 실제 코드와 대조한 뒤 결정한다.

### 6.1 총평

방향(실제/모의 분리, 실제DB 읽기 전용·hash 보존, FE 무수정·요청서 분리, 실모델 상한)은 타당하다. 다만 아래 항목은 "설계상 산술"이나 "의도"로만 적혀 있고 **강제·검증 수단**이 빠져 있어, 실행 중 조용히 위반되거나 결과 보고 때 실제/모의가 섞일 위험이 있다. 우선순위 높은 항목은 [높음]으로 표시했다.

### 6.2 실제/모의 분리

- [높음] R1 결과 표기 축 누락: §2의 5상태(통과/부분/차단/미구현/실패)만으로는 "모의로 통과"와 "실제로 통과"가 구분되지 않는다. 각 행 결과에 **근거 출처 축**(실제 실행 / 모의·격리 실행 / 기존 검사 재사용(커밋·일자 명시) / 정적 확인)을 별도 열로 두고, 한 행에 혼재하면 하위 항목별로 나눠 적도록 권고한다. 예: 행10 AI = "서버 검증 로직 통과(모의) + 실공급자 2사례 관측(실제)".
- [높음] R2 브라우저 BE 프로세스의 실키 상속: §3 FE 항목은 "브라우저 자동 AI는 모의 공급자"라고만 적었다. 브라우저용 BE 프로세스가 실제 LLM 키/모델 env를 상속하면 AI 버튼 클릭·재렌더·재시도마다 실공급자가 호출되어 4회 상한을 우회한다. 브라우저용 BE settings 복사본에서 **LLM 키 제거 + 공급자 모의 강제**를 하고, 실행 후 외부 LLM 호출 수 0을 확인하는 단계를 명시하도록 권고한다. 같은 원칙을 전체 pytest/통합 테스트 프로세스에도 적용한다(실키가 env에 남아 있으면 테스트가 실호출할 수 있음).
- R3 FE 모의 폴백 확인: VITE_USE_MOCK=false여도 FE 코드에 오류 시 mock 데이터 폴백, 하드코딩 fixture, MSW 등록 등이 있으면 화면은 정상이어도 실제 BE 연결이 아니다. 화면별로 "기대 API path가 실제 BE에 도달했는지(BE 측 요청 수/상태)"를 대조해 화면 표시와 네트워크를 함께 판정하도록 권고한다. Vite는 기존 process env가 .env 파일보다 우선하지만, FE가 다른 변수명/런타임 설정을 쓰는지 확인이 필요하다.
- R4 Kakao 실/모의: 브라우저 검색도 실제 Kakao를 호출한다(BE 경유). 브라우저 검사에서 발생한 Kakao 호출 수를 §3 "소수 요청"에 합산해 기록하거나, 브라우저용 BE는 Kakao를 모의로 두고 실제 Kakao는 API 단계에서만 검사하도록 하나를 선택해 명시하라.

### 6.3 기능 전체 판정 규칙

- [높음] R5 상위 판정 규칙: 행별 상태를 전체 결론으로 합치는 규칙이 없다. 권고: "실패 1개 이상 → 전체 실패", "차단/미구현이 남으면 → 전체 '조건부(목록 명시)'이며 '정상' 표현 금지", "모든 행 통과(실제 근거) → 정상". §4 마지막 문장(FE 차단 시 완료 주장 금지)을 FE 외 행(ETL 원천 미확보, 브랜드57, 실공급자 한도 차단)으로 일반화하라.
- R6 기지 미완료 항목 매핑: §1의 미완료(공식/조건부 수치 pending, 지원기관 맞춤정렬 미적용, AI 추가문맥/자유문장 의미검증, 로그 30일 보관·삭제, 브랜드57)는 해당 행(8·9·10·11·12)에서 "부분"이 아니라 **"미구현(기지)"**로 고정 표기하고, 검사 통과 항목과 섞지 않도록 권고한다. "pending을 올바르게 반환함"은 통과이지만 "수치 기능 자체"는 미구현으로 둘 것.
- R7 "부분" 정의: 하위 검사 중 일부만 실행/통과한 경우와, 기능은 통과했으나 실제 원천 확인이 불가한 경우를 구분해 사유를 필수로 적게 하라.
- R8 재사용 근거의 유효성: §2 "기존 검사로 확인한 경계는 재사용"은 이번 기준 SHA(45a6bbf) 이후 해당 영역 코드가 바뀌지 않았을 때만 유효하다고 조건을 명시하라(예: 행5 "원자료20표본 기존검사근거").

### 6.4 실모델 4회 hard cap

- [높음] R9 상한 강제 위치: "client retry0 + 사례2×(1+재생성1)=4"는 설계 산술이다. 다음 경로로 초과될 수 있다.
  - SDK/HTTP 클라이언트 기본 재시도(많은 LLM SDK가 기본 max_retries>0), transport 재시도, 리다이렉트.
  - 타임아웃 후 클라이언트는 실패로 보지만 공급자 측은 처리·과금된 시도.
  - 동시 cache miss 시 같은 키로 중복 호출, 앱 내부의 별도 재생성 루프.
  - 스크립트 오류·코드 수정 후 **재실행**(실행 단위 카운터는 매번 0부터 시작).
  권고: 외부 HTTP 송신 직전(transport 계층) 카운터로 시도를 세고 4 도달 시 송신 자체를 거부하며, 카운터는 **이번 작업 전체 누적**(파일/기록 기반)으로 둔다. 4회 소진 후 추가 실호출이 필요하면 사용자 승인을 받는다. 타임아웃·연결오류도 1회로 센다.
- R10 중단 조건 구체화: 인증 실패(401/403)·한도(429)·모델 미존재(404)는 첫 발생 즉시 남은 사례를 포함해 실호출을 중단한다고 명시하라. 5xx도 재시도하지 않는다.
- R11 해석 한계: 2사례는 형식/가용성 관측일 뿐 품질·안전성·결정성 판정 근거가 아니다(§3 마지막 문장과 일치). 결과 보고에 "표본 2, 통계적 의미 없음"을 적도록 권고한다.

### 6.5 FE 수정 금지

- [높음] R12 lint/build의 부수 변경: `npm install`/`npm i`는 package-lock 등 추적 파일을 바꿀 수 있으므로 금지하고, node_modules가 없으면 lockfile 기준 설치만 허용하거나 차단으로 보고하라. build 산출물(dist, tsbuildinfo, vite cache)이 추적 파일인지 확인하고, 실행 전/후 FE 워킹트리 상태 비교를 완료 조건에 넣어라(Codex 측 수행).
- R13 FE 기준 SHA 불일치 시: 현재 checkout과 원격 develop이 다르면 FE에서 pull/checkout을 하지 말고(FE 워킹트리 변경에 해당) 현재 checkout 기준으로 검사하며 불일치를 범위 한계로 기록할 것을 명시하라.
- R14 BE 쪽 우회 금지 명확화: FE 결함을 이유로 BE 계약을 바꾸지 않는다는 §4 원칙에 더해, 테스트용 CORS 허용 origin은 settings 복사본에만 넣고 실제 기본 설정/코드에 테스트 origin을 남기지 않는다고 명시하라.
- R15 FE 결함 분류: 요청서 항목마다 (FE 단독 결함 / BE 계약 불일치 중 BE가 명세 위반 / 명세 자체 모호) 분류를 두면 BE 수정 대상과 FE 요청 대상을 섞지 않는다.

### 6.6 실제 DB 보존

- [높음] R16 hash 불일치 시 처리: 검사 후 14테이블 hash가 baseline과 다를 때의 절차가 없다. 권고: 즉시 실제DB 대상 작업 중단 → 복구·재적재 등 **쓰기 조치 금지** → 차이 테이블/행수만 기록하고 사용자에게 보고. 다른 프로세스(개발 중 ETL 등)의 동시 쓰기 가능성도 원인 후보로 적는다.
- R17 ETL dry-run 세션: §3은 API 세션의 READ ONLY만 명시한다. 실제 원천 dry-run이 실제DB에 접속한다면 동일하게 READ ONLY 세션·local target guard를 거치는지, 임시 테이블/advisory lock/시퀀스 사용 경로가 없는지 확인 항목으로 추가하라.
- R18 격리DB 대상 오인 방지: 포트 55478 사용 중 여부와 컨테이너 이름 충돌을 사전 확인하고, 실제 개발 DB URL과 host/port/dbname이 모두 다름을 실행 전에 단언(assert)하라. 정리 시 이 작업이 만든 볼륨도 ID로 검증해 제거하고, 기존 컨테이너/볼륨은 건드리지 않는다.
- R19 hash 범위: 행/geometry hash 외에 스키마(alembic head, 인덱스, 제약) 전/후 비교를 같은 보고에 남기면 "앱모델 차이0"과 보존 판정이 일관된다.

### 6.7 브라우저 민감정보와 차단 시 처리

- [높음] R20 브라우저 산출물: Playwright trace/video/screenshot/HAR, Chrome 사용자 프로필, console 로그는 실제 주소·점포 정보·API 응답 본문을 포함할 수 있다. 기본값으로 trace/video/HAR를 끄고, 스크린샷이 필요하면 임시 폴더에만 두고 종료 시 삭제하며, 기록은 path/status/pageerror 종류/판정만 남긴다고 명시하라. 임시 프로필 디렉터리도 삭제 대상에 포함한다.
- R21 URL 쿼리 노출: 주소가 GET 쿼리스트링으로 전달되면 Vite dev server 로그, BE 접근 로그, 브라우저 네트워크 기록에 남는다. 기록 시 쿼리 제거(path만) 규칙을 명시하라.
- R22 검사 입력: 브라우저 검사에는 공개 주소(예: 관공서 등) 또는 합성 입력만 쓰고, 개인 주소를 쓰지 않는다고 명시하라.
- [높음] R23 브라우저 차단 시 처리: 다음 경우 행13을 "차단"으로 기록하고 **API 단독 검사로 대체해 통과 처리하지 않는다**. Chrome/Playwright 확보 불가(설치·다운로드 거부 포함), CORS/프록시 문제로 연결 불가, FE build 실패, FE가 실제 모드로 기동 불가. 이때 FE 코드/설정을 고쳐 우회하지 않고 요청서에 재현 조건을 적는다. 브라우저 도구 다운로드는 외부 네트워크 행위이므로 허용 범위(임시 폴더, repo 의존성 미추가)를 넘는 설치가 필요하면 중단·요청한다.

### 6.8 누락된 장애 경로(검사표 보완 후보)

- DB 연결 중간 단절·pool 고갈·statement timeout 시 503 외피와 캐시 미저장(실패 응답이 캐시되지 않는지).
- Kakao DNS/연결 거부·5xx·느린 응답(timeout 경계 직전/직후).
- LLM 응답이 JSON 파손·스키마 불일치·빈 응답일 때 재생성 1회 후 실패 외피와 지표 응답의 독립성(행10에 일부 있음, 실공급자 경로에도 적용).
- 동시 요청 중 클라이언트 취소 후 대기자 처리(행11에 있음) — 실제 DB 연결 반환 여부까지 확인.
- 데이터 준비 상태 미완(원천 일부만 적재)에서 각 API가 빈 결과/pending/503 중 무엇을 반환하는지 일관성.
- 시간대/월말 경계: KST 기준 월말·당일 개폐업(행7) 외 서버 시간대가 UTC일 때의 YTD/기간 계산.
- CORS 비허용 origin·preflight 실패, 허용 origin의 실패 응답에도 CORS 헤더가 붙는지(브라우저에서 5xx가 CORS 오류로 가려지는 문제).
- 행12 외부 URL 가용성 확인은 네트워크 요청이므로 횟수 제한·식별정보 미포함을 명시.

### 6.9 범위·측정 한계(보고서에 명시 권고)

- 부하·성능·장시간 안정성은 측정하지 않는다(동시성은 기능적 경합만).
- 단일 Windows 로컬 환경, 단일 브라우저(headless Chrome), 데스크톱 뷰포트 기준이며 모바일·접근성·타 브라우저는 미검사.
- 실제 데이터는 현재 개발 DB 스냅샷 기준이며 운영 데이터 대표성은 보장하지 않는다.
- 실제 Kakao/LLM은 소수 표본 관측이며 공급자 정책·모델 변경에 따라 달라질 수 있다.
- 기존 검사 재사용 항목은 이번에 재실행하지 않았음을 표시한다.
- 외부 URL "현재 가용성"은 검사 시점 1회 관측이다.
- 본 검토(§6)는 문서만 근거로 하며 코드·실행 결과를 확인하지 않았다.

### 6.10 Codex 대조 시 우선 확인 목록

1. R2·R9: 브라우저/테스트 프로세스의 LLM 키 제거와 transport 계층 누적 카운터 존재 여부.
2. R16: hash 불일치 시 중단 절차.
3. R20·R21: Playwright 산출물 기본값과 쿼리스트링 기록 여부.

5. R1·R5·R6: 결과 표의 근거 출처 열과 상위 판정 규칙.

## 7. Codex 최종 결정

Claude 실제 수정 diff와 CLI 결과(is_error=false,3turns,permission_denials=[])를 확인했다. 결과 표에는 상태와 근거(실제/격리·모의/정적/과거 재사용)를 따로 둔다. 기존 미구현·승인대기는 검사 통과와 분리하고, FE나 외부 기능에 실패/차단이 있으면 전체 정상 판정을 하지 않는다. FE 결함은 BE의 요청 보고서에만 남긴다.

브라우저용 BE는 LLM 키를 제거한 Settings 복사본과 모의 공급자를 강제하고 외부 LLM 송신을 차단한다. 실제 AI는 별도 transport의 송신 직전 누적4회 ledger를 ignored파일에 기록한다. ledger는 재실행 시 초기화하지 않으며 HTTP 오류/timeout도 시도로 센다. 인증/한도/모델경로 오류·5xx는 즉시 후속 실호출을 멈춘다. 일반 검사는 기존 명시적 mock/client를 쓰며 테스트 프로세스에 실제 키를 추가하지 않는다. 실제 Kakao는 API/브라우저 전체의 호출을 합산한다.

실제 API/ETL dry-run의 읽기전용 세션을 코드에서 확인하고, 검사 전후 schema/인덱스·14테이블 hash를 비교한다. 불일치하면 실제 DB 작업을 중단하고 원인 확인 전 쓰기 복구를 하지 않는다. R18은 host/port/dbname 각각이 다르다는 뜻으로 적용하지 않는다. loopback host가 같아도 연결 대상 tuple이 개발 DB와 다르고 fixture DB 이름을 확인하면 분리된다. 새 테스트 컨테이너의 정확한 ID/name을 확인해 중단하고 기존 볼륨은 건드리지 않는다. 현재 FE checkout과 원격 develop은21ec13f로 일치하며 lint/build 전후 추적파일 변경이 없다.

브라우저 trace/video/HAR/스크린샷을 만들지 않고 console/response는 query를 제외한 path/status·오류 종류/고정 fingerprint만 남긴다. Chrome은 Playwright가 만든 임시 프로필을 닫아 정리한다. 실제 주소는 공개 건물만 사용하고 파손 입력은 합성값만 사용한다. 브라우저를 못 실행하면 해당 행을 차단으로 남기며 API 통과로 대체하지 않는다. R6.8의 DB/원천 실패503 권고는 현행 계약과 달라 채택하지 않는다. DB/서버는500, upstream502, AI한도/실패503을 실제 코드에 맞게 확인한다. 직접 BE 결함이 확인될 때만 최소 수정/회귀를 추가한다.
