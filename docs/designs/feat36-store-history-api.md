## 1. 확인한 현재 상태

- 개발 DB 연결 및 migration `0002` 정상. 전체 689,440건, 지원 업종 355,835건이다.
- 지원 업종 및 `deleted_at IS NULL` 조건에서 개업일 null 0건, 상호 null 0건, 폐업 상태이면서 폐업일 null 16건, `date_flag IS NOT NULL` 56건이다. 날짜 플래그는 중첩되므로 이 수를 제외 건수로 간주하지 않는다.
- 기존 API는 health와 geocode이며, 앱 요청용 DB 세션 수명주기는 아직 없다.
- Store는 날짜·상호·상태·층호수·프랜차이즈에 null을 허용한다. 인허가 식별자는 `(source, license_no)`다.
- ETL 스냅샷은 `update_point`와 `collected_at`을 보존하지만 DB에는 원천 갱신일·배치 수집 완료일을 조회할 전용 모델이 없다. `Store.updated_at`은 DB 적재 시각이므로 원천 갱신일로 사용할 수 없다.
- 이번 개발 DB 적재는 사용자 제공 검증 CSV(2026-11-09 검증, 원천 기준일 미확인)에서 왔다. 이 CSV의 검증일·파일 생성일·DB 적재일은 원천 갱신일(DAT_UPDT_PNT)이 아니다. 스냅샷의 `collected_at`도 실제 Open API 수집 완료 시각인지, CSV 변환/검증 시각인지 구현 전 확인해야 한다.
- FE의 `HistoryStore.open_date`, `operating_months`는 필수이며 표는 개업일 문자열 정렬 및 `license_no` 단독 React key를 사용한다. 결측 기간과 서로 다른 원천의 같은 관리번호를 안전하게 표시하는 보완이 필요하다.

### 날짜 용어 고정

이 설계에서 아래 네 날짜를 서로 대체하지 않는다. 필드명은 §4·§6 계약 확정 전까지 설계용 이름이다.

| 설계 용어 | 의미 | 출처 | 영업 기간 종료점 사용 |
|---|---|---|---|
| `data_updated_at` | 원천 DAT_UPDT_PNT(`update_point`)의 검증된 최대 날짜 | 원천 행의 허용 필드 | 영업 중 점포에만 사용 |
| `collected_at` | 원천에서 배치 수집을 완료한 시각 | 수집 실행기 기록 | 사용 금지 |
| `loaded_at` / `Store.updated_at` | DB에 upsert한 시각 | DB | 사용 금지 |
| 요청 시각(today) | API 호출 시각 | 서버 시계 | 사용 금지 |

위 숫자는 개발 DB에 대한 읽기 전용 집계다. 사용자 CSV의 전체 원천 기준일이 확인됐다고 주장하지 않는다.

## 3. 조회·위치 설계

입력은 필수 `building_key`, 선택 `floor_unit`, 선택 `category=cafe|restaurant`다. 주소 원문 입력이나 외부 API 호출은 받지 않는다.

- building_key는 기존 서울 지번 키 규칙의 canonical 값인지 검증한다. 공백·제어문자·초과 길이·잘못된 구성을 거절하며 검증 오류에 입력 원문을 반사하지 않는다.
- floor_unit은 기존 정규화기를 재사용한다. 선택값 생략과 유효하지 않은 입력을 구분하고 유효하지 않은 상세 위치를 조용히 같은 자리로 판정하지 않는다.
- SQL은 바인딩 매개변수로 `building_key` 완전 일치, `deleted_at IS NULL`, 현행 지원 category/sub_category만 선택한다. 기본안은 ETL이 확정 매핑한 카페·음식점 4종만 포함하고 `excluded`와 상호 키워드 후보·업태 오기 검토 대기 행은 제외하는 것이다. 작업계획 5절의 "검토 대기는 자동 포함하지 않는다"를 따르며, 실제 컬럼값(`category_review_flag` 등)과의 대응은 구현 시 ETL 코드와 대조해 테스트로 고정한다.
- 식별자는 `(source, license_no)`다. 다른 source의 같은 license_no를 중복 제거·병합하지 않고 각각 반환한다. 응답 항목에 `source`를 포함해야 FE가 `source + license_no` 복합 key를 쓸 수 있으므로 FE 계약 추가 대상이다(§6). 내부 DB `id`는 정렬 동률 처리에만 쓰고 응답 식별자로 노출하지 않는다.
- `category`는 진단 맥락이며 SQL 업종 제거 필터로 쓰지 않는다. 한시 사업장·좌표 결측을 이력에서 자동 제거하지 않는다. 공간 계산 API가 아니기 때문이다.
- 날짜가 불완전하더라도 이력 자체를 숨기는 것으로 기간 결측 문제를 해결하지 않는다. 유효 개업일 오름차순, 누락·무효 개업일 마지막, 동률은 source/license_no/id로 안정적으로 정렬하는 안이다.
- 입력·점포 상세 위치가 모두 명확하고 층과 호수가 모두 일치할 때만 same_spot이다. 확인된 위치가 다르면 same_building, 어느 쪽이 없거나 충돌·모호하면 unverified다. 층만 동일한 경우 same_spot을 반환하지 않는다. 비교는 원문 문자열이 아니라 기존 정규화기의 구조화된 층·호수 값으로 한다.

위치 판정표(설계안, 테스트로 고정):

| 입력 floor_unit | 점포 floor_unit | 결과 | 이유 |
|---|---|---|---|
| 층·호수 명확 | 층·호수 명확, 둘 다 같음 | same_spot | 유일한 확정 조건 |
| 층·호수 명확 | 층 다름 | same_building | 확인된 다른 위치 |
| 층·호수 명확 | 층 같음, 호수 다름 | same_building | 확인된 다른 위치 |
| 층·호수 명확 | 층만 있음(같은 층) | unverified | 층만 같음 → same_spot 금지 |
| 층만 있음 | 층·호수 명확, 같은 층 | unverified | 층만 같음 → same_spot 금지 |
| 층만 있음 | 층만 있음, 같은 층 | unverified | 층만 같음 → same_spot 금지 |
| 층만 있음 | 층 다름 | same_building | 층이 확인된 다른 위치 |
| 호수만 있음 | 무엇이든 | unverified | 호수만으로 같은 자리 확정 불가 |
| 명확 | null·`location_level = unverified`·범위층(예: 1~2층)·복수 호수 | unverified | 결측·모호 |
| 생략 | 무엇이든 | unverified | 비교 기준 없음(같은 건물은 building_key 일치로 이미 전제) |
| 유효하지 않은 값 | — | 422 INVALID_PARAM | 조용히 생략·같은 자리 처리 금지 |

"생략 시 unverified" 대신 same_building을 쓸지는 원본 F-02 정의와 FE 표시 문구를 대조해 확정한다(보류). 어느 쪽이든 same_spot은 반환하지 않는다.
- `is_franchise` true/false/null은 franchise/independent/unknown으로 대응한다. 매칭 모듈이 아직 없다는 이유로 null을 false로 바꾸지 않는다.
- 0건은 200, total=0, stores=[], message=`이 건물에서 확인된 음식점·카페 인허가 기록이 없어요`다.

## 4. 기준일·영업 기간과 출처

원본 API §2-4·§4-2 및 데이터 활용 명세 7쪽에 따라 폐업 점포는 검증된 close_date, 영업 중 점포는 검증된 원천 DAT_UPDT_PNT 최대 날짜를 종료점으로 한다. today·파일 수정 시각·DB updated_at·재적재 시각으로 대체하지 않는다. 기타 상태를 영업 중으로 추정하지 않는다.

- 미래 개업·1960년 이전·파싱 실패·폐업일 역전·필수 종료일 누락은 기간 미산정이다. ETL의 날짜별 플래그와 실제 날짜를 함께 확인한다. 무관한 플래그까지 일괄 제외하는 방식은 피한다.
- 시작일 이후의 종료점이 확인되지 않으면 숫자 0을 만들지 않는다. 0개월은 정상적으로 계산된 실제 1개월 미만 기간에만 사용한다.
- **폐업일 결측 16건**: 상태가 폐업이면 종료점은 close_date뿐이다. close_date가 없다고 `data_updated_at`·today·적재일로 대체하거나 영업 중으로 바꾸지 않는다. 이력 행은 유지하고 상태도 폐업으로 유지하며 기간만 미산정이다. 미산정의 응답 표현(null/생략/상태 필드)은 §6-1 확정 전 구현하지 않는다. 16건은 `date_flag` 56건과 겹칠 수 있으므로 별도 건수로 합산하지 않는다.
- 영업 중 점포도 해당 source의 `data_updated_at`이 미확인이면 기간 미산정이다. 개업일이 `data_updated_at`보다 뒤이면 역전으로 보고 미산정이다.
- 후보 계산식은 달력상 완료된 개월 수: `(종료연도-시작연도)*12 + 종료월-시작월 - (종료일의 일 < 시작일의 일)`이다. 1/31→2/28, 윤년 2/29, 시작일=종료일의 처리 사례를 사용자 확정 후 고정한다. 기존 분석 정의에는 단위·버림이 제안으로만 기재되어 있어 이 식을 확정 원문으로 인용하지 않는다. **§6-2 확정 전에는 산식을 구현하지 않고, 기대값을 고정한 테스트도 작성하지 않는다.**
- 원천의 DAT_UPDT_PNT 최대값은 두 검증 CSV/스냅샷의 허용 필드에서 파싱·품질 확인한 값이어야 한다. 미래값(배치 collected_at 이후)·파싱 실패·이상값으로 기준일이 확장되면 그 값을 채택하지 않고 중단한다. 일반음식점·휴게음식점은 source별로 별도 `data_updated_at`을 가지며 한쪽 값을 다른 source 점포의 종료점으로 쓰지 않는다. 현재 사용자 CSV는 원천 기준일 미확인 상태이므로, 이 CSV 행의 update_point 최대값을 "원천 전체 기준일"로 표기할 수 있는지는 사용자 확인이 필요하다.
- API 요청 시 로컬 CSV/스냅샷을 읽지 않는다. DB의 배치 출처에 연결해 같은 데이터 버전에서 같은 결과를 반환한다.

DB에 배치 출처가 없으므로 구현 전 BE-04와 연결한 최소 기반 설계가 필요하다. 제안은 별도 `store_import_batches` 테이블에 batch_id, source, 검증된 data_updated_at, collected_at, 실제 mapping/rule version을 기록하고 ETL 쓰기와 동일 트랜잭션으로 저장하는 것이다. 기존 배치 연결은 원자료·정규화 결과와 검증한 후 진행하며, 단순 건수 일치만으로 배치를 동일시하지 않는다. 필요하면 검증 스냅샷 재적재로 출처를 부여하되 비ETL 필드를 보존하고 멱등성·원자성을 다시 검증한다. 이는 아직 migration·DB 변경 승인을 요청하거나 실행한 기록이 아니다.

기준일이 확인되지 않으면 null과 사유를 유지한다. 수집 완료일과 업종/정제 버전을 추정해 고정 문자열로 채우지 않는다. 출처 기반 없이 완전한 DataVersion을 제공했다고 표시하지 않는다.

출처 테이블 설계 요건(구현 전 승인 대상):

- **원자성**: 배치 행 생성(`status = loading`) → stores upsert → 건수·표본 검증 → `status = completed`, 검증 시각 기록을 한 트랜잭션으로 처리한다. 실패하면 stores 변경과 배치 행을 함께 롤백하고, 부분 적재된 배치가 API에 노출되지 않게 한다.
- **현재 버전 선택**: API는 source별 최신 `completed` 배치를 사용한다. `max(Store.updated_at)`·`max(batch_id)` 문자열 비교·배치 행 생성 시각으로 최신을 고르지 않는다. 반환 행의 `batch_id`가 선택 배치와 다를 때(예: 이전 배치에만 있고 이번 원천에 없는 행)의 처리 기준을 정해야 한다(보류).
- **재적재 검증**: 같은 스냅샷을 다시 적재하면 stores 행 수·핵심 필드·`data_updated_at`이 변하지 않아야 한다(멱등). 비ETL 필드(`brand_id`·`is_franchise` 등 후속 작업 값)는 덮어쓰지 않는다. 재적재가 적재 시각만 바꾸고 원천 기준일을 바꾸는 일이 없어야 한다.
- **버전 신뢰성**: mapping/rule version은 적재 실행 시 코드에 정의된 상수를 기록한 값만 인정한다. 기존 689,440건에 대해 사후 추정한 버전·날짜를 채워 넣지 않는다. 기존 행의 `batch_id` 채움 여부와 값은 구현 시 읽기 전용 집계로 확인하고, 연결 근거가 없으면 해당 출처 필드는 null과 사유로 둔다.
- 데이터 버전 식별값은 선택된 source별 배치 ID·data_updated_at·rule version의 조합으로 결정적이어야 하며, 같은 DB 상태에서 요청마다 달라지지 않는다. 일반/휴게 두 source가 한 응답에 섞일 때 meta에 source별 목록으로 둘지 단일 값으로 합칠지는 §6-3에서 확정한다.
- migration·ETL 변경·기존 데이터 재적재는 개발 DB 쓰기이므로 사용자 승인 후 진행한다.

## 5. 계층·오류·검증 계획

- `app/schemas/stores.py`: 확정된 요청·응답 모델. 출력은 기존 `{data, meta, error}` 외피를 쓴다.
- `app/services/store_history.py`: SQL 조회와 응답 변환. 계산은 순수 함수로 분리한다.
- `app/routers/stores.py`: 입력 검증·응답만 담당, main.py에 등록한다.
- DB 의존성은 import 시 접속하지 않는다. 엔진은 앱 lifespan에서 지연 생성·소유하고 shutdown 시 dispose한다. 세션은 요청별 의존성으로 열고 성공·예외·클라이언트 연결 종료 모두에서 닫는다. health·geocode는 DB 의존성을 주입받지 않으며 DATABASE_URL 미설정·DB 다운 상태에서도 기존처럼 동작해야 한다.
- **읽기 전용**: history 세션은 `READ ONLY` 트랜잭션으로 열고 commit 없이 종료한다. 앱 계정 권한(superuser 아님)에만 의존하지 않고 코드 경로에서도 쓰기를 차단한다.
- **시간 제한**: 연결 timeout과 문장 단위 `statement_timeout`을 명명된 설정으로 둔다. 원본 3초 규칙을 그대로 적용할지, 연결/쿼리/전체 요청 중 어디에 적용할지는 보류(§6-4). 기본값을 정하기 전 `building_key` 인덱스를 사용하는 실행 계획을 개발 DB에서 읽기 전용으로 확인한다.
- **오류 매핑**: DB 미설정·접속 실패·timeout을 어떤 현행 코드로 줄지 보류(§6-4). 후보는 500 INTERNAL_ERROR이며, `UPSTREAM_ERROR`는 외부 API용이므로 DB에 쓰려면 계약 확인이 필요하다. 새 오류 코드는 만들지 않는다.
- DB 오류에 SQL·접속 URL·예외 원문을 넣지 않는다. 성공·실패에 no-store, building_key·floor_unit이 포함된 쿼리·행·예외 로그 비노출을 확인한다.

### API meta와 공통 형식

- 외피는 현행 `{data, meta, error}`를 유지한다. 현행 오류 응답의 `meta = {}`를 history만 `null`로 바꾸지 않는다. 원본의 고정 meta 구조로 공통 형식을 일괄 변경하지 않는다.
- history 성공 meta에 넣을 후보는 source별 `data_updated_at`·`collected_at`·데이터 버전이며 `loaded_at`은 넣지 않거나 넣더라도 원천 기준일과 다른 이름으로 구분한다. 키 이름·위치는 BE-04 `DataVersion`과 원본 API §2-1 meta 대조 후 확정(§6-3)한다. 미확인 값은 null과 사유로 두고 빈 문자열·추정값을 쓰지 않는다.
- 원본과 현행의 차이(meta 구조, 오류 meta 값, 400↔422)는 9절 동기화 대상으로 PR에 명시한다.

## 6. 검토 시 제기된 계약 쟁점

1. **영업 기간 결측 계약**: 폐업일 없는 폐업 16건 등은 이력을 유지하고 `operating_months=null` 및 상태·사유를 반환하는 안을 제안한다. 정확한 상태·사유 필드 위치와 FE 타입·정렬·미확인 표시의 최소 보완 범위를 확정해야 한다. 현행 FE는 number만 허용하므로 BE만 조용히 바꾸지 않는다.
2. **개월 산식**: 달력상 만 개월과 일수/30 방식은 결과가 다르다. 위 달력상 완료 개월 수를 제안하되 원문이 확정하지 않은 산식을 임의 구현하지 않는다.
3. **출처·meta 계약**: `store_import_batches` 추가(migration) 승인, 현재 CSV의 update_point 최대값을 원천 기준일로 표기 가능한지, `collected_at`의 실제 의미, history meta 키·source별 표현, 응답 항목 `source` 추가와 FE 복합 key 보완.
4. **DB 운영 계약**: 시간 제한 값과 적용 범위(원본 3초), DB 미설정·실패·timeout의 오류 코드·HTTP 상태.
5. **세부 판정**: floor_unit 생략 시 unverified/same_building, 원본 category 필수 여부(현행 설계는 선택)와 CATEGORY_REQUIRED 적용 여부.

BE 작업계획 9절은 “원본 확인 → 명세 수정·FE 합의 → 구현·배포” 순서를 요구한다. 아래 Codex 최종 점검에서 현행 사용자 요청과 확보한 원본을 근거로 구현 계약을 구체화한다. 필요한 외부 자료·키가 실제로 없으면 중단하되, 통상적인 구현 선택을 별도 승인 요구로 확대하지 않는다.

## 7. 기능별 커밋 계획

1. `docs(be): 점포 이력 API 설계와 원본 계약 대조` — 이 MD 및 실제 Claude 검토 기록.
2. `feat(db): 인허가 배치 출처 조회 기반 추가` — 확정된 최소 출처 모델·migration·ETL 원자성/멱등성 검사. 필요한 범위만 구현한다.
3. `feat(be): 점포 이력과 영업 기간 조회 구현` — 스키마·서비스·기간/위치 함수 및 해당 테스트.
4. `feat(api): 점포 이력 라우터와 DB 세션 연결` — 수명주기·오류·라우터·격리 통합 검사.
5. `docs(be): 점포 이력 실데이터 검증 결과 기록` — 실제 실행 결과·남은 제한·작업계획 반영.

FE 저장소 변경은 확인된 계약에 맞춰 별도 이슈·브랜치·PR로 추적한다. 테스트하지 않은 내용, 사람의 코드 이해, 미실행 원천 재수집을 완료로 표시하지 않는다.

### Claude Code 검토

검토 범위: 이 MD 한 파일만 Read·Edit로 검토·수정했다. 원본 PDF 3종·코드·DB·FE·ETL 스냅샷은 읽지 않았고 테스트·검사도 실행하지 않았다. 아래 내용은 이 문서의 기재 사실과 현행 BE 작업계획(세션에 제공된 내용)만 근거로 한다. 원본 절 번호·쪽수와 숫자(689,440·355,835·16·56건)는 Codex 기록을 그대로 둔 것이며 재확인하지 않았다.

수정 내용과 이유:

1. **날짜 용어 고정표 추가(§1)**: 원천 갱신일·수집 완료일·적재일·요청 시각이 같은 "기준일"로 섞일 위험이 있어 의미·출처·종료점 사용 여부를 분리했다. 사용자 CSV가 "원천 기준일 미확인"이므로 CSV 검증일·적재일을 DAT_UPDT_PNT로 쓰지 않도록 명시했다.
2. **폐업일 결측 16건 처리(§4)**: 대체 종료점 금지·상태 유지·이력 유지·기간 미산정만 확정하고, 응답 표현은 §6-1로 남겼다. date_flag 56건과의 중복 합산 금지를 추가했다.
3. **개월 산식(§4)**: "동일까지" 오기를 "시작일=종료일"로 고치고, 확정 전에는 산식 구현과 기대값 고정 테스트를 하지 않는다고 명시했다.
4. **source별 기준일(§4)**: 일반/휴게 원천의 data_updated_at을 서로의 종료점으로 쓰지 않도록 했다.
5. **위치 판정표(§3)**: "세부 판정표로 고정한다"만 있고 표가 없어 추가했다. 층만 같은 모든 조합은 unverified, 확인된 다른 층/호수는 same_building으로 두었고, 원문 문자열이 아닌 정규화 값 비교를 명시했다.
6. **source+license_no(§3)**: 다른 source 병합 금지, 응답에 source 포함 필요(FE 계약 추가), 내부 id 비노출을 명시했다.
7. **검토 대기·excluded(§3)**: "명시한다"로만 남아 있던 포함 기준을 작업계획 5절에 맞춰 기본 제외로 적었다.
8. **출처 테이블 요건(§4)**: 원자성(상태 전이·롤백·부분 배치 비노출), 최신 completed 배치 선택, 멱등 재적재·비ETL 필드 보존, 실행 시 상수만 버전으로 인정·사후 추정 금지를 추가했다.
9. **DB 수명주기·읽기 전용·시간 제한·오류 매핑(§5)**: lifespan 소유, 요청별 close, READ ONLY 트랜잭션, 명명된 timeout 설정, DB 오류 코드 보류를 구분했다. DB 오류에 UPSTREAM_ERROR를 쓰는 것은 계약 확인 사항으로 두었다.
10. **meta와 공통 형식(§5)**: 외피·오류 meta={} 유지, loaded_at과 data_updated_at 구분, 키 이름 확정 보류를 명시했다.
11. **구체 테스트표(§5)**: 추상 목록을 기대 결과가 있는 사례로 바꿨다. 기간 숫자 기대값은 일부러 넣지 않았다.
12. **§6 확장**: 출처·meta, DB 운영, 세부 판정 확인 항목을 3~5번으로 추가했다.

- 기간 미산정의 응답 표현(null/상태·사유 필드 위치)과 FE number 필수 타입 보완 범위 — §6-1.
- 개월 산식과 1/31→2/28·윤년·동일일 기대값 — §6-2.
- 현재 CSV update_point 최대값을 원천 기준일로 표기할 수 있는지, 스냅샷 collected_at의 실제 의미 — §6-3.
- meta 키 구조·source별 표현, 선택 배치와 다른 batch_id 행의 처리 — §6-3, §4.
- timeout 값·적용 범위, DB 오류 코드·HTTP 상태 — §6-4.
- floor_unit 생략 시 결과, 원본의 category 필수 여부·CATEGORY_REQUIRED — §6-5. 원본을 읽지 않아 대조하지 못했다.
- building_key 최대 길이 수치.

구현 전 필수 조건:

1. 사용자가 §6-1·§6-2를 확정하고, FE 저장소에 nullable 기간·source 복합 key 보완 이슈가 생성된다. 확정 전 BE가 필수 number 필드에 null을 보내거나 0으로 채우지 않는다.
2. `store_import_batches` migration과 기존 데이터 출처 연결·재적재 방식에 대해 사용자 승인을 받는다. 승인 전 개발 DB에 쓰지 않는다.
3. 기존 stores 행의 batch_id 채움 상태와 source별 update_point 분포(미래값·이상값 포함)를 읽기 전용으로 확인하고 결과를 이 문서에 기록한다.
4. Codex가 원본 API §2-1·§2-4·§4-2와 위치 판정표·meta 후보·오류 코드를 다시 대조하고, 차이를 이 문서에 기록한다.
5. 시간 제한·DB 오류 매핑(§6-4)을 정한다.
6. 이 검토 수정본의 실제 diff를 Codex가 확인한다. 이 응답만으로 검토 완료로 표시하지 않는다.

### Codex 최종 점검 및 구현 계약

Claude 실행 결과 `is_error=false`, Read/Edit 한정 실제 MD 수정 및 위 검토 기록을 확인했다. 검토가 요구한 별도 migration 승인과 모든 구현 선택의 사용자 확정은 원문·기존 사용자 지시에 없는 추가 절차다. 사용자의 기능 진행·중단 후 계속 요청 및 API 변경 시 두 CLAUDE.md 동기화 요청 범위에서 아래 선택을 문서화하고 진행한다. 이를 사용자가 산식별로 승인했다고 기록하지 않는다.

- 응답 항목에 source를 추가한다. name/open_date/close_date는 원자료의 null을 허용하며, 유효하지 않은 개폐업일도 출력에서는 null로 정리한다. 원본 값은 DB에서 보존한다.
- operating_months는 number|null이며 operating_period_status=`fact|no_data`, operating_period_reason=안정적인 사유 코드|null이다. 사유는 FE가 한국어 문구로 표시한다. 계산된 0개월과 결측 null을 구분한다.
- 개월 산식은 §4의 달력상 완료 개월 식을 구현 선택으로 채택한다. 1/31→2/28은 0, 1/31→3/31은 2, 동일일은 0이다. 일수/30 환산은 하지 않는다.
- 원본은 점포 데이터 DAT_UPDT_PNT 최대 날짜를 공통 기준일로 정의한다. Claude가 제안한 source별로 서로 다른 기간 종료점은 원본과 달라 채택하지 않는다. 현재 DB 행에 연결된 검증 배치들의 최대 갱신 날짜를 사용하고, 해당 행의 배치 출처가 없거나 그 배치의 갱신 날짜 품질이 미확인이면 기간을 미산정한다. 응답 버전에 계산에 사용한 배치를 포함한다.
- API source 식별자 R5/R6, source별 batch 상세와 갱신 품질 사유를 meta에 함께 기록한다. 수집 완료 시각이 없는 CSV에 검증 시각을 수집 완료일로 채우지 않는다. collected_at은 미확인 null, 별도 사유를 준다. 배치의 실제 적재 시각과 스냅샷에 기록된 시각·의미는 구분해 저장한다.
- 배치 테이블은 같은 원천 upsert 트랜잭션이 끝나기 전에 삽입되며 commit 후에만 보인다. 별도 pending/completed 상태는 불필요하다. source 일치·batch_id 일치·실패 시 전체 롤백을 검증한다. 기존 스냅샷을 재검증·재적재하여 실제 적용 버전을 부여하고 임의 메타데이터만 소급 주입하지 않는다.
- floor_unit 생략/한쪽 누락/동일 층만 확인은 unverified다. category는 선택 맥락이며 오류는 현행 422 INVALID_PARAM이다. 새 오류 코드는 추가하지 않고 DB 오류·문장 timeout은 500 INTERNAL_ERROR로 안전하게 반환한다. 원본 504 REQUEST_TIMEOUT 및 전체 3초 SLA의 일괄 도입은 이번 범위 밖이다. DB 문장 제한은 명명된 설정 기본 3초로 둔다.
- FE 최소 호환 변경은 별도 이슈·브랜치에서 타입·목업·날짜 정렬·source 복합 key·결측 라벨·계약 문서·CLAUDE.md를 수정하고 lint/build 및 로컬 실행으로 검증한다. BE CLAUDE.md에도 같은 이력 계약을 기록한다.
- 최신 사용자 요청대로 PR 확인 사항 네 문구를 변경하지 않고 `[x]`로 작성한다. 사람의 코드 이해 항목은 사용자가 보면서 진행하고 있다는 명시적 확인을 근거로 한다. 로컬 실행·비밀정보 검사·양쪽 문서 동기화는 실제 수행 후 체크한다.

### 재적재 성능 점검

출처 연결 재적재 중 chunk별 다중 values SQL 생성 비용을 확인했다. 개발 DB와 분리한 임시 PostGIS DB의 동일한 합성 5,000건에서 기존 방식 6.401초, 같은 ON CONFLICT 규칙의 psycopg 매개변수 묶음 실행 1.073초였다. 보호 필드·원천별 advisory lock·트랜잭션·입력 건수 집계는 유지하고 SQL 실행 방식만 바꾼다. 실제 데이터의 동일한 속도 배수를 보장하는 수치는 아니며 격리 통합 검사를 다시 실행한다.
