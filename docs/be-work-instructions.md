# SpotON-BE 개발 작업 지시

[be-work-plan.md](be-work-plan.md)(BE 개발 작업계획서)를 **먼저 처음부터 끝까지 읽고**, 이후 모든 백엔드 개발은 해당 문서를 최상위 작업 기준으로 진행한다.

API 계약 보완안과 외부 문서 반영 대기는 [be-contract-amendments.md](be-contract-amendments.md)에서 관리한다. 로컬 보완안을 외부 명세에 이미 반영된 계약으로 간주하지 않는다.

실무 규칙은 [be-development-rules.md](be-development-rules.md)를 함께 따른다. 사용자 결정과 기존 BE 문서가 PDF 참고 지침보다 우선하며 FE·BE 별도 저장소 구조를 유지한다.

## 1. 기본 원칙

이 프로젝트는 Spot:ON 백엔드 개발이다.

작업계획서에 정의된:

- 개발 범위
- PHASE 순서
- API 목록
- DB 테이블
- ETL 흐름
- 분석 로직
- 테스트 기준
- 완료 조건

을 임의로 변경하지 않는다.

문서에 없는 기능을 임의로 추가하거나 기존 기능의 의미를 변경하지 않는다.

특히 다음 사항은 확정된 기준이다.

### 서비스 범위

- 대상 지역: 서울특별시
- 1차 업종:
  - 카페
  - 음식점

### 음식점 세부 업종

- 한식 `korean`
- 중식 `chinese`
- 일식 `japanese`
- 양식 `western`

카페는 별도 세부 업종을 두지 않는다.

다음 업종은 이번 서비스 분석 대상에서 제외한다.

- 키즈카페
- 라이브카페
- 분식
- 치킨
- 주점
- 기타 음식점
- 제과점

### 지표 범위

다음 기능은 구현한다.

- 동종업체 수
- 최근 12개월 개업 수
- 최근 12개월 폐업 수
- 연도별 개·폐업 추이
- 평균 영업 기간
- 서울시 공식 폐업률
- Spot:ON 참고 폐업률
- 1년 생존율
- 3년 생존율
- 추정매출
- 생활인구
- 상권변화지표
- 주야간 인구비

추정매출·생활인구·상권변화지표·주야간 인구비의 수치 제공은 출처 확보와 검증 후 활성화한다. 미확보는 `pending`, 확보된 자료의 조건별 결측은 `no_data`로 구분한다. 기본 점포 조회 개발을 데이터 미확보로 중단하지 않는다.

**LQ는 이번 개발에서 구현하지 않는다.**

화면, API, 분석 함수, AI 입력, 테스트 어디에도 LQ를 새로 추가하지 않는다.

# 2. 작업 우선순위

반드시 작업계획서의 PHASE 순서를 따른다.

```text
PHASE 0  개발환경 및 프로젝트 기반
   ↓
PHASE 1  공통 API / DB 기반
   ↓
PHASE 2  stores / 인허가 ETL
   ↓
PHASE 3  핵심 조회 API
   ↓
PHASE 4  상권·매출·생활인구 데이터
   ↓
PHASE 5  분석 API
   ↓
PHASE 6  AI 해석
   ↓
PHASE 7  캐시·로그·상담·통합 테스트
```

뒤 단계 구현을 위해 앞 단계를 임시 하드코딩으로 우회하지 않는다.

예를 들어:

- DB가 없는데 `/risk`부터 구현
- ETL이 없는데 테스트용 숫자를 API에 하드코딩
- `/risk`가 완성되지 않았는데 AI가 직접 지표 계산

같은 방식은 사용하지 않는다.

# 3. 현재 가장 먼저 진행할 작업

처음부터 전체 기능을 한 번에 구현하지 않는다.

우선 아래 순서까지만 진행한다.

1. 프로젝트 구조 확인
2. FastAPI 애플리케이션 초기화
3. `/api/health`
4. PostgreSQL + PostGIS 연결
5. 공통 API Response/Error Schema
6. `stores` 모델
7. Alembic Migration
8. 인허가 데이터 ETL 기반
9. 업종 매핑
10. `building_key` 생성
11. 적재 데이터 검증

이 단계가 안정화된 후:

```text
/geocode
→ /stores/history
→ /stores/nearby
→ /meta/data-range
→ /stores/snapshot
```

순서로 개발한다.

# 4. API 계약

API를 임의로 설계하지 않는다.

프로젝트의 **API 명세서 v1.2가 FE↔BE 간 계약**이다.

공통 응답은:

```json
{
  "data": {},
  "meta": {},
  "error": null
}
```

형식을 사용한다.

필드명, enum, endpoint 이름도 임의로 변경하지 않는다.

API 변경이 반드시 필요하다고 판단될 경우:

1. 바로 코드부터 수정하지 말 것
2. 기존 명세와 충돌하는 부분을 설명할 것
3. 변경이 필요한 이유를 제시할 것
4. 변경 후보를 제안할 것
5. 승인 전까지 기존 명세 기준으로 유지할 것

# 5. 데이터 처리 원칙

공공데이터는 사용자 요청마다 직접 호출하지 않는다.

기본 흐름:

```text
공공데이터
→ ETL
→ 정제
→ PostgreSQL/PostGIS
→ API 조회
```

다만 주소 검색처럼 실시간 호출이 필요한 API는 명세서 기준대로 별도 처리한다.

# 6. stores 기준

`stores`가 핵심 데이터 테이블이다.

주요 필드는 작업계획서 기준을 따른다.

특히:

- `license_no`
- `building_key`
- `floor_unit`
- `location_level`
- `open_date`
- `close_date`
- `status`
- `category`
- `sub_category`
- `area_m2`
- `lat`
- `lng`
- `geom`
- `raw_x`, `raw_y`, `raw_crs`
- `coord_source`, `coord_flag`, `date_flag`
- `is_temporary`, `category_review_flag`
- `is_franchise`
- `deleted_at`
- `batch_id`

의 의미를 임의로 바꾸지 않는다.

원본 좌표·날짜·업태를 보존하고, 좌표 보완은 출처와 변환 이력을 남긴다. 날짜 이상치는 원본 삭제 대신 해당 날짜가 필요한 집계에서 제외한다. 검토 전 카페 키워드 후보와 한시적 사업장은 기본 집계에서 제외한다.

---

# 7. building_key

건물 식별 기준은 **지번주소**다.

형식:

```text
{자치구}-{법정동}-{본번}-{부번}
```

예:

```text
마포구-서교동-123-4
```

산 지번:

```text
마포구-상암동-산12-3
```

도로명주소 자체를 building key로 사용하지 않는다.

건물명·층·호수는 지번에서 분리하고 `외 n필지`는 대표 지번을 식별한다. 도로명·지번 상세 주소 모두를 층·호수 추출 대상으로 삼고 충돌 시 위치 미확인으로 둔다.

---

# 8. 시점 조회

기준 시점 T에 영업 중인 점포:

```text
open_date <= T
AND
(close_date IS NULL OR close_date > T)
```

FE에서 별도로 계산하지 않는다.

---

# 9. 공간 검색

주변 점포 검색은 PostgreSQL + PostGIS를 사용한다.

반경 경계는 포함한다.

```text
distance <= radius
```

따라서:

- 499m → 포함
- 500m → 포함
- 501m → 제외

---

# 10. 공식 지표와 Spot:ON 참고지표

둘을 반드시 분리한다.

### 서울시 공식

- 공식 폐업률
- 공식 창업위험도 안내
- 서울시 원천 상권변화지표

현재 조회는 데이터셋별 최신 공표·적재 검증 분기, 과거 조회는 요청 시점의 분기를 사용하고 실제 적용 분기를 표시한다. 선택 분기의 값이 없으면 다른 분기로 재대체하지 않는다. 공식 창업위험도는 수치 수집 경로 확인 전 링크 전용으로 제공하는 계약 보완을 진행한다.

세부 상권을 우선하고 관광특구를 병기한다. 상권 밖에서는 상권 공식 수치를 대신 계산하지 않고 반경과 겹치는 상권 목록을 별도로 제공한다. 모호한 상권 중첩은 임의 선택하지 않는다.

### Spot:ON 참고지표

- 최근 12개월 참고 폐업률
- 1년 생존율
- 3년 생존율
- 동종업체 수

Spot:ON 자체 종합 위험점수나 자체 위험등급은 만들지 않는다.

예:

```text
62.4점
주의
고위험
추천
비추천
```

등의 종합판정은 구현하지 않는다.

---

# 11. 추정매출

추정매출은 **상권 단위 데이터**다.

다음을 구현하지 않는다.

```text
반경 500m 예상 매출
해당 점포 예상 매출
주변 점포 평균 매출
```

상권과 반경이 겹치는 경우 각 상권별 데이터를 반환한다.

여러 상권의 추정매출을 임의로 합산하지 않는다.

---

# 12. 생활인구

생활인구는 실제 방문객 수가 아니라 **통계적 추정 데이터**다.

250m 격자 데이터를 기준으로 처리한다.

비식별 결측값을 0으로 임의 변환하지 않는다.

결측은 별도로 기록한다.

---

# 13. 상권변화지표

서울시 원천 상권변화지표의 정의를 그대로 사용한다.

Spot:ON에서 임의로:

- 점수
- 등급
- 위험 단계

로 변환하지 않는다.

# 14. AI 개발 원칙

```text
데이터
→ 서버 계산
```

AI가 직접:

- 위험등급 계산
- 성공률 계산

을 하면 안 된다.

# 22. Git 원칙

기능 개발은 `main`에서 직접 하지 않는다.

```text
main
└─ develop
   ├─ feat/...
   ├─ fix/...
   └─ docs/...
```

작업 시작 전 최신 `develop` 기준으로 기능 브랜치를 생성한다.

`main`은 기본·최종 반영 브랜치, `develop`은 개발 통합 브랜치다. 기능·수정·문서는 각각 `feat/...`, `fix/...`, `docs/...`에서 작업하고 PR로 `develop`에 통합한다.

```bash
git checkout develop
git pull origin develop
git checkout -b feat/be-geocode-api
```

커밋 예:

```text
feat(be): 주소 검색 API 구현
fix(be): 반경 경계 포함 조건 수정
test(be): 시점 조회 경계 테스트 추가
data(etl): 음식점 업종 매핑 추가
```

API 명세 변경이 필요한 경우 코드부터 변경하지 않는다.

# 최종 지시

**BE 개발 작업계획서를 이 프로젝트의 작업 기준 문서로 취급한다.**

매 작업마다:

```text
현재 PHASE 확인
→ 다음 작업 확인
→ 구현
→ 테스트
→ 완료 여부 기록
→ 다음 작업
```

순서로 진행한다.

작업계획서와 코드가 충돌하면 임의로 판단해서 문서를 무시하지 말고, 충돌 내용을 먼저 알린다.

가장 중요한 원칙 네 가지:

1. **데이터 기반부터 완성하고 API를 만든다.**
2. **FE에서 계산하지 않고 BE에서 계산한다.**
3. **공식 지표와 Spot:ON 참고지표를 분리한다.**
